## Research
_Last updated by: legacy-android-researcher | 2026-07-19_

### Summary
The `:model` module is AntennaPod's shared domain layer: 27 `.java` files, ~3,800 LOC, 0 Kotlin, holding the plain data objects (Feed, FeedItem, FeedMedia, Chapter, download requests/results, playback types) that essentially every other module in the app is built on. It is a leaf module — its `build.gradle` declares no dependency on any other project module, only `androidx.annotation` (annotation-processor), `androidx.media`, and `commons-lang3` (`model/build.gradle:15-18`). Architecturally it is a bag of POJOs, enums, and one interface (`Playable`): mutable fields with getters/setters, several hand-written `equals`/`hashCode` implementations, four `Parcelable` types, and two `Serializable` types (`Feed`, `FeedItem`). There is no DI anywhere — a grep for dagger/hilt/`javax.inject`/`@Inject` across the module and all Gradle files returns nothing — so nothing constructs these objects through a container; callers `new` them directly or rebuild them from a `Parcel`/database row.

The requested work is the `kotlin` track only (not gradle-kts/di/concurrency/compose/navigation). Converting these files to idiomatic Kotlin is mostly mechanical J2K, but the module is deceptively risky for a first case-study milestone for three reasons: (1) it is the single most-depended-on module in the repo — **27 modules consume `:model`'s public API** (`event`, `storage:*`, `parser:*`, `playback:*`, `net:*`, all `ui:*`, `app`, `app-wearos`), so any getter rename, nullability tightening, or `equals`/`hashCode` change ripples app-wide; (2) several classes carry real Android-framework coupling (`Parcelable`, `TextUtils`, `AudioEffect`, `MediaMetadataRetriever`, `MediaBrowserCompat`) whose Java semantics J2K reproduces literally but which are not exercised by the plain-JUnit test suite; and (3) the safety net is thin and uneven — only 6 of 27 classes have any test, and the download/playback/transcript/preferences classes have none.

### Findings

#### Existing surface
27 production classes under `model/src/main/java/de/danoeh/antennapod/model`, in four packages:
- **`feed/`** (19 files): `Feed` (538 LOC, `Serializable`), `FeedItem` (509 LOC, `Serializable`), `FeedMedia` (548 LOC, implements `Playable` → `Parcelable`), `FeedPreferences` (324), `FeedItemFilter` (153), `FeedFilter` (150), `Chapter` (110), `FeedFunding` (92, has two `public` mutable fields `url`/`content` — `FeedFunding.java:12-13`), `EmbeddedChapterImage`, `Transcript`, `TranscriptSegment`, and the enums `SortOrder`, `VolumeAdaptionSetting`, `TranscriptType`, `FeedCounter`, `FeedOrder`, plus `SubscriptionsFilter`.
- **`download/`** (5 files): `DownloadRequest` (227 LOC, `Parcelable`), `DownloadResult` (123), `ProxyConfig`, `DownloadStatus`, and the `DownloadError` enum.
- **`playback/`** (4 files): `Playable` (interface extending `Parcelable, Serializable` — `Playable.java:15`), `RemoteMedia` (299 LOC, `Parcelable`, implements `Playable`), `MediaType` enum, `TimerValue`.
- **root**: `MediaMetadataRetrieverCompat` (subclasses the Android framework `MediaMetadataRetriever` — `MediaMetadataRetrieverCompat.java:10`).
- 7 enums total (`DownloadError`, `FeedCounter`, `FeedOrder`, `SortOrder`, `TranscriptType`, `VolumeAdaptionSetting`, `MediaType`); one interface (`Playable`). Two enums carry non-trivial logic beyond constants: `SortOrder` (int `code`/`Scope` fields, `fromCodeString`/`parseWithDefault` — `SortOrder.java:37-76`) and `VolumeAdaptionSetting` (int↔enum mapping plus framework-backed `isBoostSupported` — `VolumeAdaptionSetting.java:24-64`).

#### Where state / data lives
The module holds no repositories or persistence itself — it is pure data types constructed and consumed elsewhere. `:model` has **no project-module dependencies** (`model/build.gradle:14-18` lists only external libs), so all coupling flows inward. 27 modules declare `project(':model')` and construct/consume these types:
- `event`, `storage:database`, `storage:importexport`, `storage:preferences`
- `parser:feed`, `parser:media`, `parser:transcript`
- `playback:base`, `playback:cast`, `playback:service`
- `net:common`, `net:discovery`, `net:download:service`/`service-interface`, `net:sync:service`/`service-interface`/`wear-interface`
- `ui:chapters`, `ui:discovery`, `ui:echo`, `ui:episodes`, `ui:glide`, `ui:statistics`, `ui:transcript`, `ui:widget`
- `app`, `app-wearos`

Notable cross-object state inside the module: `Feed` ↔ `FeedItem` ↔ `FeedMedia` form a bidirectional object graph (`FeedItem.feed` is `transient`, `FeedItem.chapters` is `transient` — `FeedItem.java:42,69`; `FeedMedia.item` is `@Nullable volatile` — `FeedMedia.java:44`). `DownloadRequest`, `FeedMedia`, and `RemoteMedia` are rebuilt from `Parcel` (e.g. `DownloadRequest.java:38-42,93-101`), i.e. they cross process/IPC boundaries via Intents — their marshalling behavior is load-bearing.

#### Platform-specific notes
- **minSdk 23, targetSdk 36, compileSdk 36** (`common.gradle:3,7,8`); Java source/target **21** (`common.gradle:39-40`).
- **No DI framework** anywhere in the repo — confirmed by empty grep for dagger/hilt/`javax.inject` across `*.gradle` and `*.java`. Nothing injects these types.
- **Java/Kotlin ratio in this module: 27 Java / 0 Kotlin.** Kotlin exists in the repo only in `app-wearos` (14 `.kt` files) — that module already applies the Kotlin plugin, so there is precedent for mixed Java/Kotlin builds, but `:model` itself has never compiled Kotlin.
- **Build-config prerequisite for the kotlin track:** `model/build.gradle` applies only `alias(libs.plugins.android.library)` (`model/build.gradle:1-3`); it does **not** apply the Kotlin Android plugin. The plugin is available in the version catalog (`gradle/libs.versions.toml:83` → `kotlin-android` at Kotlin `2.3.20`, line 3) but must be added to this module before any `.kt` file will compile. This is part of the kotlin track itself (adding a one-line plugin alias to the existing Groovy build file), **not** the gradle-kts track (which would convert the build file to KTS). The `common.gradle` checkstyle task only scans `**/*.java` (`common.gradle:151`) and the `ktlint` plugin (catalog line 86) is not applied to `:model`, so converted Kotlin will initially have no lint gate here — flag for the planner.
- Android-framework coupling that makes J2K output un-unit-testable under plain JUnit (no Robolectric on these tests): `Parcelable`/`Parcel` in `DownloadRequest`, `FeedMedia`, `RemoteMedia`, `Playable`; `android.text.TextUtils` in 6 files (`MediaType.java:19`, `DownloadRequest.java:90`, `FeedPreferences.java:310`, `EmbeddedChapterImage.java:53`, `SortOrder.java:61`, `SubscriptionsFilter.java:31,60`); `android.media.audiofx.AudioEffect` (`VolumeAdaptionSetting.java:48`); `android.net.Uri`, `MediaBrowserCompat`/`MediaDescriptionCompat` (`FeedMedia.java:3,8-9`, `RemoteMedia`); `MediaMetadataRetriever` (`MediaMetadataRetrieverCompat.java:3,10`).

#### Tests in this area
9 test files under `model/src/test` (6 test classes + 3 `*Mother` factory helpers), all JUnit4 + Mockito, no Robolectric:
- **`VolumeAdaptionSettingTest`** — 14 tests: int↔enum mapping in both directions, out-of-range/negative throwing `IllegalArgumentException`, adaption-factor ordering. Stubs the framework path via `setBoostSupported(false)` in `@Before` (`VolumeAdaptionSettingTest.java:18-25`); the real `AudioEffect.queryEffects()` branch is **not** exercised.
- **`FeedFilterTest`** — 7 tests: include/exclude/combo keyword filters and minimal-duration filter (`FeedFilter.shouldAutoDownload`). Thorough for `FeedFilter`.
- **`FeedItemTest`** — 9 tests: `updateFromOther` image/date merge logic, `setNew`/`setPlayed` state transitions, `setDescriptionIfLonger` shownotes-length logic.
- **`FeedTest`** — 5 tests: `updateFromOther` image merge, `setSortOrder` scope enforcement (INTRA_FEED allowed, INTER_FEED throws, null allowed).
- **`FeedMediaTest`** — 3 tests: `setDownloaded` side-effect on item state only; uses a Mockito mock of `FeedItem`. Does **not** test any `Parcelable` round-trip.
- **`FeedItemFallbackLinkTest`** — 1 parameterized test, 7 cases: `getLinkWithFallback` null/empty/blank fallback from item link to feed link.
- Helpers: `FeedMother.anyFeed`, `FeedItemMother.anyFeedItemWithImage`, `FeedMediaMother.anyFeedMedia` — these pin specific constructor signatures (e.g. `new Feed(0, null, "title", …)` with 14 args in `FeedMother`, `new FeedMedia(null, url, size, mime)` in `FeedMediaMother`); constructor-shape changes during conversion will break these.

**Characterization-test gaps (behavior with zero coverage today — must be written BEFORE conversion):**
- **`Parcelable` marshalling is completely untested.** No test round-trips `DownloadRequest`, `FeedMedia`, or `RemoteMedia` through a `Parcel`. `DownloadRequest` has non-trivial marshalling: null username/password are written as `""` and read back via `nullIfEmpty` → `null` (`DownloadRequest.java:78-79,89-90`). This asymmetric null handling is exactly the kind of behavior J2K can silently alter, and nothing would catch it.
- Hand-written `equals`/`hashCode` in 8 classes (`DownloadRequest`, `Chapter`, `EmbeddedChapterImage`, `Feed`, `FeedFunding`, `FeedItem`, `FeedMedia`, `RemoteMedia`) are **untested** as equality contracts. Several are field-selective (e.g. `DownloadRequest.equals`/`hashCode` include some fields and omit others — `DownloadRequest.java:104-148`).
- Zero tests for: all `download/*` (`DownloadRequest`, `DownloadResult`, `DownloadStatus`, `ProxyConfig`, `DownloadError`), all `playback/*` (`Playable`/`RemoteMedia`/`MediaType`/`TimerValue`), `FeedPreferences`, `FeedItemFilter`, `SubscriptionsFilter`, `Chapter`, `EmbeddedChapterImage`, `Transcript`/`TranscriptSegment`/`TranscriptType`, `FeedFunding`, `FeedCounter`, `FeedOrder`, `MediaMetadataRetrieverCompat`, and `SortOrder`'s own `fromCodeString`/`parseWithDefault` (only its `scope` field is touched indirectly via `FeedTest`).

### Constraints & Risks
- **Public API must not silently break for 27 downstream modules.** Getter/setter names, method signatures, constructor arities, field visibility (`FeedFunding.url`/`content` are `public` fields — `FeedFunding.java:12-13`; `SortOrder.code`/`scope` are `public final` — `SortOrder.java:37-40`), and static constants (e.g. `FeedItem.NEW/UNPLAYED/PLAYED`, `Feed.FEEDFILETYPE_FEED`) are all consumed externally and must survive conversion byte-for-byte at the API level.
- **Kotlin null-safety hazards (the core of the kotlin track):** annotation coverage is partial — 23 `@Nullable` and 11 `@NonNull` across only 11 of 27 files. **Every unannotated reference type becomes a Kotlin platform type**, so J2K will guess nullability and frequently guess wrong. High-risk spots: `Playable`'s interface getters are mostly unannotated (`getEpisodeTitle`, `getStreamUrl`, `getLocalFileUrl`, `getIdentifier` returns `Object`) yet `getDescription`/`getImageLocation` are `@Nullable` (`Playable.java:21-126`) — a mismatch J2K will not reconcile across `FeedMedia` and `RemoteMedia` implementers. `TextUtils`-based null idioms will mistranslate: `TextUtils.isEmpty(x)` does **not** smart-cast `x` to non-null in Kotlin (`SortOrder.java:61`, `MediaType.java:19`), and `TextUtils.split("", div)` returns an empty array where Kotlin's `String.split` would return `[""]` (`SubscriptionsFilter.java:31`) — a semantic trap if anyone "idiomatically" swaps it out.
- **`equals`/`hashCode` trap:** converting POJOs to Kotlin `data class` would auto-generate `equals`/`hashCode`/`copy` over the primary-constructor properties, which is **not** equivalent to the existing field-selective hand-written implementations. These classes must convert to regular `class` with the existing `equals`/`hashCode` preserved verbatim, or behavior changes for map keys, dedup, and `updateFromOther` merge logic.
- **`volatile`/`transient` semantics** must be preserved: `FeedMedia.item` is `volatile` (`FeedMedia.java:44`) → needs `@Volatile`; `FeedItem.feed`/`chapters` and other `transient` fields → need `@Transient` to keep `Serializable` behavior identical.
- **Enum-with-mutable-state:** `VolumeAdaptionSetting.adaptionFactor` is a non-final field (`VolumeAdaptionSetting.java:17`) and the class holds mutable static `boostSupported` plus a `@VisibleForTesting` setter (`VolumeAdaptionSetting.java:41-64`); the Kotlin conversion must keep the test seam (`setBoostSupported`) working since `VolumeAdaptionSettingTest` depends on it.
- **Scope discipline:** the kotlin track here is J2K + preserving behavior; do not fold in DI, coroutines, or `data class` "modernization" that changes equality — those are out of scope.

### Unknowns
Open questions for the planner to resolve:
1. **Conversion granularity / milestone slicing:** all 27 files in one milestone, or staged (e.g. leaf enums first → simple POJOs → Parcelable/Serializable/`Playable` graph last)? The `Feed`/`FeedItem`/`FeedMedia`/`Playable` cluster is interdependent and hardest; the standalone enums are near-zero-risk.
2. **Characterization tests before conversion:** the pipeline's value depends on behavioral equivalence, but Parcelable/`equals`/download/playback behavior is untested. Does the plan add characterization tests as Step 1 (recommended), and do the Parcelable round-trip tests require Robolectric (currently absent from `model/src/test`) or can they be structured as JVM tests? This is a planner/client decision, not assumed here.
3. **`data class` vs plain `class` policy:** confirm the equivalence-preserving default (plain `class`, keep hand-written `equals`/`hashCode`) rather than idiomatic `data class`.
4. **Platform-type nullability calls:** for each unannotated public getter/param that becomes a platform type, someone must decide the intended Kotlin nullability. Getting this wrong changes the compile-time contract for downstream callers. Who signs off — and is upstreaming to AntennaPod in view (affects how aggressively to add `@Nullable` first, in Java, before converting)?
5. **Lint gate:** should the plan also wire `ktlint` into `:model` (catalog line 86, currently unapplied) so converted Kotlin is style-gated, given checkstyle only covers `.java`?

### Objective
Convert the 8 lowest-risk, framework-free files of the `:model` module (4 pure enums + 4 simple POJOs) from Java to idiomatic Kotlin (`kotlin` track only), preserving the public API byte-for-byte for the 27 downstream modules and proving behavioral equivalence with characterization tests written first. This is the first, deliberately small milestone of the AntennaPod portfolio case study; the remaining 19 files (the `Feed`/`FeedItem`/`FeedMedia`/`Playable` graph, all `Parcelable`/framework-coupled types) are explicitly deferred to follow-up milestones.

### Resolved Decisions

**1. Conversion granularity / milestone slicing → STAGED. Milestone 1 = 8 files only.**
The 27 files carry very uneven risk, and this is the case study's first defensible increment. Milestone 1 takes only the files that (a) have zero Android-framework coupling (no `Parcelable`, `TextUtils`, `AudioEffect`, `Uri`, `MediaMetadataRetriever`), (b) have no hand-written `equals`/`hashCode`, and (c) are not referenced by any test or `*Mother` helper **within `model/src/test`** — so they convert in isolation without touching the tested `Feed`/`FeedItem`/`FeedMedia` cluster inside `:model`. Those 8 files:
- Enums: `FeedOrder`, `FeedCounter`, `TranscriptType`, `DownloadError`
- POJOs: `DownloadStatus`, `TimerValue`, `TranscriptSegment`, `ProxyConfig`

**Downstream exposure (accurate, repo-wide):** criterion (c) is scoped to `:model`'s own test suite only. Confirmed by grep across the whole repo, all 8 classes **do** have downstream consumers and several have downstream *test* references outside `:model` — e.g. `FeedOrder`/`FeedCounter` in `net/download/service/.../DbReaderTest.java`, `DownloadError` in `storage/database/.../FeedDatabaseWriterTest.java` and `app/src/androidTest/.../HttpDownloaderTest.java` + `DownloadLogTest.java`, plus main-source consumers like `app/.../DownloadErrorLabel.java` (an exhaustive `switch` over all 23 `DownloadError` constants) and `storage/database/.../DBReader.java` (switches over `FeedOrder`). They were selected as low-risk *relative to the untested `Feed`/`FeedItem`/`FeedMedia` cluster* — not because they have zero test exposure. That downstream exposure is exactly why the cross-module verification added below (Step 7 + Acceptance Criteria) is required to *prove* the "no public API break" claim rather than assert it.

Deferred to later milestones (see Out of Scope) and NOT converted here: everything with framework coupling (`MediaType`/`SortOrder`/`VolumeAdaptionSetting`/`MediaMetadataRetrieverCompat`), hand-written `equals`/`hashCode` (`Chapter`, `EmbeddedChapterImage`, `Feed`, `FeedFunding`, `FeedItem`, `FeedMedia`, `RemoteMedia`, `DownloadRequest`), `Parcelable` marshalling, and the `Playable` interface graph.

**2. Characterization tests before conversion, and Robolectric? → YES tests as Step 1; NO Robolectric needed for this milestone.**
Step 1 writes Java characterization tests pinning current behavior for all 8 in-scope classes before any conversion (non-negotiable per the coverage gap). Because none of the 8 touch the Android framework or `Parcel`, every test runs on plain JVM JUnit4 exactly like the existing `model/src/test` suite — no Robolectric dependency is added. The Parcelable-round-trip question (`DownloadRequest`/`FeedMedia`/`RemoteMedia`) is real but belongs to a later milestone: `android.os.Parcel` is a stubbed no-op under plain unit tests, so those round-trips WILL require Robolectric (or an instrumented test) when that milestone is planned. Out of scope here.

**3. `data class` vs plain `class` → plain `class`, no `data class`, preserve existing equality semantics.**
None of the 4 in-scope POJOs (`DownloadStatus`, `TimerValue`, `TranscriptSegment`, `ProxyConfig`) define `equals`/`hashCode` today, so they currently use JVM reference equality. Converting them to `data class` would synthesize value-based `equals`/`hashCode`/`copy`, silently changing behavior for any downstream use as map keys / in sets / dedup. Convert to plain `class`, add no `equals`/`hashCode`, preserve reference equality. The characterization tests explicitly pin this (two equal-content instances must remain non-equal).

**4. Platform-type nullability sign-off → planner owns it for these 8 files (documented below); contract-preserving default = nullable-unless-provably-non-null.**
For the 27 downstream consumers, tightening a nullable reference to non-null is a compile-time contract break. Default policy for unannotated reference types: keep them **nullable (`String?`)** unless the value is a compile-time constant or provably never null, and add explicit `@Nullable`/`@NonNull`-equivalent Kotlin types rather than leaving platform types. Per-file calls for this milestone:
- `TranscriptType.fromMime(type: String?)` — param nullable (current code null-checks and returns `NONE`); `canonicalMime`/`priority` non-null (constant-initialized); return `TranscriptType` non-null.
- `TranscriptSegment(words: String?, speaker: String?)` — both nullable: constructor params are unannotated today and `append` does `words += ...` which tolerates a null seed under Java semantics; keep nullable to avoid tightening. Getters return `String?`.
- `ProxyConfig` — already fully annotated in Java (`@Nullable host/username/password`, non-null `type`); mirror exactly (`Proxy.Type`, `String?`, `Int`, `String?`, `String?`).
- `DownloadStatus`, `TimerValue`, `FeedOrder`, `FeedCounter`, `DownloadError` — primitives/enums only, no nullability decisions.
The broader question — whether to upstream these conversions to AntennaPod, which would change how aggressively to add `@Nullable` in Java first — has commercial/strategic implications and is parked in Open Questions for José. It does not block this milestone.

**5. Wire ktlint into `:model`? → YES, minimal, as a discrete setup step.**
Introducing the first Kotlin into the repo's most-depended-on module with no style gate (checkstyle scans `**/*.java` only) is a poor precedent for a case study about verification quality. Apply `alias(libs.plugins.ktlint)` (already in the catalog, line 86) to `model/build.gradle` with the default ruleset — no custom `.editorconfig` beyond defaults. If wiring it turns out to require root-level classpath/config changes beyond `model/build.gradle`, that is a scope change → stop and raise it, do not expand File Scope.

### Steps
_All steps are within the `kotlin` track; each leaves the build green and is independently committable. Grouped so each conversion diff re-runs the Step-1 characterization tests to prove equivalence._

1. **Write Java characterization tests** pinning current behavior for all 8 in-scope classes, before any conversion (build stays all-Java, green). New test files under `model/src/test/java/de/danoeh/antennapod/model/…`:
   - `FeedOrderTest`, `FeedCounterTest` — pin each `.id` constant, `fromOrdinal(knownId)` → correct constant, and `fromOrdinal(unknownId)` → documented default (`MOST_RECENT_EPISODE` / `SHOW_NONE`).
   - `TranscriptTypeTest` — pin `priority`/`canonicalMime` per constant; `fromMime` for each mime incl. aliases (`application/srr`, `application/x-subrip` → `SRT`), `null` → `NONE`, unknown → `NONE`.
   - `DownloadErrorTest` — pin `getCode()` per constant, `fromCode(knownCode)` round-trip, and `fromCode(unknownCode)` throws `IllegalArgumentException`.
   - `DownloadStatusTest`, `TimerValueTest` — constructor→getter round-trip, static constants (`STATE_QUEUED/COMPLETED/RUNNING`), and reference-equality pin (two same-content instances are NOT equal).
   - `TranscriptSegmentTest` — constructor→getter round-trip; `append` advances `endTime` and concatenates words with a single space; reference-equality pin. **Plus the null-seed case named as a live risk in Resolved Decision 4:** construct with `words = null`, call `append("foo")`, and assert the exact string Java produces today via `words += " " + wordsToAppend` (`null` coerces to `"null"`, i.e. result `"null foo"` — pin whatever the current Java source actually yields, verified by running the test green against the unconverted `.java`). This pins the exact behavior J2K must preserve before conversion.
   - `ProxyConfigTest` — field assignment incl. nullable `host`/`username`/`password`, `DEFAULT_PORT` constant, reference-equality pin.
2. **Apply the Kotlin Android plugin and wire ktlint** to `model/build.gradle` — add `alias(libs.plugins.kotlin.android)` and `alias(libs.plugins.ktlint)` (no `.kt` files yet, so build stays green; existing checkstyle/Java tests unaffected). No new tests; existing suite must stay green.
3. **Convert `FeedOrder` and `FeedCounter` to Kotlin** (`FeedOrder.kt`, `FeedCounter.kt`) — Kotlin enums with `@JvmField val id: Int` and `@JvmStatic fun fromOrdinal(...)` in the companion so Java callers keep `X.id` field access and `X.fromOrdinal(...)` static calls. Validated by `FeedOrderTest`/`FeedCounterTest` (unchanged, green).
4. **Convert `TranscriptType` and `DownloadError` to Kotlin** (`TranscriptType.kt`, `DownloadError.kt`) — `@JvmField` for `priority`/`canonicalMime`; `@JvmStatic` companion `fromMime`/`fromCode`; preserve `DownloadError.getCode()` signature and the `IllegalArgumentException` on unknown code. Validated by `TranscriptTypeTest`/`DownloadErrorTest`.
