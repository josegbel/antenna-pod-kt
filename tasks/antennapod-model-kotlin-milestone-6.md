## Research
_Last updated by: legacy-android-researcher | 2026-07-24_

### Summary
`:model` is a pure data-carrier Gradle library module (`de.danoeh.antennapod.model`), currently 4 Java / 23 Kotlin after Milestone 5. The four remaining Java files are the "Tier C" cluster identified in Milestone 5's research: `DownloadRequest` (227 LOC), `FeedMedia` (548 LOC), `RemoteMedia` (299 LOC), and the `Playable` interface (128 LOC). The live-source LOC counts match Milestone 5's inventory exactly, so that inventory is confirmed still current — no files changed shape since. What binds these four together and separates them from Tiers A/B is that they all implement `android.os.Parcelable` for real IPC use — the types are marshalled through `Intent`/`Bundle`/`Parcel` into the download service and playback service and (for `FeedMedia`) exposed to `MediaBrowserCompat`. `Playable` additionally extends `java.io.Serializable`; `FeedMedia` and `RemoteMedia` are its only two implementers (confirmed repo-wide — no external implementers), and both are in scope this milestone. All three concrete classes carry hand-written, field-selective `equals`/`hashCode` (including a mutual `FeedMedia`↔`RemoteMedia` cross-type `equals`), which must be preserved verbatim and must NOT become `data class`es.

This milestone is the last slice of the `:model` kotlin track — after it the module is 100% Kotlin. The conversion is mechanical J2K per file, but the value proposition is behavioral equivalence of the `Parcel`/`Bundle` marshalling, which is where the real hazards live: each type parcels only a *subset* of its fields and applies *asymmetric* null/empty transforms on the round trip (documented per-type below). Per José's 2026-07-24 resolved decision, characterization uses **Robolectric added to `:model`'s test deps** to exercise real `Parcel`/`Bundle` round-trips under plain JUnit — a disclosed one-milestone exception to the Robolectric-free precedent. Notably, Robolectric is already used in 10+ test classes elsewhere in this repo (incl. an existing `DownloadRequest` Parcel-round-trip test in `:net:download:service-interface`); the precedent it breaks is specific to `:model`, not the repo.

### Findings

#### Existing surface
- **`DownloadRequest`** (`model/src/main/java/de/danoeh/antennapod/model/download/DownloadRequest.java`, 227 LOC): `Parcelable` only (NOT `Serializable`, NOT `Playable`). Immutable core fields (`destination`/`source`/`title`/`feedfileId`/`feedfileType`/`arguments`) plus mutable `username`/`password`/`lastModified` (setters) and mutable progress state (`progressPercent`/`soFar`/`size`/`statusMsg`/`mediaEnqueued`/`initiatedByUser`). Three constructors (public 9-arg, private `Parcel`, public 11-arg), a `CREATOR`, hand-written field-selective `equals`/`hashCode`, and two private helpers `nonNullString`/`nullIfEmpty` implementing the asymmetric null handling.
- **`FeedMedia`** (`model/src/main/java/de/danoeh/antennapod/model/feed/FeedMedia.java`, 548 LOC): `implements Playable` (→ `Parcelable, Serializable`). Largest and most widely consumed. Holds a `@Nullable volatile FeedItem item` plus a parallel `itemID` (used to reconnect the item after a parcel round-trip, since `item` itself is not parceled). Contains `getMediaItem()` (MediaBrowser bridge), `checkEmbeddedPicture()` (uses `MediaMetadataRetrieverCompat`), trivial `id`-based `equals`/`hashCode`, and a cross-type branch delegating to `RemoteMedia.equals`.
- **`RemoteMedia`** (`model/src/main/java/de/danoeh/antennapod/model/playback/RemoteMedia.java`, 299 LOC): `implements Playable`. Mostly-immutable (12 `final` fields) representation for casting/unsubscribed previews. Two constructors (12-arg + `FeedItem`-derived), a `CREATOR`, and hand-written `equals`/`hashCode` using `commons-lang3` `StringUtils.equals`/`HashCodeBuilder` over exactly `downloadUrl`/`feedUrl`/`itemIdentifier`, with a cross-type branch matching against `FeedMedia`.
- **`Playable`** (`model/src/main/java/de/danoeh/antennapod/model/playback/Playable.java`, 128 LOC): interface `extends Parcelable, Serializable`. ~24 members (getters/setters + `onPlaybackStart`, `getPlayableType`). Only `getDescription()` and `getImageLocation()` carry `@Nullable`; the rest are unannotated despite several returning null in practice (see nullability note below).

#### Where state / data lives
- These are in-memory data carriers, not persistence. Real persistence is in `:storage:database` (which maps them to/from SQLite) — 13 files reference `FeedMedia`, 3 reference `Playable`, 1 references `RemoteMedia` there.
- The load-bearing runtime path is **IPC marshalling**: `PlaybackServiceStarter` casts a `Playable` to `Parcelable` and puts it as an Intent extra (`playback/service/.../PlaybackServiceStarter.java:39`), read back at `PlaybackService.java:542` via `getParcelableExtra`. `DownloadRequest`s are marshalled as a `putParcelableArrayList` inside a `Bundle` into the download service (the pattern the `stackoverflow.com/a/22926342` comment in `DownloadRequest.writeToParcel` refers to — writing empty strings rather than skipping, so array-list unmarshalling doesn't fail).
- `FeedMedia.getMediaItem()` bridges into the media-session/`MediaBrowserCompat` surface consumed by `:playback:service` and Android Auto.

#### Platform-specific notes
- **Parcel/Bundle → Robolectric (resolved).** `android.os.Parcel`/`Parcelable`/`Bundle` are unimplemented stubs under bare-JVM `:model` unit tests; real round-trips need Robolectric (José's resolved decision). `:model/build.gradle` currently has only `junit`, `androidx.test.core`, `mockito.core` as test deps — Robolectric must be added.
- **`android.net.Uri.parse` in `FeedMedia.getMediaItem()`** (`FeedMedia.java:118,120`): returns null under the bare-JVM stub, so any characterization of `getMediaItem()` also needs Robolectric (or a `Uri` mock). This is separate from the Parcel path.
- **MediaBrowser coupling is `FeedMedia`-only.** `MediaBrowserCompat`/`MediaDescriptionCompat` appear **only** in `FeedMedia` (`FeedMedia.java:8-9,108-123`). `RemoteMedia` has **no** MediaBrowser/MediaDescription coupling at all — correcting the task-prompt assumption that both are coupled. Under the Robolectric that this milestone adds, `getMediaItem()` runs without extra mocking; it need not stay mocked, but it is also not a Parcel concern and could be left conversion-only (see Unknowns).
- **`MediaMetadataRetrieverCompat`** (used by `FeedMedia.checkEmbeddedPicture`) is already Kotlin (`model/src/main/java/de/danoeh/antennapod/model/MediaMetadataRetrieverCompat.kt`) — not part of this scope, but `checkEmbeddedPicture`/`hasEmbeddedPicture` touch it and are hard to unit-test (real media retriever).
- **`android.text.TextUtils.isEmpty`** in `DownloadRequest.nullIfEmpty` (`DownloadRequest.java:90`): same bare-JVM stub hazard the M5 tests hit with `mockStatic(TextUtils.class)` — but under this milestone's Robolectric it resolves for free.
- **Serializable / `serialVersionUID`:** `Playable extends Serializable`, so `FeedMedia` and `RemoteMedia` are transitively `Serializable`. **None of the four files declares a `serialVersionUID`** (verified: NONE). `DownloadRequest` is `Parcelable`-only, not `Serializable`. This is the same J2K-changes-the-computed-UID risk the planner pinned with `serialVersionUID = 1L` in Milestones 4/5.
- **Nullability platform-type hazard (`kotlin` track):** `Playable`'s getters are mostly unannotated but return null in practice — e.g. `FeedMedia.getEpisodeTitle`/`getChapters`/`getWebsiteLink`/`getFeedTitle`/`getPubDate` all `return null` when `item == null` (`FeedMedia.java:306-374`); `RemoteMedia.getLocalFileUrl` always returns null. Because `Playable` and both implementers convert together this milestone, the Kotlin nullability chosen for each interface getter must match real implementer behavior, or the overrides won't compile.

#### Tests in this area
- **Only `FeedMedia` has any existing coverage, and it is narrow:** `FeedMediaTest.java` (3 tests) exercises only `setDownloaded`/item-state transitions using a mocked `FeedItem` — no Parcel round-trip, no `getMediaItem`, no `equals`/`hashCode`. Helper `FeedMediaMother.anyFeedMedia()` builds a `FeedMedia(null, url, size, mime)`.
- **No Parcel round-trip test exists inside `:model`** for any of the four. `Parcel.obtain`/`createFromParcel` appear only in the three production files plus one external test.
- **Relevant external test (de-facto partial characterization):** `net/download/service-interface/src/test/java/.../DownloadRequestBuilderTest.java` is a `@RunWith(RobolectricTestRunner.class)` test that round-trips `DownloadRequest`s through `Bundle.putParcelableArrayList` with WithAuth/NoAuth/MixAuth cases — it indirectly pins the `username`/`password` null→`""`→null asymmetry (asserts `getPassword()` equality across the round trip). But it drives via `DownloadRequestBuilder`, lives in another module, and only spot-checks a few fields (its own comment notes `equals()` "doesn't quite work" for the `arguments` Bundle). It is not a substitute for a `:model`-local, direct-`CREATOR` round-trip test.
- **Characterization gaps (must be written BEFORE conversion):** direct `Parcel` round-trip for all four via their `CREATOR`; `RemoteMedia` round-trip (zero coverage anywhere); `FeedMedia` round-trip (zero); the field-subset + asymmetry behaviors enumerated below; the cross-type `FeedMedia`↔`RemoteMedia` `equals`; and (optionally) `getMediaItem`.

### Constraints & Risks
- **Parcel writes a field SUBSET — round-trips are lossy by design; preserve verbatim:**
  - `DownloadRequest` (`writeToParcel` L66-83 vs `CREATOR`/private `Parcel` ctor L38-42): parcels `destination`/`source`/`title`/`feedfileId`/`feedfileType`/`lastModified`/`username`/`password`/`mediaEnqueued`/`arguments`/`initiatedByUser`. It does **NOT** parcel `progressPercent`/`soFar`/`size`/`statusMsg` — yet `equals` **does** compare them (L115-118). So a parceled-then-restored request with non-zero progress will `!equals` the original. Characterization must compare only parceled fields (or default progress to 0).
  - `username`/`password` asymmetry: written via `nonNullString` (null → `""`), read via `nullIfEmpty` (`""` → null). A `null` round-trips to `null`; an originally-`""` value round-trips to `null` (a real, if benign, divergence). `lastModified` is written/read plain (symmetric, null-preserving).
  - `equals`/`hashCode` asymmetry inside `DownloadRequest`: `equals` ignores `arguments`; `hashCode` includes `arguments.hashCode()` (L141) — and would NPE if `arguments` were null. Preserve exactly.
  - `FeedMedia` (`writeToParcel` L289-303 vs `CREATOR` L428-442): `item` is **not** parceled — only `id` and `item.getId()`→`itemID` survive (item restored as `null`, `itemID` reattached). `lastPlayedTimeHistory` is written as `getTime()` (0 if null) and read back as `new Date(0L)` — a **null → epoch-Date** asymmetry (never null after restore). `hasEmbeddedPicture`/`startPosition`/`playedDurationWhenStarted` are not parceled. `FeedMedia.equals` is `id`-only so round-trip equality still holds on `id`.
  - `RemoteMedia` (`writeToParcel` L232-248 vs `CREATOR` L250-266): `pubDate` written as time (0 if null), read as `new Date(...)` — same **null → epoch-Date** asymmetry. `chapters` is not parceled (restored null). `equals`/`hashCode` over `downloadUrl`/`feedUrl`/`itemIdentifier` only.
- **Hand-written `equals`/`hashCode` must stay — no `data class`.** The `FeedMedia`↔`RemoteMedia` cross-type `equals` is mutually referential (`FeedMedia.equals` L509-511 delegates to `RemoteMedia.equals`; `RemoteMedia.equals` L276-287 handles `FeedMedia`), so the two files are compile-coupled and their `equals` semantics must be converted in lockstep.
- **`Playable` interface nullability decision is load-bearing.** Choosing non-null for getters that actually return null breaks the implementers' overrides; choosing nullable propagates `?` into consumers. Because Java consumers dominate (~102 Java files reference `FeedMedia`, ~40 reference `Playable`) and Java is unaffected by Kotlin nullability, the compile risk is concentrated in the handful of Kotlin call sites.
- **Property-vs-getter ripple into already-Kotlin in-module files (out of the 4-file scope).** Converting `Playable`/`FeedMedia` to Kotlin with *properties* breaks Kotlin callers that use Java `getX()` syntax. Three such call sites exist, all in `:model` files converted in earlier milestones: `EmbeddedChapterImage.kt:50` (`media.getChapters()` on a `Playable`), `FeedFilter.kt:48` (`item.media!!.getDuration()`), `FeedItem.kt:50` (`value.getItem()`). Java consumers (the overwhelming majority) are unaffected either way. The planner must decide: expand File Scope to update these three to property syntax, or keep the Kotlin members as functions to avoid the ripple.
- **Robolectric-in-`:model` reopens the KMP-portability tension** the Robolectric-free precedent was meant to avoid (future-work deferred initiative #1). In scope as an explicit, disclosed exception; flag it stays confined to this milestone's test deps.
- Wide blast radius but **public API must not silently break for Java callers** — every `getX()`/`setX()` must remain callable with identical signatures from Java. Consumer counts: `FeedMedia` ~102 Java files across `:app`/`:storage:database`/`:playback:service`/`:net:download:*`/`:parser:feed`/etc.; `Playable` ~40 (`:app`, `:playback:service`, `:storage:database`, `:playback:base`/`:cast`, `:ui:*`); `DownloadRequest` ~13 (mostly `:net:download:service`); `RemoteMedia` ~6 (`:playback:cast`, `:storage:database`).

### Unknowns
1. **Sub-batching.** `Playable` + `FeedMedia` + `RemoteMedia` are coupled three ways (shared interface nullability contract, mutual cross-type `equals`, `FeedMedia` referencing `RemoteMedia` type) and argue for converting together or in tight sequence. `DownloadRequest` is fully independent (no `Playable`, no `Serializable`, no cross-references) and can go solo — likely first, as the simplest and the one with an existing external round-trip test to mirror. Planner to decide the exact step grouping/ordering.
2. **`Playable` getter nullability, member by member** — which getters become `String?`/`List<Chapter>?`/`Date?` to match implementer behavior, and whether to keep members as **functions** (to avoid the Kotlin getter-syntax ripple) or convert to idiomatic **properties** (and expand File Scope to fix the 3 in-module Kotlin call sites).
3. **`serialVersionUID`.** Pin `serialVersionUID = 1L` on `FeedMedia`/`RemoteMedia` (Serializable via `Playable`; matches M4/M5 precedent) and/or on the `Playable` interface? `DownloadRequest` is not Serializable, so it's exempt.
4. **File Scope boundary** — whether `EmbeddedChapterImage.kt`, `FeedFilter.kt`, `FeedItem.kt` (already Kotlin) are added for one-line getter→property updates, contingent on decision #2.
5. **`getMediaItem()` / `checkEmbeddedPicture()` characterization.** Both are platform-coupled (`Uri`/`MediaBrowserCompat`, `MediaMetadataRetrieverCompat`) and have zero coverage. Decide whether they get characterization tests under the new Robolectric dep or are treated as conversion-only (mechanical J2K, no behavioral test).
6. **`DownloadRequest` test approach** — write a fresh `:model`-local direct-`CREATOR` round-trip test, and/or mirror the existing `DownloadRequestBuilderTest` `Bundle.putParcelableArrayList` pattern to pin the null/empty-auth asymmetry from inside `:model`.

## Plan

> 2. **MAJOR — `FeedMediaTest`'s parcel round-trip expected values corrected against live `FeedMedia.java`.** `startPosition` restores to its field-initializer default **`-1`** (`FeedMedia.java:46`), not `0`; `playedDurationWhenStarted` restores to the **restored `playedDuration`** value, not `0` and not the pre-parcel original, because the 12-arg constructor the `CREATOR` calls unconditionally sets `playedDurationWhenStarted = playedDuration` (`FeedMedia.java:79`, `CREATOR` at `:432`). `hasEmbeddedPicture` restores to `null` (the 12-arg ctor never sets it). Step 3 and the Acceptance Criteria now specify these exact values, and the test is required to set the original `playedDurationWhenStarted != playedDuration` so it actually discriminates the asymmetry.
> 3. **MAJOR — the new `chapters!!` no longer claims "exact" NPE preservation; the divergence is disclosed honestly.** Red-team empirically confirmed (and I concur on inspection) that `media.chapters!![chapter]` throws the same exception **class** (`NullPointerException`) but regresses the **message** from a detailed JEP-358 diagnostic to none. Unlike Milestone 5's analogous `imageUrl` fix — which could widen a Java platform-type parameter (`Pattern.matcher(CharSequence)`) so the null flowed through unchanged and preserved the exact message — **that trick does not apply here**: the crash originates at a Kotlin list-index operator (`[]`) on a Kotlin-nullable `List<Chapter>?`, which has no downstream Java platform boundary to launder the null through, so the exact JEP-358 message is genuinely unpreservable. Per the [[unverifiable-equivalence-policy]] precedent, Step 4 now (a) softens the wording from "exactly" to an honest same-class/different-message disclosure, (b) requires a call-site comment, (c) adds an Acceptance-Criteria caveat, and (d) adds a regression-guard test (`getModelForNullChaptersThrowsNpe`) pinning the new shape so a future silent change (e.g. swapping `!!` for `?.` and dropping the crash) is caught — mirroring the regression-guard M5 added on this identical file (`getModelForNullImageUrlThrowsFromInsideMatcherNotAtExtraction`). This adds `EmbeddedChapterImageTest.java` to File Scope. The same message-divergence disclosure applies to the second `!!` at `FeedItemFilter.kt:106` (finding 1).

### Objective
Convert the last 4 Java files in `:model` — `DownloadRequest`, the `Playable` interface, `RemoteMedia`, and `FeedMedia` — to Kotlin on the `kotlin` track, preserving each type's hand-written `equals`/`hashCode` and its **lossy-by-design, asymmetric** `Parcel`/`Bundle` marshalling verbatim. After this milestone `:model` is 100% Kotlin.

### Resolved Decisions

**(Unknown 1) Sub-batching / step order.** `DownloadRequest` converts **solo and first** (no `Playable`, no `Serializable`, no cross-references; it has an existing external round-trip test to mirror, and doing it first lands the Robolectric test-infra with the lowest-risk file). The coupled cluster then converts in dependency order — **`Playable` interface → `RemoteMedia` → `FeedMedia`** — after a single shared characterization step pins the whole cluster's behavior (the `FeedMedia`↔`RemoteMedia` cross-type `equals` spans both, so it must be pinned once, together). Each conversion is its own diff and each leaves the build green: when `Playable` is Kotlin but its two implementers are still Java, the Java overrides satisfy the Kotlin interface (Java is nullability-agnostic); when `RemoteMedia` is Kotlin but `FeedMedia` is still Java, the mutual `equals` calls resolve cross-language at runtime. This mirrors the per-file characterize-then-convert cadence of Milestones 4/5.

**(Unknown 2) `Playable` nullability + properties-vs-functions.** Convert interface getters/setters to **idiomatic Kotlin properties**, matching the module's own M4/M5 precedent (every earlier `:model` conversion turned `getX()` into a property) and the `kotlin`-track "idiomatic target" bar. This breaks in-module Kotlin callers that use `getX()` syntax, so those files are added to File Scope (see Unknown 4).
