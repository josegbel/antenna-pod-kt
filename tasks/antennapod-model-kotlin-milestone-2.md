## Research
_Last updated by: legacy-android-researcher | 2026-07-20_

### Summary
`:model` is now 8 Kotlin / 19 Java (down from 27/0 at Milestone 1's start): `model/build.gradle:1-4` already applies both `kotlin.android` and `ktlint` (Milestone 1's toolchain setup), so no new build-config prerequisite exists for Milestone 2 — any batch of files can be converted immediately. This research re-verifies Milestone 1's carry-forward risk triage (checkpoint "Decisions for next session") against the actual current source of all 19 remaining files, rather than trusting the old categorization, and finds it substantially still holds with corrected downstream-exposure numbers and a few new details. The 19 files split into three tiers of clearly rising risk: (A) 4 files with genuine Android-framework coupling (`SortOrder`, `VolumeAdaptionSetting`, `MediaType`, `MediaMetadataRetrieverCompat`); (B) 8 files with hand-written `equals`/`hashCode` that must be preserved verbatim, including the `Feed`/`FeedItem`/`FeedMedia`/`Playable`/`RemoteMedia` graph plus `Chapter`, `EmbeddedChapterImage`, `FeedFunding`, `DownloadRequest`; (C) 7 remaining files — `DownloadResult`, `FeedFilter`, `FeedItemFilter`, `SubscriptionsFilter`, `Transcript` — with neither framework coupling nor equality overrides (this research reclassifies `FeedPreferences` out of the old "remaining POJOs" bucket and into a framework-touching category, see below, since it calls `TextUtils.join` — a detail Milestone 1's checkpoint list didn't capture).

Following Milestone 1's philosophy of a small, defensible slice rather than converting everything at once, this research's read is that Tier C (specifically `FeedFilter`, `DownloadResult`, `FeedItemFilter`, `Transcript`) is the next-lowest-risk batch: zero Android-framework imports, zero hand-written `equals`/`hashCode` (so no equality-contract risk), and — critically — none of them are referenced by the `FeedMother`/`FeedItemMother`/`FeedMediaMother` test helpers (confirmed by reading all three), so they convert without touching the already-tested `Feed`/`FeedItem`/`FeedMedia` cluster, exactly as Milestone 1's Resolved Decision 1 criteria required. `SubscriptionsFilter` shares the "no equals/hashCode" property but does carry `android.text.TextUtils` framework coupling and has zero test coverage anywhere in the repo, so it reads as a better fit alongside the Tier A framework batch than in this Tier C candidate slice — flagged as a judgment call for the planner rather than decided here. `FeedPreferences` (324 LOC, four nested enums with an int-code/`fromCode` pattern identical to Milestone 1's `FeedOrder`/`FeedCounter`) is tempting as "simple," but its `getTagsAsString()` calls `TextUtils.join` (`FeedPreferences.java:310`) and it has 33 downstream consumers with only 2 downstream test references — a large, mostly-untested surface that this research recommends deferring rather than folding into Milestone 2's batch.

### Findings

#### Existing surface
19 production Java files remain across three packages (`model/src/main/java/de/danoeh/antennapod/model/{feed,download,playback}` plus the module root), confirmed by `find`:
- **`feed/`** (12 files): `Chapter` (110 LOC), `EmbeddedChapterImage` (73), `Feed` (538), `FeedFilter` (150), `FeedFunding` (92), `FeedItem` (509), `FeedItemFilter` (153), `FeedMedia` (548), `FeedPreferences` (324), `SortOrder` (77), `SubscriptionsFilter` (62), `Transcript` (50), `VolumeAdaptionSetting` (65).
- **`download/`** (2 files): `DownloadRequest` (227), `DownloadResult` (123).
- **`playback/`** (3 files): `MediaType` (30), `Playable` (128, interface), `RemoteMedia` (299).
- **root** (1 file): `MediaMetadataRetrieverCompat` (18).
- Total ≈ 3,576 LOC across 19 files (`wc -l`).
- The 8 already-converted Kotlin files remain untouched by this survey (`model/src/main/java/de/danoeh/antennapod/model/{download,feed,playback}/*.kt`): `DownloadError.kt`, `DownloadStatus.kt`, `ProxyConfig.kt`, `FeedCounter.kt`, `FeedOrder.kt`, `TranscriptSegment.kt`, `TranscriptType.kt`, `TimerValue.kt`.

**Re-verified risk tiers (supersedes the checkpoint's carry-forward list — corrected details in bold):**

**Tier A — Android-framework coupling (4 files):**
- `SortOrder.java:3` imports `android.text.TextUtils`, used in `fromCodeString` (`SortOrder.java:61`, `TextUtils.isEmpty(codeStr)`). Public final fields `code`/`scope` (`SortOrder.java:37,39-40`) and a nested `Scope` enum (`SortOrder.java:33-35`). No hand-written `equals`/`hashCode`. No dedicated `SortOrderTest` exists anywhere in the repo — its `scope` field is only touched indirectly via `FeedTest.testSetSortOrder` per Milestone 1's research; `fromCodeString`/`parseWithDefault` have zero test coverage.
- `VolumeAdaptionSetting.java:3` imports `android.media.audiofx.AudioEffect`, used in `isBoostSupported()` (`VolumeAdaptionSetting.java:44-59`, calls `AudioEffect.queryEffects()` at line 48). Has a mutable non-final field `adaptionFactor` (`VolumeAdaptionSetting.java:17`) and mutable static `boostSupported` with a `@VisibleForTesting` setter (`VolumeAdaptionSetting.java:41-42,61-64`). `VolumeAdaptionSettingTest` (14 tests) exists and is thorough for the mapping/factor logic, but **stubs the framework path** via `setBoostSupported(false)` in `@Before` (`VolumeAdaptionSettingTest.java:18-20`) — the real `AudioEffect.queryEffects()` branch (lines 48-58) is never exercised by any test today, same gap Milestone 1 flagged and still true.
- `MediaType.java:3` imports `android.text.TextUtils`, used in `fromMimeType` (`MediaType.java:19`, `TextUtils.isEmpty(mimeType)`). Small (30 LOC), no equals/hashCode. No dedicated `MediaTypeTest`; only exercised indirectly wherever `RemoteMedia`/`FeedMedia` call `getMediaType()`.
- `MediaMetadataRetrieverCompat.java:10` — **not just framework-coupled but literally `extends android.media.MediaMetadataRetriever`** (a concrete Android SDK class with native methods), overriding only `close()` (`MediaMetadataRetrieverCompat.java:11-17`). This is qualitatively riskier than the other three: J2K converting a class that subclasses a framework class needs verification that Kotlin's subclassing semantics (constructor delegation, `open`/`final` defaults) don't change behavior — no existing test touches this class at all (0 downstream test references), and it cannot be meaningfully unit-tested without Robolectric or instrumentation since the superclass's real behavior depends on native/OS media decoding.

**Tier B — hand-written `equals`/`hashCode`, must convert to plain `class` not `data class` (8 files):**
- `Chapter.java:93-109` — `equals`/`hashCode` on `id` only. No framework imports. No dedicated `ChapterTest` in the repo despite 21 downstream consumers (5 of which are tests: `ui/chapters/.../ChapterUtilsTest.java`, `net/download/service/.../DbTestUtils.java`, three `parser/media/.../*ChapterReaderTest.java`).
- `EmbeddedChapterImage.java:44-59` — `equals` via `TextUtils.equals(imageUrl, ...)` (`EmbeddedChapterImage.java:53`, so this one is **both** Tier A and Tier B: framework coupling *and* a hand-written equality contract) and `hashCode` via `imageUrl.hashCode()` (note: NPEs if `imageUrl` is null — untested edge case). Also depends on the unconverted `Playable` interface (`EmbeddedChapterImage.java:4`).
- `FeedFunding.java:28-47` — hand-rolled `equals` with a null-both-fields special case (`FeedFunding.java:35-37`) plus a separate all-non-null case (`:38-40`) that is not a full equivalence relation (e.g. one field null + other non-null with matching remaining field is unhandled, falls through to `return false`) — pin this exact behavior, don't "fix" it. `hashCode` concatenates `url + SEPARATOR + content` as a string then hashes (`FeedFunding.java:46`) — NPEs if either is null, another pre-existing latent bug to preserve as-is. Public mutable fields `url`/`content` (`FeedFunding.java:12-13`).
- `Feed.java:521-537` — `equals`/`hashCode` on `id` only. 123 downstream files reference `Feed` (by far the largest surface of any remaining file, 34 of which are tests) — this and `FeedItem`/`FeedMedia` are the highest-blast-radius conversions in the whole module.
- `FeedItem.java:492-508` — `equals`/`hashCode` on `id` only. `transient Feed feed` (`FeedItem.java:42`) and `transient List<Chapter> chapters` (`FeedItem.java:69`) need `@Transient` to preserve `Serializable` behavior. 128 downstream files (highest in the module), 25 of which are tests.
- `FeedMedia.java:496-519` — `equals` has an **asymmetric cross-type delegation to `RemoteMedia`**: `if (o instanceof RemoteMedia) { return o.equals(this); }` (`FeedMedia.java:509-511`), then falls through to `id`-only comparison for same-class instances. `@Nullable volatile FeedItem item` (`FeedMedia.java:44`) needs `@Volatile`. Implements `Playable` → framework coupling via `android.net.Uri` (`FeedMedia.java:3`), `android.support.v4.media.MediaBrowserCompat`/`MediaDescriptionCompat` (`FeedMedia.java:8-9`, used in `getMediaItem()` lines 108-124), and constructs a `MediaMetadataRetrieverCompat` in `checkEmbeddedPicture()` (`FeedMedia.java:482`). 95 downstream files, 21 tests, but only `FeedMediaTest` (3 tests, mocked `FeedItem`, no `Parcel` round-trip) exists in `model/src/test`.
- `RemoteMedia.java:268-289` — `equals` mirrors `FeedMedia`'s cross-type check from the other side (`RemoteMedia.java:276-287`, compares `downloadUrl`/`itemIdentifier`/feed's `downloadUrl` against a `FeedMedia`+`FeedItem`+`Feed` chain). `hashCode` uses commons-lang3 `HashCodeBuilder` (`RemoteMedia.java:291-298`). Implements `Playable` → `Parcelable`. Lowest downstream exposure of this cluster (4 files, 1 test) but its equality is **mutually coupled to `FeedMedia`** — converting one without the other requires the cross-class `equals` to keep compiling and behaving identically both ways.
- `DownloadRequest.java:104-148` — hand-written `equals` (`:104-129`) deliberately **omits the `arguments` `Bundle` field** from comparison, but `hashCode` (`:131-148`) **includes `arguments.hashCode()`** (`DownloadRequest.java:141`). This is a pre-existing equals/hashCode contract violation in the current Java (two `DownloadRequest`s with different `arguments` but otherwise-identical fields are `equals()` but can have different `hashCode()`) — must be preserved exactly as a characterization-test-pinned quirk, not "fixed," per the module's no-behavior-change rule. Also `Parcelable` with the asymmetric null-handling Milestone 1 flagged (`nullIfEmpty`/`nonNullString`, `DownloadRequest.java:85-91`).

**Tier C — remaining POJOs/filters with neither framework coupling nor `equals`/`hashCode` (7 files, the likely Milestone 2 candidates):**
- `DownloadResult.java` — `Serializable` (`:11`), no `equals`/`hashCode`, no Android imports (only `androidx.annotation.NonNull`, a compile-time annotation). Defensive `Date` cloning on `completionDate` (`DownloadResult.java:58,98`), mirroring the pattern Milestone 1 already handled in `DownloadStatus`. 20 downstream files (7 `net/download/service` main-source consumers, `storage/database` `DBReader`/`DBWriter`/`PodDBAdapter`/`FeedDatabaseWriter`, `app`'s download-log UI), 3 of which are tests (`storage/database/.../FeedDatabaseWriterTest.java`, `app/src/androidTest/.../DownloadLogTest.java` and `.../HttpDownloaderTest.java`) — **no dedicated `DownloadResultTest` exists in `model/src/test`**, a real characterization gap to fill first.
- `FeedFilter.java` — `Serializable` (`:10`), no `equals`/`hashCode`, pure `java.util.regex` parsing, no Android imports. **Already has a thorough dedicated test, `FeedFilterTest`** (7 tests covering null/include/exclude/combo/minimal-duration filters, read in full). Lowest downstream exposure of any remaining file: only 3 non-model files reference it (`app/.../EpisodeFilterDialog.java`, `app/.../FeedSettingsPreferenceFragment.java`, `storage/database/.../FeedPreferencesCursor.java`), none of them tests.
- `FeedItemFilter.java` — `Serializable` (`:8`), no `equals`/`hashCode`, pure string-array parsing, no Android imports. Its `matches()` method reads `Feed.STATE_SUBSCRIBED`/`FeedItem.TAG_QUEUE` constants (`FeedItemFilter.java:104-152`) but only as int/String constants — no coupling requiring `Feed`/`FeedItem` to already be Kotlin. **Highest downstream exposure in Tier C by far: 51 non-model files** (nearly every UI screen/fragment/swipe-action in `app`, `net:download:service`'s auto-download algorithms, `net:sync:service`, `playback:service`), 5 of which are tests. No dedicated `FeedItemFilterTest` exists in `model/src/test` today — another characterization gap, and this file's downstream breadth means the Step-7-style cross-module verification from Milestone 1 is even more important here than it was for `FeedOrder`/`FeedCounter`.
- `Transcript.java` — no `equals`/`hashCode`, no Android imports, pure Java (binary-search `findSegmentIndexBefore`, `Transcript.java:17-29`). **The only Tier C file that directly consumes an already-converted Milestone 1 Kotlin class**: its `segments` field is `ArrayList<TranscriptSegment>` (`Transcript.java:8`) and `addSegment`/`findSegmentIndexBefore` call `TranscriptSegment.getStartTime()` (`Transcript.java:11,22`) — a Kotlin getter Java already calls today without incident, since `TranscriptSegment` was itself converted with `@JvmField`/plain-getter preservation in Milestone 1. 10 downstream files (mostly `parser/transcript`'s three format parsers + `ui/transcript` + `app`'s transcript UI), 3 of which are tests (the three `parser/transcript/.../*TranscriptParserTest.java` files). No dedicated `TranscriptTest` in `model/src/test`.
- `SubscriptionsFilter.java:3` — imports `android.text.TextUtils`, used in the constructor (`SubscriptionsFilter.java:31`, `TextUtils.split(properties, divider)`) and `serialize()` (`SubscriptionsFilter.java:60`, `TextUtils.join`). No `equals`/`hashCode`. This is the file Milestone 1's research specifically flagged for a J2K idiom trap: `TextUtils.split("", div)` returns an empty array where Kotlin's `String.split` on an empty string returns `[""]` — a semantic difference that would silently break `isEnabled()` (`SubscriptionsFilter.java:52`, checks `properties.length > 0`) if naively "modernized" during conversion. **Zero test coverage anywhere in the repo** (0 downstream test files, no `model/src/test` file) despite 6 downstream consumers. Its framework coupling plus total absence of a safety net argue for grouping it with Tier A rather than this batch — flagged as a judgment call, not decided here.
- `FeedPreferences.java` — **reclassified out of the old checkpoint's undifferentiated "remaining POJOs" bucket.** No `equals`/`hashCode`, `Serializable` (`:13`), but imports `android.text.TextUtils` (`FeedPreferences.java:4`) and calls `TextUtils.join` in `getTagsAsString()` (`FeedPreferences.java:310`) — the checkpoint note didn't capture this framework coupling. Contains four nested enums with an int-`code`/`fromCode` pattern (`AutoDeleteAction`, `NewEpisodesAction`, `SkipSilence`, `AutoDownloadSetting`, `FeedPreferences.java:20-108`) structurally identical to Milestone 1's `FeedOrder`/`FeedCounter` — genuinely low-risk in isolation, but the outer class itself has 33 downstream consumers and only 2 downstream test references (`app/.../PlaybackServiceMediaPlayerTest.java` and `playback/service/.../PlaybackVolumeUpdaterTest.java`), a large surface with a thin safety net. Recommend deferring the outer class to a dedicated future slice, though its four nested enums could plausibly be extracted/converted independently if a future milestone wants a "framework-free nested enum" quick win — flagged as an option, not decided.
- `Playable.java:15` — interface `extends Parcelable, Serializable`. Not itself instantiable so has no `equals`/`hashCode` to preserve, but its partial `@Nullable` annotation coverage (`getDescription`/`getImageLocation` are `@Nullable`, `Playable.java:69-70,125-126`; most other getters — `getEpisodeTitle`, `getStreamUrl`, `getLocalFileUrl`, `getIdentifier` — are unannotated) means converting it to Kotlin requires simultaneously deciding nullability for both of its implementers (`FeedMedia`, `RemoteMedia`, both Tier B) — it cannot be converted alone without also touching both implementations' method signatures. 40 downstream files, 6 tests. This interface is a hard blocker on `FeedMedia`/`RemoteMedia` conversion order: whichever milestone converts one of the two `Playable` implementers likely has to convert `Playable` itself in the same pass.

#### Where state / data lives
`:model` remains a pure data-holding leaf module — no repositories/persistence live here (`model/build.gradle` still declares no `project(':...')` dependency, only external libs). The cross-object graph inside the module is unchanged from Milestone 1's findings: `Feed` ↔ `FeedItem` ↔ `FeedMedia` (bidirectional, `FeedItem.feed`/`chapters` `transient`, `FeedMedia.item` `@Nullable volatile`), plus the newly-relevant fact that `RemoteMedia`'s `equals`/constructor (`RemoteMedia.java:62-79`) and `EmbeddedChapterImage`'s constructor (`EmbeddedChapterImage.java:16-26`) both reach into this same graph via the `Playable` interface, so Tier C's `Transcript` is genuinely the *only* remaining file with zero coupling to the Tier B graph. `DownloadRequest`/`FeedMedia`/`RemoteMedia` still cross process/IPC boundaries via `Parcel` (unchanged from Milestone 1), and this remains completely untested — no round-trip test exists for any of the three.

### Constraints & Risks
- **Public API preservation is even more load-bearing here than in Milestone 1** for the files with the largest downstream surface: `FeedItemFilter` (51 downstream files, none of them `:model`), `SortOrder` (34), `FeedPreferences` (33), `Playable` (40), `MediaType` (19), `DownloadResult` (20) all dwarf Milestone 1's largest consumer counts. Whichever files Milestone 2 selects, the Milestone 1 pattern of cross-module build/test verification (not just `:model` compiling green) is non-negotiable — see Milestone 1 Plan Step 7 / Acceptance Criteria for the template to reuse.
- **`equals`/`hashCode` traps are worse in Tier B than anything Milestone 1 saw:** `DownloadRequest`'s equals/hashCode already violate the Java equals/hashCode contract today (`arguments` excluded from `equals`, included in `hashCode`) — this is a "preserve the bug" case, not a "the conversion introduces a bug" case, and needs an explicit characterization test asserting the contract violation itself so nobody "fixes" it during conversion. `FeedMedia`/`RemoteMedia` have a **mutually-coupled asymmetric cross-type `equals`** — converting one without the other risks either a compile break or a silently-different equality relation depending on which side's Kotlin conversion changes null-handling.
- **`FeedFunding`'s `equals` is not a total function** (a mixed-null case falls through unhandled to `false` without being an explicit branch) and its `hashCode` NPEs on null `url`/`content` — same "preserve exactly, characterize first" requirement.
- **The `SubscriptionsFilter` idiom trap Milestone 1 flagged is still live and still untested**: `TextUtils.split("", div)` → `[]`, but Kotlin's `"".split(div)` → `[""]`. If this file is converted (in Milestone 2 or a later one), the characterization test must pin the *actual* current behavior of `isEnabled()` for an empty properties string before any Kotlin is written.
- **`Playable`'s partial nullability annotation coverage is unchanged from Milestone 1's finding** — converting it forces a nullability decision for `FeedMedia`/`RemoteMedia` simultaneously; it cannot be deferred once either implementer is touched.
- **No behavior changes** — same rule as Milestone 1: any semantic difference a characterization test surfaces is a bug to fix in the test/plan, not a behavior to silently adopt.

### Unknowns
Open questions for the planner to resolve:
1. **Milestone 2 batch selection.** This research's read is Tier C's `FeedFilter`/`DownloadResult`/`FeedItemFilter`/`Transcript` (4 files, zero framework coupling, zero equals/hashCode, none referenced by the tested `Feed`/`FeedItem`/`FeedMedia` cluster's Mother helpers) as the next defensible slice — smaller than Milestone 1's 8 files, which is reasonable given the remaining pool is smaller and the next-cheapest tier up (Tier B's equals/hashCode cluster) is meaningfully riskier. Whether to also include `SubscriptionsFilter` (no equals/hashCode, but framework-coupled and completely untested) or `FeedPreferences`'s four nested enums (structurally like Milestone 1's picks, but bolted onto a 324-LOC class with 33 consumers) is not resolved here — flagged as a judgment call, not decided.
2. **`FeedItemFilter`'s unusually wide downstream surface (51 files).** Even though it has none of Tier B's equality/framework risk, its blast radius is larger than any single file Milestone 1 touched. Does the plan need FeedItemFilter-specific downstream verification (e.g. `:app`, `:playback:service`, `:net:sync:service` compile/test targets) beyond what a generic Step-7-style check would cover, given how many UI screens and swipe actions consume it directly?
3. **`SortOrder`/`MediaType`/`VolumeAdaptionSetting`'s Robolectric question, deferred but now concrete.** Milestone 1 correctly deferred this; this research confirms Robolectric (`gradle/libs.versions.toml:77`) has precedent in 11 other modules, so wiring it into `:model` is cheap when that milestone arrives — but `VolumeAdaptionSetting.isBoostSupported()`'s real `AudioEffect.queryEffects()` branch and `MediaMetadataRetrieverCompat extends MediaMetadataRetriever` may need actual instrumented (on-device/emulator) tests rather than Robolectric shadows, since Robolectric's `AudioEffect`/`MediaMetadataRetriever` shadows may not model native decoding behavior faithfully. Needs a spike before that milestone is planned, not resolved here.
4. **`DownloadRequest`/`FeedMedia`/`RemoteMedia` Parcelable round-trip test strategy** — still unresolved from Milestone 1, still not needed for any Tier C candidate, but now closer: whichever milestone tackles Tier B's Parcelable files needs to decide Robolectric vs. instrumented `androidTest` for the round-trip characterization tests.
5. **Conversion order within Tier B when it's eventually tackled:** `FeedMedia` and `RemoteMedia`'s mutually-coupled `equals` plus `Playable`'s shared-interface nullability decision suggest those three (`Playable`, `FeedMedia`, `RemoteMedia`) likely need to convert together in one milestone rather than split across milestones — is that an acceptable scope for a single future milestone, or should `Feed`/`FeedItem` (self-contained `equals`/`hashCode`, no cross-type coupling) go first as a separate, smaller step within Tier B?
