## Research
_Last updated by: legacy-android-researcher | 2026-08-20_

### Summary

This milestone's target is not a module of source code — it is the repo's build surface: a single Groovy version catalog (`gradle/libs.versions.toml`, 87 lines: 10 shared `[versions]`, 65 `[libraries]`, 7 `[plugins]`), a root `build.gradle` that declares every plugin `apply false`, a `common.gradle` script applied by all 34 modules, and per-module `build.gradle` files. There is no convention plugin, no `buildSrc`, and no `build-logic` composite — `common.gradle` is a plain `apply from:` script, so "add a shared convention" here means editing `common.gradle` (which hits all 34 modules at once) or editing the two module files individually. Confirmed against `develop`: there is **no Hilt, Dagger, Koin, KSP, KAPT, Paparazzi, Compose BOM, `compose.material3`, `compose.foundation`, `ui-tooling`, `kotlinx-coroutines-core` or `-android`** anywhere in `*.gradle`/`*.toml`/`*.properties`. The only Compose in the repo is `app-wearos`, which already applies `libs.plugins.kotlin.compose` and sets `buildFeatures { compose true }` — meaning the Compose *compiler* plugin is already catalogued, already versioned in lockstep with Kotlin, and already proven to work on this AGP/Gradle/Kotlin combination. That is the single biggest de-risking fact in this survey: the Compose half of this milestone is mostly "apply an already-working plugin to a second module", not a new toolchain introduction.

Three findings materially change the milestone's shape from what the pre-research context assumes. **First, `:app` is 100% Java** — zero `.kt` files, no Kotlin plugin, no ktlint plugin — while every module in the repo already runs javac annotation processing (`annotationProcessor libs.androidx.annotation` in all 34 module files, and a real processor in `ui/glide/build.gradle:19`). Hilt at `:app` therefore needs the Hilt Gradle plugin plus `annotationProcessor hilt-android-compiler` and **needs no KSP or KAPT at all**; the symbol-processing question is real but belongs to `:ui:preferences` at Milestone 18, where the first Kotlin `@HiltViewModel` will live. **Second, the `kotlin-bom` 1.9.24 skew is empirically harmless and does not block anything** — I resolved the real classpath and `kotlin-stdlib` already wins at 2.3.20; only the two content-free `-jdk7`/`-jdk8` shims sit at 1.9.24. It is a cosmetic wart, not a prerequisite, and the pre-research instruction to "resolve before adding anything else" rests on an assumption that measurement disproves. **Third, Paparazzi is the only genuinely risky addition**, and its risk lands squarely on the thing this whole pipeline sells: Milestone 15's 38-test Robolectric characterization suite lives in the exact module Paparazzi would be applied to, and Milestone 15b (if merged) adds a `@GraphicsMode(NATIVE)` Robolectric test that already renders real bitmaps through the same layoutlib native path Paparazzi uses. Everything else in this milestone is additive and inert; Paparazzi is the one item that can break a green suite.

### Findings

#### Corrections to the pre-research context

Two carried-over statements are wrong against current source. Reporting, not relitigating.

1. **The Kotlin Gradle plugin is *not* "applied repo-wide by `common.gradle`".** `common.gradle` applies no Kotlin plugin (`common.gradle:1-158` — the only Kotlin reference is the `kotlin-bom` platform at `:74`). `org.jetbrains.kotlin.android` is applied per-module, to exactly six modules: `:model`, `:event`, `:net:sync:service-interface`, `:net:sync:service`, `:net:download:service-interface`, `:ui:preferences`, plus `:app-wearos`. What `common.gradle` applies repo-wide is the **`kotlin-bom` platform on every module's `implementation` configuration**, including the 27 modules that contain no Kotlin at all. That distinction is what makes finding #2 possible.
2. **The `kotlin-bom` 1.9.24 vs. Kotlin 2.3.20 skew does not block this milestone and is not a prerequisite.** Measured, not assumed — `./gradlew --offline :ui:preferences:dependencyInsight --configuration playDebugCompileClasspath`:
   - `org.jetbrains.kotlin:kotlin-stdlib` resolves to **2.3.20**. The BOM's 1.9.24 constraint loses to the Kotlin plugin's own direct 2.3.20 dependency (Gradle takes the highest of competing constraints).
   - `kotlin-stdlib-jdk8` and `kotlin-stdlib-jdk7` resolve to **1.9.24**, pinned by the BOM, because nothing else requests them higher. Since Kotlin 1.8.0 both of those artifacts are empty shims whose entire content was merged into `kotlin-stdlib`; they exist only to satisfy stale transitive requests. So the "skew" is between the real stdlib and two artifacts that contain no code.
   - `kotlin-stdlib:2.3.20` now publishes its own version constraints on `-jdk7`/`-jdk8` (visible as `(c)` edges in the tree), which is the exact problem KT-55297 — cited in `common.gradle:72-73` as the reason the BOM exists — was filed about and fixed in Kotlin 1.9.20. **The BOM's stated justification is obsolete.**
   Three options, all defensible, none blocking: (a) leave it and document (smallest diff, consistent with `AGENTS.md`'s minimal-diff rule and this milestone's "no behavior change" framing); (b) change `kotlin-bom` to `version.ref = "kotlin"` (one line, aligns the shims, zero effect on the real stdlib); (c) delete the platform line from `common.gradle` entirely since its rationale no longer holds (correct, but a 34-module classpath change on a milestone that is supposed to add things, not remove them). If (b) or (c) is chosen it must be its own step with its own build verification, sequenced **before** the new dependencies so a failure is attributable — but it is not a gate on starting.

#### Existing surface

**`gradle/libs.versions.toml` — structure and conventions the new entries must match.**

- `[versions]` (`:1-11`) holds **only** refs shared by two or more library entries: `agp`, `kotlin`, `media3`, `wear-compose`, `compose`, `lifecycle-runtime-compose`, `glide`, `okhttp`, `espresso`, `androidx-test`. Single-use dependencies inline their version instead (`androidx-annotation = { module = "...", version = "1.9.1" }`, `:14`). Following this, a `hilt` version ref is justified (two libraries + one plugin), `coroutines` is justified (two or three libraries), `paparazzi` is borderline (one plugin, and the plugin carries the library), `compose-bom` is justified only if more than one entry references it — see the versionless-entry note below.
- `[libraries]` (`:13-78`) are grouped by origin, not alphabetised globally: androidx (`:14-51`, itself near-alphabetical), google (`:52-55`), kotlin/kotlinx (`:56-57`), Apache/third-party (`:58-74`), test libraries last (`:75-78` — `awaitility`, `junit`, `robolectric`, `mockito-core`). #### Java/Kotlin interop boundary

For a toolchain milestone the "interop boundary" is which modules a build-file edit propagates into. Three edges matter:

1. **`:app` is Java and consumes `:ui:preferences` as `implementation project(':ui:preferences')` (`app/build.gradle:84`).** Compose classes compiled inside `:ui:preferences` never appear on `:app`'s *compile* classpath (Gradle `implementation` does not expose them), only its runtime classpath. **`:app` therefore needs no Compose plugin, no `buildFeatures { compose true }`, and no Compose dependency — not now, and not at Milestone 20 either.** This directly answers the question flagged in the task brief. Two consequences do reach `:app` anyway: R8 on `assemblePlayRelease`/`assembleFreeRelease` must shrink the Compose runtime (Compose ships consumer ProGuard rules, so this is expected-fine but is exercised by CI, not by a local debug build), and `:app:lint` with `checkDependencies true` will run Compose lint checks against `:ui:preferences`'s sources.
2. **Hilt at `:app` is a one-way edge that reaches every module at runtime but no module at compile time** — until Milestone 18 puts an `@HiltViewModel` in `:ui:preferences`, at which point `:ui:preferences` needs `hilt-android` + a Kotlin-capable processor and `:app` needs to be able to see that module's `@InstallIn` metadata (it already does, via the project dependency).
3. **`common.gradle` is applied by all 34 modules.** Any edit there — including the `kotlin-bom` line — is a 34-module blast radius, not a slice-local change. This milestone should prefer per-module `build.gradle` edits over `common.gradle` edits wherever both are possible.

A resolution detail that constrains all three: AGP's *consistent resolution* is active (visible in `dependencyInsight` output as "version resolved in configuration ':ui:preferences:playDebugRuntimeClasspath' by consistent resolution"). Compile classpaths are forced to agree with the corresponding runtime classpath, so a `testImplementation`-only addition (Paparazzi's layoutlib artifacts) can surface conflicts that a `implementation`-only mental model would not predict.

#### Characterization-test gaps

This milestone changes no runtime behavior, so there is no screen behavior to characterize — but "no behavior change" is a *claim*, and right now nothing in the repo can falsify it. Three real gaps, in priority order:

1. **Resolved-dependency drift is completely unpinned.** Adding `hilt-android` pulls `dagger`, `javax.inject`, and androidx `activity`/`fragment`/`lifecycle-viewmodel-savedstate` onto `:app`; adding coroutines explicitly upgrades what is already there transitively (see below); a Compose BOM constrains a family of androidx artifacts. Gradle resolves conflicts to the *highest* version, so nothing downgrades — but versions across `:app` and `:ui:preferences` **will** move, silently, and no test or CI step would notice. The cheapest honest fix is a before/after `./gradlew :app:dependencies` + `:ui:preferences:dependencies` diff, captured in Implementation Notes and gated by an acceptance criterion. This is the one "characterization test" a toolchain milestone can actually have, and it is exactly the kind of evidence this pipeline's value proposition rests on.
2. **`kotlinx-coroutines-core`/`-android` are already on `:ui:preferences`'s compile classpath at 1.7.3** — measured, not assumed. `dependencyInsight` shows `kotlinx-coroutines-android:1.7.3` arriving via `androidx.work:work-runtime:2.10.3` (a direct dependency, `ui/preferences/build.gradle:44`) and via `androidx.lifecycle:lifecycle-viewmodel-ktx:2.6.2` ← `androidx.fragment:fragment-ktx:1.8.9` ← `androidx.preference:preference:1.2.1`. **Declaring them explicitly at any version above 1.7.3 is a real, if small, runtime change to code that already runs** (work-runtime's and lifecycle's internals), on a milestone framed as "no behavior change." That must be disclosed and covered by re-running both flavoured test tasks, not glossed as an inert catalog addition.
3. **Nothing verifies that a catalog entry actually resolves until a module consumes it.** An unused `[libraries]` entry is completely inert — Gradle never fetches it, and no build task touches it. So an acceptance criterion of the form "confirm the new dependencies resolve" is unsatisfiable for any entry this milestone catalogs but does not wire into a module. The planner must decide, per artifact, between *catalogued-but-unproven* and *wired-and-proven*, and write acceptance criteria that match. This is the most likely place for the plan to make a claim the implementation cannot back up.

#### Track-specific findings

**`di` — Hilt.**
- Required at `:app`: (a) `[versions] hilt`, `[libraries] hilt-android` (`com.google.dagger:hilt-android`) and `hilt-compiler` (`com.google.dagger:hilt-android-compiler`), `[plugins] hilt` (`com.google.dagger.hilt.android`); (b) `apply false` in root `build.gradle`; (c) `alias(libs.plugins.hilt)` in `app/build.gradle`'s `plugins {}`; (d) `implementation libs.hilt.android` + `annotationProcessor libs.hilt.compiler` in `app/build.gradle`; (e) `@HiltAndroidApp` on `PodcastApp.java:12`. **That is the entire `:app` footprint — 1 catalog block, 1 root line, 3 module lines, 1 annotation + 1 import. No manifest change.**
- **KSP/KAPT is not needed at `:app`.** `:app` has no Kotlin, and the repo already runs javac annotation processors on Java-only modules (`ui/glide/build.gradle:19` runs `glide-compiler`; all 34 modules declare `annotationProcessor libs.androidx.annotation`). Both KSP and KAPT *require* the Kotlin Gradle plugin, so applying either to `:app` would mean adding Kotlin to a module that has none — pure scope creep with no consumer.
- **Recommendation: KSP, not KAPT — but applied to `:ui:preferences`, not `:app`.** Rationale: KAPT generates Java stubs for every Kotlin file before processing and is in maintenance mode; KSP reads the Kotlin AST directly and is what Dagger/Hilt has supported and recommended since 2.48. KAPT's one genuine advantage here is that it ships *with* the Kotlin plugin (`org.jetbrains.kotlin.kapt`, `version.ref = "kotlin"`), so it can never drift; **KSP's version is `<kotlin>-<ksp>` and must match `kotlin = "2.3.20"` exactly** — there is no "close enough", and a KSP release for that exact Kotlin version must be confirmed to exist before the plan commits to it. That is the single hard version constraint in this milestone.
- **Timing question for the planner:** applying KSP + `ksp libs.hilt.compiler` to `:ui:preferences` *now*, with no Hilt annotations to process, is a near-no-op that adds build time — but it converts the KSP-version risk from a Milestone 18 surprise into a Milestone 16 verification, which is precisely what a de-risking toolchain milestone is for. The alternative (catalog the KSP plugin, apply it at Milestone 18) leaves the version constraint unproven. Recommend applying it now, and note that mixing `annotationProcessor` Hilt at `:app` with `ksp` Hilt at `:ui:preferences` is supported by Dagger but **is not proven in this repo** — flag it for Milestone 18's own verification rather than asserting it here.
- **Hilt's hidden cost is the static-analysis gauntlet, not the wiring.** See `common.gradle` above: `-Werror` javac on generated sources, `lint { warningsAsErrors true, checkGeneratedSources = true }`, and SpotBugs over generated bytecode with a custom hook that throws on any finding and **no `dagger`/`hilt` exclusion in `config/spotbugs/exclude.xml`**. Budget a step for this. Any exclusion added must follow this repo's established convention of a justifying comment per `<Match>` (see the heavily-commented entries in `config/spotbugs/exclude.xml`).
- Hilt version: latest stable in the `2.5x` line. I cannot verify from here which that is on 2026-08-20 and **will not guess a number into a plan** — the planner or developer must resolve it against Maven Central and record the exact pin. Constraints to check when they do: Hilt's AGP compatibility floor against **AGP 8.11.0 / Gradle 8.13 / JDK 21**, and Hilt's own transitive androidx `activity`/`fragment`/`lifecycle` versions against `:app`'s current resolved graph (gap #1 above).

**`compose`.**
- **The right module is `:ui:preferences`** — confirmed against Milestone 20's scope (`tasks/antennapod-sync-settings-modernization-future-work.md:65`, replacing `preferences_synchronization.xml` with a `ComposeView`). It is a `com.android.library` with the Kotlin plugin already applied, which is exactly what the Compose plugin needs. Edits: `alias(libs.plugins.kotlin.compose)` in its `plugins {}`, `android { buildFeatures { compose true } }`, and dependencies.
- **No Compose compiler version to pick.** Since Kotlin 2.0 the Compose compiler ships with Kotlin and is applied by `org.jetbrains.kotlin.plugin.compose`, which is **already in the catalog at `version.ref = "kotlin"`** (`gradle/libs.versions.toml:84`) and already declared `apply false` at `build.gradle:5`. No `composeOptions { kotlinCompilerExtensionVersion }` block is needed or wanted. This removes the whole class of Compose-compiler/Kotlin skew problems.
- **`:app` needs nothing.** See interop boundary #1.
- **BOM choice is a real decision with a repo-consistency angle.** The catalog already pins `compose = "1.7.5"` for `androidx-compose-ui`/`-runtime`, consumed by `app-wearos`. Two coherent options: (a) pick the `androidx.compose:compose-bom` release whose `compose-ui` is **1.7.5** (the `2024.11.00` train), so the entire repo stays on exactly one Compose UI version and `app-wearos` is not touched — minimal diff, consistent with `AGENTS.md`'s minimal-change rule; (b) pick a current BOM and leave `app-wearos` at 1.7.5, accepting two Compose UI versions in one repo (harmless — they never share a classpath — but untidy), or bump `app-wearos` too, which is an out-of-slice diff. Option (a) is the lower-risk default; option (b) is the better *portfolio* story if freshness matters, which makes it a José-flavoured call rather than a purely technical one. Either way `compileSdk 36` (`common.gradle:2`) clears any modern Compose `compileSdk` floor.
- Artifacts and configurations: `androidx.compose.material3:material3` + `androidx.compose.foundation:foundation` + `androidx.compose.ui:ui-tooling-preview` as `implementation`; **`androidx.compose.ui:ui-tooling` as `debugImplementation`**, not `implementation` — it drags the preview/inspector infrastructure into release builds otherwise, and `:app`'s release variants are R8-minified in CI (`.github/workflows/checks.yml:64-73`). `debugImplementation` works in a flavoured library module and applies across both flavours.
- Note for Milestone 20, not this one: `google-material` 1.12.0 (View Material3) and `androidx.compose.material3` are two independent implementations of the same spec — adding the Compose one does not unify theming, and the six-variant `ThemeSwitcher` bridge remains an open Milestone 20 problem.

**`concurrency`.**
- `kotlinx-coroutines-core` and `-android` are absent from the catalog but **present transitively at 1.7.3** on `:ui:preferences` (measured; see characterization gap #2). The catalog's only coroutines entry is `kotlinx-coroutines-play-services = "1.9.0"` (`gradle/libs.versions.toml:57`), used solely by `app-wearos` (`app-wearos/build.gradle:79`).
- Catalog convention says a shared version deserves a ref: introduce `[versions] coroutines` and point `-core`, `-android`, and (optionally, by re-pointing the existing line) `-play-services` at it. Re-pointing `play-services` is a one-line touch of an existing entry that changes nothing if the version chosen is 1.9.0 — cheap consistency. Choosing a version **above** 1.9.0 would move `app-wearos`'s resolved coroutines too, which is out of slice.
- **Recommend deferring `kotlinx-coroutines-rx3` to Milestone 17.** Three reasons: (i) whether it is needed at all depends on Milestone 17's undecided bridge-vs-replace call (`tasks/antennapod-sync-settings-modernization-future-work.md:34`); (ii) an unused catalog entry proves nothing (characterization gap #3), so adding it now buys no de-risking; (iii) it must version-match `-core` anyway, so adding it later is a one-line change against a ref that already exists. The Rx surface it would bridge is small — two orphaned subscriptions in `GpodderAuthenticationFragment` plus `NextcloudLoginFlow` in `:net:sync:gpoddernet`, which is outside this module. **Note the version-ref shape makes deferral cheap only if the `coroutines` ref is added now**, which is an argument for adding the ref in this milestone even though only two of its three consumers exist yet.

**Paparazzi — the one item that can break a green suite.**
- Paparazzi is a **Gradle plugin** (`app.cash.paparazzi`), not a plain test dependency: `[plugins]` entry + root `apply false` + module application. Its tasks are per-variant, so in this flavoured module they are `recordPaparazziFreeDebug` / `verifyPaparazziPlayDebug` etc. — never the unflavoured names (`ui/preferences/README.md:54-56`, convention 8, and the same warning in this sequence's standing conventions).
- **Paparazzi only supports `com.android.library` modules.** `:ui:preferences` is a library, so this happens to be satisfied — but it also means Paparazzi can never be applied to `:app`, which is worth recording so nobody tries.
- **The coexistence risk with Robolectric is the headline.** Paparazzi and Robolectric's `@GraphicsMode(NATIVE)` both drive layoutlib and its native rendering libraries, and they would share one unit-test source set and one unit-test classpath in this module — the same source set holding Milestone 15's 38 characterization tests and (if 15b merges) `SyncSettingsScreenshotCaptureTest.kt`'s native-graphics bitmap render. AGP consistent resolution (see interop boundary) means Paparazzi's `testImplementation` additions are not isolated from the main classpath either. **I cannot verify from here that they coexist cleanly on this AGP/Gradle/JDK combination**, and this repo's regression net is precisely what would break. The plan should treat Paparazzi as its own final step, with an acceptance criterion that re-runs `testFreeDebugUnitTest` **and** `testPlayDebugUnitTest` in full and an explicit rollback criterion if they do not stay green.
- **Worth putting to the planner: the repo may not need Paparazzi at all.** Milestone 15b already demonstrated a working screenshot mechanism in this exact module using Robolectric `@GraphicsMode(NATIVE)` with zero new tooling — which is what makes the "add Paparazzi" line in the milestone scope worth a deliberate justify-or-defer decision rather than automatic execution. Paparazzi's genuine advantages (deterministic `record`/`verify` golden-image gating; no bitmap-comparison harness to hand-roll) are real and are exactly what Milestone 20 will want, and `ui/preferences/README.md` convention 9 explicitly warns that the Robolectric capture's PNG is *never* asserted byte-for-byte because cross-machine font rasterisation is not deterministic. But Milestone 20 is when the first snapshot is actually written, and adding Paparazzi now buys de-risking only if this milestone actually writes a throwaway snapshot test to prove the plugin works — which a "no behavior change, no new tests" milestone may not want to do. Recommend the planner choose explicitly between (a) add + prove with one trivial snapshot test, (b) add catalogued-only and accept it is unproven, (c) defer to Milestone 20. Do not let it default.
- Version constraints to verify (not guessable from here): a Paparazzi release supporting **AGP 8.11.0, Gradle 8.13, JDK 21, and Kotlin 2.3.20**. Paparazzi's AGP support has historically lagged AGP releases by months, and this repo is on a recent AGP. If no compatible release exists, that is a finding, not a workaround opportunity.
