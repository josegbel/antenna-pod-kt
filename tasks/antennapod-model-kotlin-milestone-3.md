## Research
_Last updated by: legacy-android-researcher | 2026-07-21_

### Summary

`:model` is a pure data-model Gradle library (`de.danoeh.antennapod.model`, an `android.library` with the Kotlin + ktlint plugins already applied since Milestone 1) holding the app's core value types — `Feed`, `FeedItem`, `FeedMedia`, `Chapter`, plus playback/download/enum helpers. Re-verified against current source, it is **15 Java / 12 Kotlin (27 files total)**, exactly matching the carried-forward count. Milestones 1 (8 framework-free enums/POJOs) and 2 (`FeedFilter`, `DownloadResult`, `FeedItemFilter`, `Transcript`) are merged; the 12 Kotlin files listed in `model/README.md` line 4 all exist on disk. The `kotlin` track has no prerequisites and is the only track requested here; every conversion is billed as behavioral-equivalence-preserving, so the gating question each milestone is *what safety net exists before the J2K conversion runs*.

This milestone should take the **framework-coupled tier** — `MediaType`, `SortOrder`, `VolumeAdaptionSetting`, `MediaMetadataRetrieverCompat` — the coherent next-lowest-complexity group (4 files, 190 LOC total, all enum- or tiny-class-shaped, mirroring Milestone 2's 4-file batch). This batch forced a real decision about `android.text.TextUtils` / `android.media.AudioEffect` / `MediaMetadataRetriever` coupling, since `:model` has **no Robolectric wiring** — **resolved 2026-07-21 (see Unknown 1 resolution below): `TextUtils.isEmpty(x)` calls in `MediaType`/`SortOrder` convert to Kotlin's `x.isNullOrEmpty()` instead of adding Robolectric**, which removes the framework coupling (and the architectural risk it posed to a future KMP target) rather than papering over it with a test-only shim. My explicit recommendation is to **exclude both `SubscriptionsFilter` and `FeedPreferences` (including its four nested enums) from this batch** — reasoning in Constraints & Risks and Unknowns. They are higher-risk for reasons that are independent of the enum tier and should not be smuggled in alongside it.

### Constraints & Risks

- **Robolectric-in-`:model` — RESOLVED, do not add it for this batch.** José flagged an architectural concern during scoping: `:model` is a plain data-model module today, and adding a Robolectric/`android.*` test dependency to characterize `TextUtils.isEmpty` calls would be shimming around framework coupling that has no business being in `:model` at all — especially relevant if the codebase ever adds a Kotlin Multiplatform iOS target, where `commonMain` cannot reference `android.text.TextUtils` in any form, tested or not. Robolectric itself is `testImplementation`-scoped and would never ship to a consumer on any platform, but its presence would have been evidence of real main-source Android coupling that *does* block KMP portability. **Decision: instead of adding Robolectric, replace `TextUtils.isEmpty(x)` with Kotlin's `x.isNullOrEmpty()` (identical null-or-empty semantics, zero Android dependency) in `MediaType` and `SortOrder` as part of the J2K conversion itself.** This removes the framework coupling rather than testing around it, and eliminates the need for Robolectric in this batch entirely. This is not a blocker on `VolumeAdaptionSetting`, which already has a passing net.
- **`AudioEffect`/`MediaMetadataRetriever` coupling in `VolumeAdaptionSetting`/`MediaMetadataRetrieverCompat` has no stdlib replacement — explicitly OUT OF SCOPE for this milestone.** Unlike `TextUtils.isEmpty`, hardware audio-effect enumeration and media metadata extraction are genuine platform capabilities with no cross-platform equivalent; making these two files KMP-portable would require an `expect`/`actual` split moving the Android-specific implementation out of `:model` into an Android-only source set. That is a structural decision for a future milestone (if/when KMP is actually pursued), not something to fold into a straight J2K conversion. Flagged here so it isn't silently reintroduced by a future "let's just add Robolectric" shortcut.
- **Numeric-contract preservation.** `SortOrder`'s `code` literals and `VolumeAdaptionSetting`'s `value` literals are persisted; a J2K reshuffle or `enumValues` ordering assumption must not touch them. Kotlin conversion should keep `code`/`value` as `@JvmField val` (per `model/README.md:5`) so downstream Java `.code` / `.value` field access still compiles.
- **`@JvmStatic` on the static helpers.** `SortOrder.parseWithDefault/fromCodeString/toCodeString`, `MediaType.fromMimeType`, `VolumeAdaptionSetting.fromInteger/setBoostSupported/isBoostSupported` are all called as Java statics by ~23 (`MediaType`), ~37 (`SortOrder`), ~15 (`VolumeAdaptionSetting`) downstream files. Converting to a Kotlin `companion object` without `@JvmStatic`/`@JvmField` would break every caller's compile — this is the primary API-preservation hazard for the batch.
- **`@VisibleForTesting` seam must survive.** `VolumeAdaptionSetting.setBoostSupported` is the hook `VolumeAdaptionSettingTest` depends on; it must remain callable from Java with the same signature or the existing test breaks.
- **Nullability of `TextUtils`-adjacent params.** `MediaType.fromMimeType(String mimeType)` and `SortOrder.fromCodeString(@Nullable String)` accept null; `SortOrder` already annotates `@Nullable`. J2K will read `@Nullable` correctly but will infer platform types for `MediaType`'s un-annotated `mimeType` and for `TextUtils` return values — planner should specify the intended Kotlin nullability so J2K's guess isn't rubber-stamped.
- **`SubscriptionsFilter` — recommend EXCLUDE.** 62 LOC, framework-coupled via `TextUtils.split`/`TextUtils.join` (`SubscriptionsFilter.java:31,60`), and **zero test coverage anywhere** (0 test files reference it, re-verified). `TextUtils.split` has the exact trailing-empty-token / empty-string-returns-`[]` behavior that bit `FeedItemFilter` in Milestone 2's `String.split` trap — converting it with no safety net is precisely the high-risk shape the pipeline exists to avoid. It should only move once a Robolectric characterization test is written for it first; it is riskier than the enum tier and should not ride along.
- **`FeedPreferences` — recommend EXCLUDE, and do NOT carve out just the nested enums.** 324 LOC, `implements Serializable` (so the `serialVersionUID` trap is live), mutable getters/setters, 35 downstream references but only 1 downstream test file and no `:model` test. Its four nested enums (`AutoDeleteAction`, `NewEpisodesAction`, `SkipSilence`, `AutoDownloadSetting`, each an int-`code`/`fromCode` shape like Milestone 1's picks — `FeedPreferences.java:20-108`) *look* trivially convertible, but they cannot be converted in isolation: they are nested inside a Java class, so converting only them means either (a) converting the whole 324-LOC Serializable parent this milestone — a large jump from M2's scope with the serialVersionUID hazard and near-zero net — or (b) extracting them to standalone files, which changes the `FeedPreferences.AutoDeleteAction` reference path for 35 consumers — an API change, i.e. bespoke restructuring the researcher must not fold in quietly. Either path is a separate, deliberately-scoped decision for the planner/client.

## Plan
_Last updated by: legacy-android-planner | 2026-07-21 (revised for red-team loop 1 findings: MAJOR 1 field visibility, MAJOR 2 `close()` override, MINOR 3 non-numeric test, MINOR 4 `parseWithDefault` nullability)_

### Objective
Continue the `:model` `kotlin`-track case study (Milestone 3) by converting the framework-coupled enum tier — `MediaType`, `SortOrder`, `VolumeAdaptionSetting`, `MediaMetadataRetrieverCompat` — from Java to behaviorally-equivalent Kotlin, decoupling `MediaType`/`SortOrder` from `android.text.TextUtils` via Kotlin's `isNullOrEmpty()` (no Robolectric) and preserving every persisted numeric contract and downstream Java-callable API.

### Resolved Decisions

- **Unknown 1 — Robolectric in `:model` (RESOLVED by José, carried forward, not re-litigated):** Do NOT add Robolectric or any `android.*` test dependency to `:model`, and do NOT touch `model/build.gradle`. The `TextUtils.isEmpty(x)` guards in `MediaType.fromMimeType` and `SortOrder.fromCodeString` are decoupled instead — final Kotlin form is `x.isNullOrEmpty()` (identical null-or-empty semantics, zero framework dependency, KMP-safe).
- **Sequencing consequence of Unknown 1 (RESOLVED by planner — this is the one genuinely new call):** `TextUtils.isEmpty(...)` is the *first executed line* of both `fromMimeType` and `fromCodeString`, so on `:model`'s bare-JVM unit runner (no Robolectric, no `testOptions.unitTests.returnDefaultValues`) **every** branch of both methods throws "not mocked" pre-conversion — the current Java is not executable under a module-local unit test at all. Therefore, for `MediaType` and `SortOrder` only, the characterization-test step also replaces the `TextUtils.isEmpty(x)` guard with its **documented pure-Java identity** `x == null || x.isEmpty()` (Android's own `TextUtils.isEmpty` javadoc: "Returns true if the string is null or 0-length") and drops the `android.text.TextUtils` import — the minimal change that makes the file bare-JVM-testable *while still Java*, so the characterization net can go green BEFORE the J2K conversion. The subsequent J2K step then collapses `x == null || x.isEmpty()` into idiomatic `x.isNullOrEmpty()`. Net effect matches José's decision (Kotlin end-state uses `isNullOrEmpty()`, no Robolectric); the only nuance is that framework decoupling lands one commit earlier than the `.kt` rename so "tests green before conversion" is literally satisfiable. Flagged non-blocking in Open Questions in case José wants it folded into a single conversion commit instead.
- **Unknown 2 — `MediaMetadataRetrieverCompat.close()` testability (RESOLVED by planner: documented no-unit-test exception):** `close()` is framework-pure — it subclasses `android.media.MediaMetadataRetriever` and calls `release()`, swallowing `IOException` with no branch logic that materializes off-device. Chosen option (a): a documented no-unit-test exception, recorded in `model/README.md`. Rejected (b) adding `:model`'s first `androidTest`/instrumented source set — disproportionate infra for one 8-line swallow-and-log method in a small case-study milestone, and no `androidTest` precedent exists in `:model`; rejected (c) deferring the file — it converts cleanly and belongs with its tier. Equivalence is verified by inspection (identical `release()` call + `IOException` catch) plus the module still compiling and `:app:assembleDebug` succeeding for its ~5 downstream callers. A future instrumented milestone for the genuinely-untestable framework paths is flagged in Open Questions.
  - **`override` is mandatory on the Kotlin `close()` (RESOLVED by planner, addressing red-team MAJOR 2, loop 1):** `android.media.MediaMetadataRetriever` `implements AutoCloseable` and declares a real, non-final `public void close() throws IOException` in `compileSdk 36`'s `android.jar` (verified by red-team via `javap`). The existing `.java` overrides it implicitly (Java doesn't require `@Override`), which is why it compiles today; Kotlin, by contrast, makes `override` **mandatory** when redeclaring a supertype member — omitting it is a hard compile error, not a warning. Step 6's Kotlin must therefore be `override fun close()`.
  - **`throws IOException` needs NO Kotlin-side signature handling (RESOLVED by planner, addressing red-team MAJOR 2, loop 1):** Kotlin has no checked exceptions — all exceptions are unchecked at the type level — so overriding a Java method that declares `throws IOException` requires no `@Throws` annotation and no change to the override's signature. The method still `catch (e: IOException)` internally exactly as the Java does; the only reason `IOException` appears at all is the local `try`/`catch` around `release()` (itself declared `throws IOException`). No `@Throws(IOException::class)` is added (it would be pointless here since `close()` swallows the exception and never rethrows).
- **Unknown 4 — explicit Kotlin nullability (RESOLVED by planner, not left to J2K):** `MediaType.fromMimeType`'s currently-unannotated `String mimeType` parameter becomes explicit `String?` (required: `isNullOrEmpty()` is an extension on `CharSequence?`, and the method's contract already accepts null → `UNKNOWN`). `SortOrder.fromCodeString`'s already-`@Nullable` `codeStr` becomes `String?`; its return stays `SortOrder?` and `toCodeString`'s param/return stay `SortOrder?`/`String?` (mirroring the existing `@Nullable`s). Do not accept J2K's platform-type inference for these.
- **Unknown 4 (extended) — `SortOrder.parseWithDefault` nullability (RESOLVED by planner, addressing red-team MINOR 4, loop 1; not left to J2K):** `parseWithDefault(value: String, defaultValue: SortOrder)` — **both parameters non-null.** Reasoning, not a J2K rubber-stamp: (1) the method body is `try { return valueOf(value) } catch (IllegalArgumentException) { return defaultValue }` — `value` flows straight into `Enum.valueOf`, which already throws (NPE) on a null name, so the method never had graceful null-`value` handling to preserve; a non-null Kotlin param simply moves the same failure to an `Intrinsics` check at entry for a case that cannot occur. (2) `defaultValue` is only ever *returned* on the catch branch, never dereferenced, so it is null-tolerant internally — but the sole downstream caller (`storage/preferences/.../UserPreferences.java:829`, `SortOrder.parseWithDefault(sortOrderStr, SortOrder.DATE_NEW_OLD)`) passes a non-null `String` (from `prefs.getString(key, "use-default")`) and a non-null enum literal, so non-null is exactly equivalent for every real call. Documented residual: were a *future* caller to pass `defaultValue = null` expecting null-passthrough, the non-null param would `NPE` at entry instead of returning null — currently unreachable, flagged so the reviewer treats non-null as a deliberate decision, not an oversight.
- **API-preservation (per `model/README.md`, carried forward):** No `data class` for any of the four (none override `equals`/`hashCode`; keep enum/plain-class identity). **Field visibility must match today's Java exactly — do not widen (red-team MAJOR 1, loop 1):** `SortOrder.code`/`scope` are `public final` today (`SortOrder.java:37,40`) and therefore stay `@JvmField val` so downstream Java field access (`.code`, `.scope`) keeps compiling. **`VolumeAdaptionSetting.value`/`adaptionFactor` are `private` today (`VolumeAdaptionSetting.java:16-17`) — reachable only via `toInteger()`/`getAdaptionFactor()`, and grep confirms zero of the 15 downstream references touch them directly — so they must become plain `private val` (NOT `@JvmField val`, which would newly expose them as public Java fields and is a no-op on a private property anyway). `toInteger()`/`getAdaptionFactor()` remain the sole Java-visible accessors, exactly as today.** All static helpers (`MediaType.fromMimeType`; `SortOrder.parseWithDefault`/`fromCodeString`/`toCodeString`; `VolumeAdaptionSetting.fromInteger`/`isBoostSupported`/`setBoostSupported`) move to `companion object` with `@JvmStatic` so the ~23 / ~37 / ~15 downstream Java callers keep compiling. `VolumeAdaptionSetting.setBoostSupported` keeps `@VisibleForTesting` and its `(Boolean?)` signature — `VolumeAdaptionSettingTest`'s `@Before setBoostSupported(false)` / `@After setBoostSupported(null)` calls compile unchanged against a `@JvmStatic fun setBoostSupported(boostSupported: Boolean?)`, so **no test adjustment is required**.
- **Numeric persistence contracts preserved verbatim:** `SortOrder.code` literals (1–11, 101–106) and `VolumeAdaptionSetting.value` literals (0–5) must not be re-derived from ordinals; the `SortOrderTest` `codeLiteralsPreserved` assertion and the existing `VolumeAdaptionSettingTest` `toInteger` cases pin them.
- **Test files stay Java (carried-forward José decision):** No `:model` test file is converted to Kotlin this milestone; new characterization tests are authored in Java.

### Steps
Each step names the file(s) and test(s) it touches, is small enough to review as one diff, and leaves the build green (`./gradlew :model:test` and `./gradlew :app:assembleDebug`).

1. **Add `MediaTypeTest.java` characterization net and decouple `MediaType` from `TextUtils` (still Java).** Create `model/src/test/java/de/danoeh/antennapod/model/MediaTypeTest.java` (package `de.danoeh.antennapod.model`) with one assertion per branch of `fromMimeType`: `fromMimeTypeNullReturnsUnknown`, `fromMimeTypeEmptyReturnsUnknown`, `fromMimeTypeAudioPrefixReturnsAudio` (`"audio/mpeg"`), `fromMimeTypeVideoPrefixReturnsVideo` (`"video/mp4"`), `fromMimeTypeApplicationOggReturnsAudio`, `fromMimeTypeApplicationOpusReturnsAudio`, `fromMimeTypeApplicationXFlacReturnsAudio`, `fromMimeTypeUnknownApplicationReturnsUnknown` (`"application/pdf"`). In the same diff, in `MediaType.java` replace `TextUtils.isEmpty(mimeType)` with `mimeType == null || mimeType.isEmpty()` and remove the `android.text.TextUtils` import.
