# antennapod-net-sync-service-interface-kotlin

> **Description:** kotlin track migration of the `:net:sync:service-interface` module (interface for the sync service, depended on by consumers; implementation registered via `ClientConfigurator`) — fourth case-study module in the antennapod portfolio, following `antennapod-model-kotlin` (Milestones 1–7), `antennapod-event-kotlin` (Milestones 8–9), and `antennapod-net-download-service-interface-kotlin` (Milestone 10). ## Research
_Last updated by: legacy-android-researcher | 2026-07-28_

### Summary

`:net:sync:service-interface` is a small, 100%-Java Android library module: **9 production files / 514 LOC**, all in the single package `de.danoeh.antennapod.net.sync.serviceinterface`, and **zero test files — the module has no `src/test` and no `src/androidTest` source set at all** (`net/sync/service-interface/src/` contains only `main`). Despite being the architectural sibling of `:net:download:service-interface` (Milestone 10), its actual shape is materially different. Milestone 10's module was three abstract static-singleton facades plus logic-dense filename utilities. This one is: (a) **one** abstract static-singleton facade, `SynchronizationQueue` (36 LOC, 9 abstract methods, implemented by `SynchronizationQueueImpl` in `:net:sync:service` and registered at `app/src/main/java/de/danoeh/antennapod/ClientConfigurator.java:53`); (b) its no-op `SynchronizationQueueStub`, used as a test double by four Java tests in two *other* modules; (c) a pure `interface`, `ISyncService`, implemented by two Java backends in `:net:sync:gpoddernet`; (d) four data/DTO carriers (`EpisodeAction`, `EpisodeActionChanges`, `SubscriptionChanges`, `UploadChangesResponse`); (e) one enum with a static lookup, `SynchronizationProvider`; and (f) one checked exception, `SyncServiceException`, subclassed by two Java classes. **57% of the module's LOC is a single file, `EpisodeAction.java` (293 LOC)**, which is a builder + JSON serializer/deserializer and is by far the densest logic here. The module depends on `:model` (already Kotlin) and declares `:storage:preferences`, `libs.rxandroid` and `libs.rxjava` which are **not referenced by any source file** — they are dead dependencies (`net/sync/service-interface/build.gradle:12,15,16`).

The `kotlin` track here is a **serialization-contract problem layered on top of an interop-width problem**, and the risk centre is different from Milestone 10's. Three things drive that. First, `EpisodeAction`'s JSON read/write is the on-the-wire contract with gpodder.net and Nextcloud *and* the on-disk format of the user's pending-sync queue in `SharedPreferences` (`net/sync/service/src/main/java/.../SynchronizationQueueStorage.java:35,164`) — and **nothing in this repository tests it, in any module**. A silent regression there loses queued play positions without any crash, which is precisely the failure class this pipeline exists to prevent. Second, this module is downstream of already-Kotlin `:model`, exactly as Milestone 10 was, but the forced-null-decision sites are fewer and sharper: the entire nullability exposure funnels through `EpisodeAction.Builder(FeedItem, Action)` (`EpisodeAction.java:241-244`), which chains `item.getFeed().getDownloadUrl()` and `item.getMedia().getDownloadUrl()` across two `Feed?`/`FeedMedia?` links whose results are both `String?`. Third — and this is the item with no Milestone 10 analogue — **two JVM-shape decisions are load-bearing at compile time in other modules**: `UploadChangesResponse.timestamp` is a `public final long` **field**, read unqualified from inside a Java subclass (`GpodnetUploadChangesResponse.java:48`) and qualified from `:net:sync:service` (`SyncService.java:208,255`), so it needs `@JvmField` rather than a Kotlin `val`; and `EpisodeAction`'s four `public static final Action` aliases (`:23-26`) are consumed as `EpisodeAction.PLAY` etc. from five modules and cannot be `const val` (not a primitive/String), so they need `@JvmField` too. Alongside those, one *silent* regression candidate stands out: `SynchronizationProvider.fromIdentifier(String)` returns `null` today for an unrecognised or null key, and `SyncService.doWork()` depends on that null to no-op for every user who has never configured sync.

### Findings

#### Existing surface

All nine production files live in one package, `de.danoeh.antennapod.net.sync.serviceinterface`. The module README (`net/sync/service-interface/README.md:1-4`) describes it as "the interface for starting the sync service. Defines `ISyncService` for backend implementations and `SynchronizationQueue` for queuing local changes before upload."

| File | LOC | Shape | Responsibility |
|---|---|---|---|
| `EpisodeAction.java` | 293 | immutable value + nested `enum` + nested `Builder` | The module's only logic-dense file. 4 `public static final Action` aliases, `readFromJsonObject`, `writeToJsonObject`, hand-written `equals`/`hashCode`/`toString`, 6 getters, nested `enum Action`, nested `Builder` with 2 constructors and 6 fluent mutators. |
| `SynchronizationQueue.java` | 36 | `public abstract class` + static singleton | Sync-queue facade. `private static SynchronizationQueue instance` + `getInstance()`/`setInstance()`, then 9 abstract methods (`sync`, `syncImmediately`, `fullSync`, `syncIfNotSyncedRecently`, `clear`, `enqueueFeedAdded`, `enqueueFeedRemoved`, `enqueueEpisodeAction`, `enqueueEpisodePlayed`). |
| `SynchronizationQueueStub.java` | 41 | concrete no-op subclass | Test double, consumed by **4 Java tests in 2 other modules**. |
| `SubscriptionChanges.java` | 39 | immutable DTO | `List<String> added`/`removed` + `long timestamp`, both lists `@NonNull`-annotated; `toString()` dereferences both lists. |
| `EpisodeActionChanges.java` | 34 | immutable DTO | `List<EpisodeAction>` + `long timestamp`, list `@NonNull`-annotated; `@NonNull toString()`. |
| `SynchronizationProvider.java` | 25 | `enum` + static lookup | Two constants (`GPODDER_NET`, `NEXTCLOUD_GPODDER`), a `String identifier`, and `static fromIdentifier(String)` **returning `null` on no match** (`:13`). |
| `ISyncService.java` | 20 | `interface` | 6 methods, every one `throws SyncServiceException`. Implemented by 2 Java classes in `:net:sync:gpoddernet`. |
| `SyncServiceException.java` | 13 | checked `Exception` | `serialVersionUID = 1L` (`:4`), ctors `(String)` and `(Throwable)`. Subclassed by 2 Java classes. |
| `UploadChangesResponse.java` | 13 | `public abstract class` | A single **`public final long timestamp` field** (`:8`) — not a getter — plus a `(long)` constructor. Subclassed by 2 Java classes in `:net:sync:gpoddernet`. |

Notable structural details:

- **Only one static singleton holder, and it uses the bean naming.** `SynchronizationQueue.getInstance()`/`setInstance()` (`SynchronizationQueue.java:6-14`). This is *easier* than Milestone 10, whose `DownloadServiceInterface` used the non-bean `get()`/`setImpl()` pair that no Kotlin construct emits naturally. A Kotlin `companion object` with a `@JvmStatic var instance` gets the right JVM names here for free — but see the interop section for why the *type* still needs a decision.
- **`EpisodeAction` mixes four idioms in one file**: a static-factory JSON parser that returns `null` (`:55-95`), an instance JSON writer that returns `null` on failure (`:186-206`), a nested `enum`, and a nested `Builder` whose PLAY-only setters silently no-op for non-PLAY actions (`:266-285`).
- **`EpisodeAction`'s four static aliases duplicate the nested enum constants**: `public static final Action NEW = Action.NEW;` and three siblings (`:23-26`). Java callers use both forms — `EpisodeAction.PLAY` in production, `EpisodeAction.Action.PLAY` in tests. Both must survive.
- **`SynchronizationProvider` declares its static method *before* its instance field and constructor** (`:7-20`), which is unusual ordering and will interact with ktlint/J2K member reordering; the repo's `AGENTS.md` forbids reordering code, so the Kotlin form should keep the companion where it reads equivalently rather than being "tidied".
- **`EpisodeAction` has a pre-existing `equals` defect.** `EpisodeAction.java:161` reads `&& action != that.action` where every sibling clause is an equality test. The consequence: two field-identical `EpisodeAction`s are **not** equal, while two actions differing only in `action` can be. `hashCode()` (`:168-179`) *does* include `action`, so the equals/hashCode contract is violated in the same direction. Nothing in the repo calls `EpisodeAction.equals` (the `ArrayMap`s in `EpisodeActionFilter` are keyed on `Pair<String,String>`, not on actions), so this is currently dead-but-wrong code. It is called out here because it is the kind of thing a converter or a reviewer will "fix" mid-migration, which would be a behaviour change smuggled into an equivalence-preserving diff.
- **`writeToJsonObject` hardcodes the date pattern that `readFromJsonObject` reads from a constant.** `PATTERN_ISO_DATEFORMAT` (`:22`) is used at `:72`; the identical literal `"yyyy-MM-dd'T'HH:mm:ss"` is re-typed inline at `:193`. Equivalent today; worth pinning by test before anyone unifies them.
- **`build.gradle` is markedly plainer than Milestone 10's module.** `net/sync/service-interface/build.gradle` is 17 lines: `alias(libs.plugins.android.library)` only, `apply from: "../../../common.gradle"`, namespace, and 6 dependency lines. It does **not** apply `playFlavor.gradle`, does **not** apply `id("java-test-fixtures")`, has **no `lint { }` block**, and declares **no test dependencies whatsoever**. Do not carry Milestone 10's build assumptions over.

#### Java/Kotlin interop boundary

**Inbound (what calls INTO this module).** Seven Gradle modules declare `implementation project(':net:sync:service-interface')` — two more than Milestone 10's module had: `:app` (`app/build.gradle:86`), `:net:download:service` (`net/download/service/build.gradle:17`), `:net:sync:gpoddernet` (`net/sync/gpoddernet/build.gradle:11`), `:net:sync:service` (`net/sync/service/build.gradle:16`), `:storage:database` (`storage/database/build.gradle:19`), `:playback:service` (`playback/service/build.gradle:21`), `:ui:preferences` (`ui/preferences/build.gradle:34`). Registered at `settings.gradle:32`.

Across those seven modules, **28 files reference the package and every single one is `.java`. There is no Kotlin caller anywhere in the repo.** So all interop pressure is one-directional and flows through the JVM signature, not through Kotlin's type system — with the important caveat that Kotlin's emitted `@Nullable` annotations *are* visible to SpotBugs, which is a hard gate here (see track-specific findings).

Breakdown of the inbound surface that must not change:

- **`SynchronizationQueue.getInstance()` — the widest entry point, 22 call sites in 6 modules.** `:app`: `MainActivity.java:221`, `EpisodeMultiSelectActionHandler.java:117,130`. `:playback:service`: `Media3PlaybackService.java:286,515`, `PlaybackService.java:983,1206`. `:storage:database`: `DBWriter.java:163,193,705,873,878`, `FeedDatabaseWriter.java:138`. `:net:download:service`: `MediaDownloadedHandler.java:113`, `FeedUpdateWorker.java:118`. `:ui:preferences`: `GpodderAuthenticationFragment.java:85,234`, `NextcloudAuthenticationFragment.java:95,99`, `SynchronizationPreferencesFragment.java:97,101,106`.
- **`SynchronizationQueue.setInstance(...)` — 5 call sites.** Production: `ClientConfigurator.java:53`. Java tests in *other* modules: `net/download/service/src/test/.../DbCleanupTests.java:88`, `DbQueueCleanupAlgorithmTest.java:31`, `DbWriterTest.java:67`, `storage/database/src/test/.../FeedDatabaseWriterTest.java:46`. Those four also instantiate **`SynchronizationQueueStub`** — so the stub's no-arg constructor and its 9 overrides are inbound API, not internal, and a regression there fails `:net:download:service:test` and `:storage:database:test` rather than this module's own suite.
- **`UploadChangesResponse.timestamp` — direct public-field access, and the sharpest compile-time item in the module.** Read qualified from `:net:sync:service` at `SyncService.java:208` (`newTimeStamp = uploadResponse.timestamp;`) and `:255` (`newTimeStamp = postResponse.timestamp;`), **and read unqualified via Java field inheritance from inside the Java subclass** `GpodnetUploadChangesResponse.java:48` (`"timestamp=" + timestamp`). A Kotlin `val timestamp: Long` in the constructor emits a *private* backing field plus `getTimestamp()`, which breaks all three sites at compile time. `@JvmField val timestamp: Long` emits a genuine `public final long` and is the only drop-in form. Secondarily, `GpodnetEpisodeActionPostResponse.java:46` renders itself via `ToStringBuilder.reflectionToString(this, ...)`, which walks inherited private fields — the field *name* stays `timestamp` under either form, so its output is unaffected, but this should be verified rather than assumed.
- **`EpisodeAction`'s four static `Action` aliases — 6 production call sites in 5 modules.** `EpisodeAction.DOWNLOAD` at `MediaDownloadedHandler.java:114`; `EpisodeAction.PLAY` at `SynchronizationQueueImpl.java:122`, `SyncService.java:240`, `EpisodeMultiSelectActionHandler.java:111`, `FeedDatabaseWriter.java:132`; `EpisodeAction.NEW` at `EpisodeMultiSelectActionHandler.java:131`; `EpisodeAction.DELETE` at `DBWriter.java:164`. Because their type is an enum, not a primitive or `String`, **`const val` is not available** — this is the structural difference from Milestone 10's `WORK_*` constants, where `const val` was the answer. Here the only working form is `@JvmField val PLAY = Action.PLAY` in a `companion object` (or, less faithfully, `@JvmStatic` accessors, which would change the JVM shape from field to method). A plain `val` breaks all 6 sites.
- **`EpisodeAction.Action` (the nested enum) is also used directly**: `EpisodeAction.Action.PLAY` at `EpisodeActionFilterTest.java:27,33,39,48,54,72,78,84,93,99,116,122,131,137,154,160,169,175,192,200` (20 sites in one test file in `:net:sync:service`). A Kotlin nested `enum class` keeps the same `Outer.Inner` JVM name, so this is safe by default — noted only because it means the enum must stay nested and must not be promoted to a top-level type.
- **`EpisodeAction.Builder` — 7 production call sites plus 12 in one test.** Production, all via `new EpisodeAction.Builder(<FeedItem>, <Action>)`: `MediaDownloadedHandler.java:114`, `SynchronizationQueueImpl.java:122`, `SyncService.java:240`, `EpisodeMultiSelectActionHandler.java:111,131`, `DBWriter.java:164`, `FeedDatabaseWriter.java:132`. **Every one of the seven immediately chains `.currentTimestamp()`.** The `(String, String, Action)` constructor is used only from tests (`EpisodeActionFilterTest.java`, 12 sites) and from `readFromJsonObject` itself (`EpisodeAction.java:68`). The fluent chain `.timestamp()/.guid()/.currentTimestamp()/.started()/.position()/.total()/.build()` is all live API.
- **`EpisodeAction.readFromJsonObject(JSONObject)` — 2 call sites, with opposite null discipline.** `ResponseMapper.java:52-55` (`:net:sync:gpoddernet`) **does** null-check the result. `SynchronizationQueueStorage.java:35` (`:net:sync:service`) **does not** — it calls `actions.add(EpisodeAction.readFromJsonObject(...))` unguarded, so a malformed stored entry puts a `null` into the returned `ArrayList<EpisodeAction>`, which then flows into `SyncService.syncEpisodeActions` and `EpisodeActionFilter`. That is a pre-existing latent NPE, not something this track introduces, but it constrains the return type: it **must** be `EpisodeAction?`.
- **`EpisodeAction.writeToJsonObject()` — 1 call site**, `SynchronizationQueueStorage.java:164`, whose result is passed straight to `JSONArray.put(Object)` with no null check (it returns `null` on `JSONException`, `EpisodeAction.java:203`).
- **`EpisodeAction`'s getters** are read from `EpisodeActionFilter.java:25,58,60,62,72-74` (`getPodcast`, `getEpisode`, `getAction`, `getTimestamp`) and `SyncService.java:277,278,288` (`getGuid`, `getEpisode`, `getPosition`). `getStarted()` and `getTotal()` are read **only** by `GpodnetService`/`NextcloudSyncService` when serializing uploads.
- **`SynchronizationProvider.fromIdentifier(String)` — 2 call sites, with opposite null discipline.** `SyncService.java:353-357` **does** null-check and returns `Result.success()`. `SynchronizationPreferencesFragment.java:119-124` **does not** — it feeds the result straight into `getProviderSummary(provider)`/`getProviderIcon(provider)` (`:229-248`), each of which `switch`es on it, so a null there NPEs today. Also inbound: `SynchronizationProvider.GPODDER_NET`/`NEXTCLOUD_GPODDER` constants (`SynchronizationPreferencesFragment.java:136`, `GpodderAuthenticationFragment.java:256`, `NextcloudAuthenticationFragment.java:93`), `values()` (`SynchronizationPreferencesFragment.java:165`), `getIdentifier()` (3 sites), and Java `switch` statements over the enum (`SyncService.java:358-369`, `SynchronizationPreferencesFragment.java:199+,230,241`).
- **`ISyncService` is implemented by two Java classes** — `GpodnetService.java` and `NextcloudSyncService.java` in `:net:sync:gpoddernet`. All six method signatures and the `throws SyncServiceException` clauses must survive. Kotlin does not have checked exceptions, so every method needs `@Throws(SyncServiceException::class)` or the Java implementations' `throws` clauses become illegal-narrowing / the Java *callers*' `catch (SyncServiceException e)` blocks become unreachable-catch compile errors. `SyncService.java:209` has exactly such a `catch (SyncServiceException exception)`, and `syncSubscriptions`/`syncEpisodeActions` declare `throws SyncServiceException` (`:144,219`). **This is a hard compile-time requirement with no Milestone 10 analogue** — that module had no checked exceptions.
- **`SyncServiceException` is subclassed by two Java classes** — `GpodnetServiceException.java:5-14` (both ctors, plus its own `serialVersionUID`) and `NextcloudSynchronizationServiceException.java:5-8` (`Throwable` ctor only). Both call `super(...)`. Also thrown/caught throughout `GpodnetService.java` (7 refs) and `NextcloudSyncService.java` (7 refs), and `instanceof`-tested at `SyncService.java:100`.
- **`SubscriptionChanges` / `EpisodeActionChanges`** are constructed only in `:net:sync:gpoddernet` (`ResponseMapper.java:40,57`) and consumed only in `:net:sync:service` (`SyncService.java:148-155,182,193-194,222-224`). Their getters and `toString()` (used in a `Log.d` at `SyncService.java:154`) are the whole surface.

**Public API that must not silently break.** In practice: `SynchronizationQueue`'s static get/set pair + 9 abstract methods; `SynchronizationQueueStub`'s constructor + 9 overrides; `ISyncService`'s 6 methods with their `throws` clauses; `SyncServiceException`'s 2 constructors; `UploadChangesResponse.timestamp` **as a field** and its `(long)` constructor; `SynchronizationProvider`'s 2 constants, `values()`, `getIdentifier()`, and `fromIdentifier()`; `EpisodeAction`'s 4 static aliases, nested `Action` enum, nested `Builder` (2 ctors + 6 mutators + `build()`), `readFromJsonObject`, `writeToJsonObject`, and 6 getters; `SubscriptionChanges`/`EpisodeActionChanges`' constructors, getters and `toString()`. #### Current test coverage

**This module has zero tests.** `net/sync/service-interface/src/` contains only `main` — no `test`, no `androidTest`, no `testFixtures`. `build.gradle` declares no `testImplementation` at all. There is no lint baseline and no SpotBugs exclusion for the package. This is a strictly worse starting position than any prior milestone in this case study: `:model` and `:event` had substantial in-module suites, and Milestone 10's module had two test files (220 LOC). Here the module's entire safety net is (i) compilation of seven dependent Java modules and (ii) whatever coverage leaks in from other modules' suites, enumerated below. **Do not read the numbers below as coverage of this module — they are coverage of other modules that happens to traverse this one.**

**`net/sync/service/src/test/java/.../EpisodeActionFilterTest.java` (209 LOC, 5 tests) — the only test in the repo that exercises `EpisodeAction` at all.** It is a JUnit 3-style `extends TestCase` (`:18`) in `:net:sync:service`, and it runs under plain JUnit with no Robolectric (`net/sync/service/build.gradle:34` declares only `libs.junit`). What it actually touches of *this* module: the `Builder(String, String, Action)` constructor, `.timestamp(Date)`, `.position(int)`, `.build()`, and — transitively, inside `EpisodeActionFilter` — `getPodcast()`, `getEpisode()`, `getAction()`, `getTimestamp()`. What it actually asserts: only the **size** of the returned map (`assertSame(1, ...)` `:62`, `assertSame(0, ...)` `:107`, `assertEquals(2, ...)` `:145`, `assertEquals(0, ...)` `:183`, `assertSame(1, ...)` `:208`) — never the identity or field values of any `EpisodeAction` in it. The one genuinely useful null-behaviour fact it pins is at `:186-209`: an action built **without** a timestamp (`:191-196`, comment "no timestamp") is overridden by a remote action that has one, i.e. `getTimestamp()` returning `null` is a live, exercised state.

What that test does **not** touch, anywhere in the repo: `readFromJsonObject`, `writeToJsonObject`, `equals`, `hashCode`, `toString`, `getGuid`, `getStarted`, `getTotal`, `currentTimestamp()`, `.guid()`, `.started()`, `.total()`, the `Builder(FeedItem, Action)` constructor, the four static `Action` aliases, and the non-PLAY branch of the `started`/`position`/`total` gating.

**`SynchronizationQueue`'s static holder round-trip is exercised, but only as a mute.** `DbCleanupTests.java:88`, `DbQueueCleanupAlgorithmTest.java:31`, `DbWriterTest.java:67` (all in `:net:download:service`) and `FeedDatabaseWriterTest.java:46` (in `:storage:database`) each call `SynchronizationQueue.setInstance(new SynchronizationQueueStub())` in `@Before` so that production code under test can call `getInstance()` without NPEing. **None of them asserts anything about the queue**, and because the stub is a no-op, none of them observes any enqueue behaviour. Their real value to this track is narrow but genuine: a `@JvmStatic` regression on `getInstance`/`setInstance`, or a `SynchronizationQueueStub` signature regression, breaks `:net:download:service:test` and `:storage:database:test` loudly. `getInstance()`'s **null default** (no `setInstance` called) is exercised by nothing.

**`ISyncService`, `SyncServiceException`, `UploadChangesResponse`, `SubscriptionChanges`, `EpisodeActionChanges`, `SynchronizationProvider`: no test coverage anywhere in the repo, direct or indirect.** `net/sync/gpoddernet/src/test/.../HostnameParserTest.java` and `net/sync/service/src/test/.../GuidValidatorTest.java` exist but touch none of these types. `SyncService` itself — the single biggest consumer — has no test at all.

#### Characterization-test gaps

Ordered by risk. These must be written and green **before** any `.java` → `.kt` rename, not after. Note a prerequisite that applies to gaps 1 and 2: this module currently has **no test source set and no test dependencies**, so Step 1 of any plan includes creating `src/test/java/...` and adding `testImplementation libs.junit`. And because `org.json.JSONObject`, `android.text.TextUtils` and `android.util.Log` are all Android-framework classes that throw `RuntimeException: Stub!` under plain JUnit (`common.gradle:50-55` sets `includeAndroidResources = true` but **not** `returnDefaultValues`), **`libs.robolectric` is unavoidable for the `EpisodeAction` JSON tests** — the `TextUtils`→stdlib swap discussed below does not remove that need, because `JSONObject` itself is the blocker. That is a real deviation from the `:model`/`:event` Robolectric-free precedent and from this repo's KMP-portability preference, and should be planned as a disclosed, scoped exception the way `model/build.gradle:24-28` documents its own.

1. **`EpisodeAction.readFromJsonObject` + `writeToJsonObject` — ~55 LOC of dual-contract serialization, zero tests. This is the single biggest gap in the module and the highest-consequence one.** These two methods define both the gpodder.net/Nextcloud wire format *and* the `SharedPreferences` persistence format of the user's pending-sync queue (`SynchronizationQueueStorage.java:35,164`). Nothing anywhere asserts: the mandatory-field guard returning `null` when `podcast`, `episode` or `action` is absent-or-empty (`:59-61`); that an unrecognised `action` string returns `null` rather than throwing (`:62-67`, `IllegalArgumentException` swallowed); that `action` matching is case-insensitive via `toUpperCase(Locale.US)` (`:64`); that an unparseable `timestamp` is **swallowed** and leaves `timestamp` null rather than rejecting the record (`:75-77`, `printStackTrace`); the exact UTC `yyyy-MM-dd'T'HH:mm:ss` parse and format, including `TimeZone.getTimeZone("UTC")` on both sides (`:72-73`, `:193-194`); that `guid` is only set when non-empty (`:79-82`); the **PLAY-only, all-or-nothing** gating of `started`/`position`/`total` on read, with its asymmetric predicate `started >= 0 && position > 0 && total > 0` (`:87` — note `started` uses `>=`, the other two use `>`), so a record with `position == 0` silently keeps all three at `-1`; that `putOpt` is used for `podcast`/`episode`/`guid` (so nulls are *omitted*, not written as `"null"`) while `put` is used for `action` (`:189-192`); that `started`/`position`/`total` are written **only** for PLAY (`:196-200`); and that a `JSONException` yields `null` plus a `Log.e` rather than propagating (`:201-204`). A **round-trip test** (`build → writeToJsonObject → readFromJsonObject → assert field-by-field`, avoiding `equals` because it is broken — see gap 4) plus **fixed golden JSON strings in both directions** is the right shape here. Getting any of this wrong silently drops or corrupts users' queued play positions with no crash and no visible symptom — exactly the failure mode this pipeline's value proposition rests on.
2. **`EpisodeAction`'s null-timestamp path through `writeToJsonObject` — untested, and it is a live crash.** `writeToJsonObject` at `:195` calls `formatter.format(this.timestamp)`; because `timestamp` is statically typed `Date`, javac binds `DateFormat.format(Date)`, which NPEs on null — and the surrounding `try` catches only `JSONException` (`:201`), so it propagates. A null timestamp is reachable: `readFromJsonObject` leaves it null whenever `timestamp` is absent or unparseable (`:69-78`), and `EpisodeActionFilterTest.java:191-196` proves the no-timestamp state is real. All seven *production* `Builder` call sites do chain `.currentTimestamp()`, so the crash is not reachable from the enqueue path today — but it is reachable from a re-serialization of a parsed action. Pin the current behaviour (whatever it is — verify empirically rather than trusting this analysis) before conversion, because Kotlin's overload resolution between `format(Date!)` and `format(Any!)` for a `Date?` receiver argument is exactly the kind of thing J2K will silently pick differently.
3. **`SynchronizationProvider.fromIdentifier` — zero tests, and it is the module's sharpest silent-regression site.** Untested behaviours: exact-match on identifier returns the constant; **unrecognised string returns `null`**; **`null` input returns `null`** (today `identifier.equals(null)` is `false` for both constants, so the loop falls through to `return null` at `:13`). The third one is load-bearing: `SyncService.doWork()` calls `getActiveSyncProvider()` unconditionally as its first statement (`:68`), which calls `fromIdentifier(SynchronizationSettings.getSelectedSyncProviderKey())` (`:353-354`), and `getSelectedSyncProviderKey()` is `prefs.getString(SELECTED_SYNC_PROVIDER, null)` — genuinely null for **every user who has never configured sync** (`storage/preferences/src/main/java/.../SynchronizationSettings.java:44-46`). The null return is what makes `doWork()` no-op. A 3-assert test here is trivially cheap and is the only guard against turning that no-op into a crash. Also worth pinning: `getIdentifier()` returns the exact strings `"GPODDER_NET"`/`"NEXTCLOUD_GPODDER"`, which are **persisted in `SharedPreferences`** (`SynchronizationSettings.setSelectedSyncProvider`, called from `GpodderAuthenticationFragment.java:256` and `NextcloudAuthenticationFragment.java:93`) — so they are an on-disk contract, not just an in-memory one.
4. **`EpisodeAction.equals`/`hashCode` — zero tests, and `equals` is defective.** `:161` uses `action != that.action` where the intent was clearly `action == that.action`. Consequence: field-identical instances compare unequal; instances differing only in `action` can compare equal; and `hashCode()` includes `action` (`:173`), so the contract is violated. Nothing in the repo calls it. This needs a characterization test **that pins today's behaviour, defect included**, before conversion — otherwise J2K's output plus a reviewer's instinct will quietly "fix" it, and a quiet fix is a behaviour change. Whether to also *deliberately* fix it (in a separate, clearly-labelled commit, or not at all in this milestone) is a planner decision, not a converter decision. See Unknowns.

No test anywhere covers a non-PLAY action with these set. Also untested: the `-1` defaults themselves as observable via `getStarted()`/`getPosition()`/`getTotal()`; `currentTimestamp()` (`:262-264`) setting a non-null `Date`; `guid()` (`:257-260`); and — most importantly — the **`Builder(FeedItem, Action)` constructor** (`:241-244`), which is the *only* constructor used in production and is exercised by nothing. #### Track-specific findings — `kotlin`

**Hazard 1 (compile-time, loud): `UploadChangesResponse.timestamp` must become `@JvmField`.** Detailed in the interop section. J2K's default output for `public final long timestamp` on an abstract class with a `(long)` constructor is a constructor `val`, which emits a private field + `getTimestamp()`. That breaks `SyncService.java:208,255` and `GpodnetUploadChangesResponse.java:48` at compile time in two other modules. `@JvmField val timestamp: Long` is the only faithful form. Loud rather than silent, but it is the item J2K is most reliably wrong about here.

**Hazard 2 (compile-time, loud): `ISyncService` needs `@Throws(SyncServiceException::class)` on all six methods.** Kotlin has no checked exceptions and emits no `throws` clause by default. Two Java classes implement this interface (`GpodnetService`, `NextcloudSyncService`) and declare `throws SyncServiceException` on their overrides; Java callers `catch (SyncServiceException ...)` around calls made through the interface type (`SyncService.java:209`) and re-declare `throws SyncServiceException` on their own methods (`:144,219`). Without `@Throws`, the Java `catch` becomes an unreachable-catch compile error. **No Milestone 10 analogue** — that module had no checked exceptions at all. `SyncServiceException` itself, once converted, does not need `@Throws` (it is the exception type, not a thrower), but its `serialVersionUID` (`SyncServiceException.java:4`) must be preserved as `private const val serialVersionUID: Long = 1L` inside a `companion object` so that it still emits a `static final long` field — a plain `val` would not, and the two Java subclasses each carry their own (`GpodnetServiceException.java:6`) so serialization compatibility across the hierarchy is observable.

**Hazard 3 (compile-time, loud): `EpisodeAction`'s four static aliases need `@JvmField`, not `const val`.** Their type is `Action`, so `const val` — Milestone 10's answer for `WORK_*` — is not applicable. `@JvmField val NEW = Action.NEW` in a `companion object` emits a `public static final Action` on the outer class, which is the drop-in. A plain `val` breaks six production call sites in five modules. Note the initialization-order subtlety: the companion's fields reference the nested enum, so the enum must be initialized first — it is, since `Action`'s clinit is independent, but it is worth an explicit test (gap 5) rather than an assumption.

**Hazard 4 (silent, highest consequence): `SynchronizationProvider.fromIdentifier`'s parameter and return must both be nullable.** Return type `SynchronizationProvider?` is forced by the `return null` at `:13`. The *parameter* is the dangerous half: J2K will typically emit `fun fromIdentifier(provider: String): SynchronizationProvider?` because there is no `@Nullable` annotation to tell it otherwise, and Kotlin then emits `Intrinsics.checkNotNullParameter`. The single most important caller passes a genuinely-null value on a hot path — `SyncService.java:353-354` ← `SynchronizationSettings.getSelectedSyncProviderKey()` ← `prefs.getString(SELECTED_SYNC_PROVIDER, null)` — for every user who has never configured sync, on **every single invocation of the sync worker**. Today that returns `null` and `doWork()` returns `Result.success()`. With a non-null parameter it becomes a hard crash in a `Worker`. And because the caller is Java, **the compiler will not warn about it**. `provider: String?` is the equivalence-preserving declaration. This is the direct structural analogue of Milestone 10's `isDownloadingEpisode(null)` finding, and like that one it is invisible to both the compiler and a code review. Gap 3's test must exist before this file is touched.

**Hazard 5 (silent): `SynchronizationQueue.getInstance()`'s return type and `enqueueEpisodePlayed`'s parameter.** Two separate decisions on the same file. (a) `private static SynchronizationQueue instance` (`:6`) has no initializer, so `getInstance()` can return `null` before `ClientConfigurator.java:53` runs; the honest Kotlin type is `SynchronizationQueue?`. All 22 Java call sites immediately dereference the result without a guard, so they NPE today in that window and would continue to — but declaring the getter nullable emits `@Nullable`, which is visible to SpotBugs (see the gate note below) even though javac ignores it. Declaring it non-null (`lateinit var`, or a `!!`-backed getter) changes the failure from `NullPointerException` at the call site to `UninitializedPropertyAccessException`/`IllegalStateException` inside the getter — a different exception type for the same broken state. Neither is a behaviour *improvement*; the planner should pick deliberately and record why. (b) `enqueueEpisodePlayed(FeedMedia media, boolean completed)` (`:35`) is called with a nullable argument at `DBWriter.java:878` (`item.getMedia()`, unguarded — the surrounding `if` checks `item.isPlayed()`, not media). Today, `SynchronizationQueueImpl.enqueueEpisodePlayed` (`net/sync/service/src/main/java/.../SynchronizationQueueImpl.java:111-118`) checks `SynchronizationSettings.isProviderConnected()` and **returns before touching `media`** — so for a user with sync not configured, a null media is a **benign no-op today**. If the parameter becomes non-null `FeedMedia`, Kotlin's `Intrinsics.checkNotNullParameter` fires in the abstract class's... actually in the *implementation*'s prologue only if the impl is also Kotlin; since `SynchronizationQueueImpl` stays Java, the check lands on nothing and the behaviour is unchanged. **But `SynchronizationQueueStub.enqueueEpisodePlayed` *is* in this module** and would gain the check — meaning the four other-module tests that install the stub would start crashing if any of them passes null. Worth verifying empirically rather than reasoning about; either way `media: FeedMedia?` is the faithful declaration. The other three `String` parameters (`enqueueFeedAdded`/`enqueueFeedRemoved`'s `downloadUrl`) are likewise fed `feed.getDownloadUrl()` — `String?` from `model/src/main/java/de/danoeh/antennapod/model/feed/Feed.kt:27` — at `DBWriter.java:193,705,873`, all unguarded.

**Hazard 6 (silent): `:model` is already Kotlin, and the whole nullability funnel is `EpisodeAction.Builder(FeedItem, Action)`.** `EpisodeAction.java:241-244`:
```java
public Builder(FeedItem item, Action action) {
    this(item.getFeed().getDownloadUrl(), item.getMedia().getDownloadUrl(), action);
    this.guid(item.getItemIdentifier());
}
```
Against Kotlin `:model`: `FeedItem.feed` is `Feed?` (`FeedItem.kt:56`), `FeedItem.media` is `FeedMedia?` (`FeedItem.kt:47`), `FeedItem.itemIdentifier` is `String?` (`FeedItem.kt:29`), `Feed.downloadUrl` is `String?` (`Feed.kt:27`), `FeedMedia.downloadUrl` is `String?` (`FeedMedia.kt:62`). Today javac erases all five and this compiles silently. After conversion the compiler forces four explicit decisions:
- `item.feed!!.downloadUrl` and `item.media!!.downloadUrl` — **`!!` is the equivalence-preserving choice**, because both chains NPE today when the link is null. A `?.` would silently substitute `null` and change shipping behaviour. Reachability differs per caller: `EpisodeMultiSelectActionHandler.java:109-111` and `:127-131` *do* guard `item.getMedia() != null` before building; `SyncService.java:236-240` guards media; `DBWriter.java:164` and `FeedDatabaseWriter.java:132` guard media (`:130`); `MediaDownloadedHandler.java:112` guards `item != null` but **not** `item.getMedia()`; `SynchronizationQueueImpl.java:122` passes `media.getItem()` after guarding it non-null at `:115`. So `item.getFeed()` is unguarded at every one of the seven sites, and `item.getMedia()` is unguarded at one. Preserving that asymmetry is correct; harmonising it is a behaviour change dressed as a cleanup.
- **The `podcast` and `episode` fields must be `String?`.** This is the subtle one. Both are assigned from `String?` sources via the `FeedItem` constructor, and `readFromJsonObject` also feeds them from `object.optString(..., null)` (`:56-57`). If J2K declares them non-null `String` (which it will, since there are no annotations), Kotlin inserts `Intrinsics` checks at the `Builder(String, String, Action)` constructor and **construction starts throwing where it currently succeeds** — `writeToJsonObject`'s `putOpt` (`:189-190`) exists precisely to tolerate nulls there. `getPodcast()`/`getEpisode()` must therefore return `String?`, which in turn emits `@Nullable` visible to `EpisodeActionFilter.java:25,58` (Java, so no compile break, but see the SpotBugs note).
- **`guid` must be `String?`** (`:239` has no initializer; `getGuid()` is fed to `GuidValidator.isValidGuid(String)` at `SyncService.java:277`, whose whole first clause is `guid != null` — `net/sync/service/src/main/java/.../GuidValidator.java:6`). Unambiguous.
- **`timestamp` must be `Date?`** (`:235` has no initializer; `EpisodeActionFilter.java:60,62,72-74` null-checks it four times, and `EpisodeActionFilterTest.java:191-196` proves the null state is live). Unambiguous — but see gap 2 for the `formatter.format(timestamp)` overload-resolution trap that follows from it.

**Hazard 7 (silent, low): `EpisodeAction.readFromJsonObject`'s return type and `org.json`'s platform types.** The return must be `EpisodeAction?` (three `return null` paths: `:60,66`, plus the implicit one). `JSONObject.optString(String, String)` is unannotated, so Kotlin sees `String!` and will *not* force a decision at `:56-58,69,79` — an asymmetry worth naming, because it is a place where the conversion silently does **not** surface a real null risk. `writeToJsonObject()` must likewise return `JSONObject?` (`:203`).

**Other conversion mechanics.**
- `EpisodeAction`'s `private EpisodeAction(Builder builder)` (`:37-46`) is a private constructor taking the builder — J2K handles this, but the resulting Kotlin will want to be a primary constructor with `val`s, which changes the field-init order. Keep the builder-arg form; the class is not a data class and must not become one (a `data class` would generate `equals`/`hashCode`/`toString`/`copy`, silently replacing three hand-written methods — including the defective `equals` — and adding a `copy()` to the public API).
- `EpisodeAction.Action` and `EpisodeAction.Builder` must stay nested (`enum class Action`, `class Builder`) — Kotlin nested classes are static-equivalent by default, so `new EpisodeAction.Builder(...)` from Java keeps working without `inner`.
- `SynchronizationProvider` becomes `enum class SynchronizationProvider(val identifier: String)`. `getIdentifier()` comes free from the `val`. `fromIdentifier` goes into a `companion object` with `@JvmStatic`. The `for (... : values())` loop (`:8-12`) idiomatically becomes `entries.firstOrNull { it.identifier == provider }` — equivalent, but note `values()` itself is still called from Java at `SynchronizationPreferencesFragment.java:165` and must remain available (it does, for enum classes).
- `SubscriptionChanges.toString()` (`:20-25`) lacks the `@NonNull` its sibling has; both become non-null `override fun toString(): String` regardless. `SubscriptionChanges`' `@NonNull List<String>` params (`:12-13`) become non-null `List<String>`, which is faithful — but note the only caller, `ResponseMapper.java:40`, passes freshly-built `LinkedList`s, so nothing exercises the annotation.
- `TextUtils.isEmpty(x)` at `EpisodeAction.java:59,70,80` is applied to `String?` values, so `x.isNullOrEmpty()` is exactly equivalent and is the KMP-portability-consistent swap per prior precedent in this repo. It does **not** remove the Robolectric requirement (`JSONObject` does that), and it does widen the diff against `AGENTS.md`'s minimal-diff rule. Recording as available, not recommended — planner's call.
- `androidx.annotation.NonNull` imports (`EpisodeAction.java:6`, `SubscriptionChanges.java:3`, `EpisodeActionChanges.java:4`) dissolve into Kotlin types; `build.gradle:14`'s `annotationProcessor libs.androidx.annotation` becomes inert for converted files.

### Unknowns

Questions the planner needs to resolve before ordering steps:

1. **Null-parameter policy for `SynchronizationProvider.fromIdentifier(String)`.** The equivalence-preserving answer is `provider: String?`, preserving today's `null → null` no-op that keeps `SyncService.doWork()` from crashing for every never-configured-sync user. The "obviously cleaner" non-null `String` is the wrong answer and the compiler will not object to it. Needs an explicit recorded decision, plus gap 3's test landed first.
2. **`EpisodeAction.equals`'s inverted `action != that.action` (`:161`) — pin, fix, or both?** Three options: (a) pin today's defective behaviour by test and convert faithfully — maximally equivalence-honest, but ships a knowingly-broken `equals` and a reviewer will read the test as endorsing it; (b) pin, convert faithfully, then fix in a clearly-separated follow-up commit or milestone; (c) fix as part of the conversion — which is a behaviour change inside an equivalence diff and would violate the track's contract. Recommended reading is (b), and note that nothing in the repo calls `equals`, so no test outside this module can detect either choice. This also interacts with the repo's unverifiable-equivalence policy and with `AGENTS.md`'s no-comments rule if a warning comment is the chosen mitigation.
3. **`SynchronizationQueue.getInstance()`'s return type: `SynchronizationQueue?`, or non-null via `lateinit`/`!!`?** Nullable is honest and matches the uninitialized-`static` reality, but emits `@Nullable` across 22 unguarded Java dereference sites and is the most plausible trigger for a new SpotBugs `NP_*` finding in `:app`, `:storage:database`, `:playback:service`, `:net:download:service` and `:ui:preferences`. Non-null changes the exception type thrown in the pre-`ClientConfigurator` window. Neither is a behaviour improvement; the decision should be recorded with its reasoning, and the SpotBugs consequence checked empirically **early** (a throwaway conversion of just `SynchronizationQueue.kt` run against `./gradlew lint` would answer it before any test-writing is sunk).
4. **How far to go on `EpisodeAction` JSON characterization, given it forces Robolectric into a module that has no test source set at all.** This is the biggest and highest-consequence gap (a dual wire/on-disk contract), and it is also the reason the module acquires its first-ever test dependency and its first-ever Robolectric dependency — a deviation from the `:model`/`:event` Robolectric-free precedent and from this repo's KMP-portability preference, neither of which can be honoured here because `org.json.JSONObject` is an Android-framework class. Is a full round-trip-plus-golden-JSON suite in scope, or is a subset acceptable? Deferring `EpisodeAction` itself to a later milestone (converting the other 8 files first, 221 LOC, mostly mechanical) is a legitimate answer and better than thin coverage of the riskiest file.
5. **Milestone shape: one PR or two?** The module is 514 LOC across 9 files, which argues for a single PR like `:event`'s Milestone 8. But 57% of the LOC and ~90% of the risk is in one file (`EpisodeAction.java`), and the characterization debt is total (zero existing tests) and front-loaded. A tests-first PR (new test source set + `EpisodeAction` JSON/equals/builder characterization + `fromIdentifier` nulls) followed by a conversion PR is the plausible alternative, and maps cleanly onto Unknown 4's deferral option.
6. **Does the `@Throws(SyncServiceException::class)` decision extend to a repo-wide convention?** This is the first module in the case study to convert a Java interface with checked exceptions crossing into Java implementors. Whether `@Throws` gets applied mechanically to all six `ISyncService` methods, or only where a Java `catch` actually requires it, should be decided once and recorded — the mechanical answer is safer and the narrow answer is smaller.
7. **Whether to take the `TextUtils.isEmpty` → `isNullOrEmpty()` swap in `EpisodeAction`** (`:59,70,80`). KMP-portability-consistent with prior precedent, but it does not remove Robolectric (JSONObject does that) and it widens the diff against `AGENTS.md`'s minimal-diff rule. Lower stakes than in Milestone 10, where the equivalent swap would have removed a whole module's `android.*` dependency.
8. **Whether to remove the three dead dependencies** (`:storage:preferences`, `libs.rxandroid`, `libs.rxjava` at `build.gradle:12,15,16`) while `build.gradle` is already being edited for the Kotlin plugins. Leaving them is the smaller diff; removing them is defensible cleanup with a real (if small) build-time benefit. One-line judgement call, not a risk. Worth confirming with a `./gradlew :net:sync:service-interface:dependencies` read before touching anything, since this research established non-use by grep alone.
9. **`SynchronizationQueueStub`'s parameter nullability, and whether it can regress other modules' tests.** The stub lives in this module and is installed by four Java tests in `:net:download:service` and `:storage:database`. If its `enqueueEpisodePlayed(FeedMedia, boolean)` gains a non-null `Intrinsics` check and any of those tests' code paths passes a null media, those suites break — which would be a *useful* signal, but the plan should anticipate it rather than treat it as a surprise. Needs an empirical check (run the four suites against a `media: FeedMedia` variant) rather than reasoning.

### Objective

**D0 — The two nullability rules this plan applies everywhere, stated once so every later decision is checkable against them.**

Milestone 10 made ~20 individual nullability calls and justified each in prose. This module's calls collapse onto two rules; naming them up front is what makes the reviewer's job mechanical rather than interpretive.

- **Rule N (non-null only where the first action already dereferences).** A reference parameter may be declared **non-null** if and only if the Java body dereferences it unconditionally as its first action — so Kotlin's `Intrinsics.checkNotNullParameter` throws `NullPointerException` at the same public entry point, for the same input, that Java already throws from. Everywhere else the parameter is **nullable**, because a non-null declaration would add a runtime check that does not exist today, at a site whose Java callers the compiler will not warn.
- **Rule A (honour a pre-existing `@NonNull`).** Where the Java source already carries `androidx.annotation.NonNull` on a parameter, the Kotlin type is non-null even if Rule N would say otherwise. This is the author's declared contract and Milestone 10's D4 precedent (`runOnceOrAsk(context: Context)`). It is a **disclosed narrowing**, recorded in AC15, not a silent one.

Rule N yields non-null at exactly two sites: `EpisodeAction.readFromJsonObject(jsonObject: JSONObject)` (`EpisodeAction.java:56` dereferences immediately) and the **`item` parameter only** of `EpisodeAction.Builder(item: FeedItem, action: Action?)` (`:242` evaluates `item.getFeed()` as its first bytecode). Note that this is a *per-parameter* rule, not a per-signature one: the `action` parameter sitting beside that non-null `item`, in the same constructor, is nullable — it is never dereferenced, only forwarded. D9 states both `Builder` overloads' `action` type explicitly, because this is the one place in the module where two parameters of one signature land on opposite sides of Rule N. Rule A yields non-null at exactly three: `SubscriptionChanges`' two `List<String>` params and `EpisodeActionChanges`' `List<EpisodeAction>` param. **Every other reference parameter in the module is nullable.** Any deviation is a review finding.

**D1 — `SynchronizationProvider.fromIdentifier(provider: String?): SynchronizationProvider?`. Non-negotiable; the parameter is the dangerous half.** (Unknown 1; research's headline silent hazard.)

Both halves are nullable. The return type is forced by `return null` at `SynchronizationProvider.java:13`. The **parameter** is the one that ships a crash if it is wrong, and Rule N says nullable: the Java body never dereferences `provider` — it calls `synchronizationProvider.getIdentifier().equals(provider)` (`:9`), where the receiver is the non-null enum constant's identifier and `provider` is only ever an argument to `String.equals`, which returns `false` for null. So `fromIdentifier(null)` returns `null` today, by construction and not by accident.

That null return is load-bearing on a hot path. `SyncService.doWork()` calls `getActiveSyncProvider()` as its first statement; that calls `fromIdentifier(SynchronizationSettings.getSelectedSyncProviderKey())` (`SyncService.java:352-354`); and `getSelectedSyncProviderKey()` is `prefs.getString(SELECTED_SYNC_PROVIDER, null)` (`SynchronizationSettings.java:44-46`) — **genuinely null for every user who has never configured sync**, on every invocation of the sync worker. Today `selectedService == null` returns `null` and `doWork()` no-ops. J2K's natural output is `fun fromIdentifier(provider: String): SynchronizationProvider?` (there is no `@Nullable` to tell it otherwise), which emits `Intrinsics.checkNotNullParameter` and turns that no-op into a hard crash inside a `Worker` for the entire never-configured-sync population. The caller is Java, so **javac will not warn, and the seven-module compile stays green**. This is the direct analogue of Milestone 10's `isDownloadingEpisode(null)` finding.

Body: `entries.firstOrNull { it.identifier == provider }` in a `companion object`, with `@JvmStatic`. This is equivalent rather than merely similar: `identifier` is non-null for both constants, Kotlin's `==` on `String` is null-safe structural equality, and `firstOrNull` preserves declaration order, so the result is identical to the Java loop for every input including `null`. `entries` (Kotlin 1.9+; the repo is on 2.3.20) replaces `values()`, but `values()` itself remains callable from Java — enum classes always emit it — which `SynchronizationPreferencesFragment.java:165` requires.

`getIdentifier()` comes free from `enum class SynchronizationProvider(val identifier: String)`. Its exact return strings `"GPODDER_NET"` / `"NEXTCLOUD_GPODDER"` are an **on-disk contract** (persisted by `SynchronizationSettings.setSelectedSyncProvider` from `GpodderAuthenticationFragment.java:256` and `NextcloudAuthenticationFragment.java:93`), and constant **declaration order** is a UI contract (`SynchronizationPreferencesFragment.java:165` builds a list from `values()` and `:186` indexes it by position). Both are pinned by test in Step 1.

**`AGENTS.md`'s no-reordering rule cannot be honoured literally here, and that is not a finding.** `SynchronizationProvider.java` declares `fromIdentifier` *before* the `identifier` field and constructor (`:7-20`). Kotlin requires enum constants first and puts the constructor in the class header, so the only legal shape is: header → constants → `companion object { fromIdentifier }`. Recorded so a reviewer reads the reordering as forced, not as tidying.

**D2 — `EpisodeAction`'s four static `Action` aliases become `@JvmField val` in the companion. `const val` is unavailable and a plain `val` breaks six call sites in five modules.**

`public static final Action NEW = Action.NEW;` and its three siblings (`EpisodeAction.java:23-26`) are read as `EpisodeAction.DOWNLOAD` / `PLAY` / `NEW` / `DELETE` from `MediaDownloadedHandler.java:114`, `SynchronizationQueueImpl.java:122`, `SyncService.java:240`, `EpisodeMultiSelectActionHandler.java:111,131`, `DBWriter.java:164` and `FeedDatabaseWriter.java:132`. Their type is an enum, **not** a primitive or `String`, so `const val` — Milestone 10's answer for its five `WORK_*` constants — does not apply. `@JvmField val NEW = Action.NEW` inside `companion object` emits a genuine `public static final Action NEW` **on the outer class**, which is the only drop-in. **D3 — `UploadChangesResponse.timestamp` must be `@JvmField`, and this is the module's sharpest compile-time item.** (Research hazard 1.)

`abstract class UploadChangesResponse(@JvmField val timestamp: Long)`, KDoc preserved on the property.

The field is read three ways: qualified from `:net:sync:service` (`SyncService.java:208` `newTimeStamp = uploadResponse.timestamp;` and `:255`), **unqualified via Java field inheritance from inside the Java subclass** `GpodnetUploadChangesResponse.java:48` (`"timestamp=" + timestamp` — verified by reading the file, not inferred), and reflectively by `GpodnetEpisodeActionPostResponse.java:46`'s `ToStringBuilder.reflectionToString(this, …)`, which walks inherited fields. J2K's default for a `public final long` field on an abstract class with a `(long)` constructor is a constructor `val`, which emits a **private** backing field plus `getTimestamp()` — breaking the first two sites at compile time and silently changing the third's output. `@JvmField val` emits a real `public final long timestamp` with no accessor, which is byte-for-byte the Java shape.

There is a **third** subclass research did not enumerate: `NextcloudSyncService.java:160`, a `private static class NextcloudGpodderEpisodeActionPostResponse extends UploadChangesResponse`. It only calls `super(epochSecond)`, so it adds no new constraint, but it means three Java classes — not two — depend on this abstract class staying Java-subclassable with a public `(long)` constructor.

Fallback if `@JvmField` is rejected on a constructor property for any reason: declare it as a body property `@JvmField val timestamp: Long` initialised from a plain constructor parameter. Any fallback used must be recorded.

**D4 — `@Throws(SyncServiceException::class)` goes on all six `ISyncService` methods, mechanically, with no reachability analysis. This becomes the case study's standing convention.** (Unknown 6; research hazard 2 — no Milestone 10 analogue.)

Kotlin has no checked exceptions and emits no `throws` clause. All six Java declarations carry `throws SyncServiceException` (`ISyncService.java:7-19`), and the consequences of omitting `@Throws` are compile errors in a *different* module, in both directions:

- **Implementor side.** `GpodnetService` and `NextcloudSyncService` declare `throws` on their overrides — and `NextcloudSyncService` narrows to `throws NextcloudSynchronizationServiceException` (`:104,114`). A Java override may not declare a checked exception the overridden method does not, so without `@Throws` every one of those overrides becomes an error.
- **Caller side.** `SyncService.java:209` has `catch (SyncServiceException exception)` around a call made through the interface type, and `:144,219` re-declare `throws SyncServiceException`. Without `@Throws` the `catch` becomes an unreachable-catch compile error.

The mechanical rule is chosen over a narrow "only where a Java `catch` requires it" rule for three reasons: all six Java declarations are uniform, so mechanical *is* the faithful transcription; a narrow rule requires a reachability analysis that must be redone every time a caller changes; and a missing `@Throws` is only loud today because the implementors happen to be Java — the day one becomes Kotlin, the signal disappears. **Standing convention for this case study: transcribe every `throws` clause on a converted Java signature as `@Throws`, unconditionally.** Applies equally to any future module; recorded in the module README (Step 13) and in future-work item 11.

`SyncServiceException` itself needs no `@Throws` (it is the exception type, not a thrower) — see D6.

`ISyncService`'s reference parameters and return types are declared **non-null**. This is documentation-only and provably JVM-inert: a Kotlin interface with no default bodies emits no `Intrinsics` call anywhere, and the two Java implementors synthesize none. Both implementors iterate the lists unconditionally, so null was never a supported input. AC13 asserts the inertness rather than assuming it.

**D5 — `@JvmSuppressWildcards` on the two `List`-taking `ISyncService` methods. Without it, Step 7 breaks the build in another module — and the failure is invisible in this file.** (New finding; not in research.)

Kotlin's `List<E>` is declared `List<out E>`, so a `List<T>` **parameter** emits the generic signature `java.util.List<? extends T>` whenever `T` is non-final. `uploadEpisodeActions(queuedEpisodeActions: List<EpisodeAction>)` is therefore compiled to `List<? extends EpisodeAction>` for as long as `EpisodeAction` is a non-final **Java** class — which is exactly the state of the world at Step 7, five steps before `EpisodeAction` is converted. A Java override declaring `uploadEpisodeActions(List<EpisodeAction>)` is then not override-equivalent, and javac rejects both implementors with "same erasure, yet neither overrides the other".

This is loud rather than silent, but it would stall the implementation mid-run on a symptom that points at `:net:sync:gpoddernet` (out of File Scope) rather than at the file actually responsible. It also resolves itself invisibly at Step 12 when `EpisodeAction` becomes a final Kotlin class, which is a worse outcome than fixing it: the plan would be relying on an undocumented coupling between one file's finality and another file's binary signature.

So: `@JvmSuppressWildcards` at **function level** on `uploadSubscriptionChanges` and `uploadEpisodeActions`. Function level (not class level) because it is an unambiguously valid annotation target. `uploadSubscriptionChanges`' `List<String>` needs it only for uniformity — `String` is final, so no wildcard is generated either way — and stating that explicitly is cheaper than leaving a reviewer to wonder why one of the two is annotated.

Two consequences to note and **not** fix:
- `EpisodeActionChanges(episodeActions: List<EpisodeAction>)` is left unannotated. Its generic signature *does* change between Step 9 (`List<? extends EpisodeAction>`) and Step 12 (`List<EpisodeAction>`), but constructors are never overridden and its only caller, `ResponseMapper.java:57`, passes a `List<EpisodeAction>` which is assignable to both. Harmless; recorded so the signature change is not read as a regression.
- Return types never get wildcards, so `getEpisodeActions(): List<EpisodeAction>` and `getAdded()`/`getRemoved(): List<String>` need nothing.

**Machine-checked (AC12):** `javap -s` on `ISyncService` shows no `? extends` in any of the six generic signatures.

**D6 — `SyncServiceException` must be `open`, and `serialVersionUID` must be a `private const val` in a companion. The `open` is preservation, not widening.**

```kotlin
open class SyncServiceException : Exception {
    constructor(message: String?) : super(message)
    constructor(cause: Throwable?) : super(cause)

    companion object {
        private const val serialVersionUID = 1L
    }
}
```

Kotlin classes are final by default, so without `open` the two Java subclasses — `GpodnetServiceException.java:5` and `NextcloudSynchronizationServiceException.java:5` — fail to compile. This is the one `open` modifier authorised anywhere in this plan: it preserves subclassability that Java already had, and is therefore not the unrequested API widening the `:event` D19 rule forbids. Every other converted class stays final (see D8's finality inventory).

Constructor parameters are nullable per Rule N (`super(message)` does not dereference), which also keeps `SyncServiceException(null)` constructible exactly as today.

`serialVersionUID` (`:4`) must still emit a `static final long` **on `SyncServiceException` itself**, because both Java subclasses carry their own and serialization compatibility across the hierarchy is observable. A plain `val` emits an instance field and a getter, which is wrong in three ways at once. `private const val` in a `companion object` is expected to emit `private static final long serialVersionUID` on the outer class.

**D8 — `EpisodeAction`'s structure: a private 8-argument primary constructor, private Builder fields, nested types stay nested, and it is emphatically not a `data class`.**

Four structural decisions, only one of which J2K gets right unaided.

**(a) The private constructor takes the eight values, not the `Builder`.** In Kotlin, an outer class **cannot** access a nested class's `private` members — the reverse of Java, which permits it. Transcribing `private EpisodeAction(Builder builder)` (`:37-46`) literally would force `Builder`'s eight fields to `internal`, which emits name-mangled accessors and widens `Builder`'s JVM surface for no reason. So:

```kotlin
class EpisodeAction private constructor(
    val podcast: String?, val episode: String?, val guid: String?, val action: Action?,
    val timestamp: Date?, val started: Int, val position: Int, val total: Int,
)
```

with `Builder.build()` = `EpisodeAction(podcast, episode, guid, action, timestamp, started, position, total)` and `Builder`'s fields staying `private`, exactly as Java has them. The constructor's arity changes but it is **private in both versions**, so it is invisible to every Java caller; assignment order is identical and no initializer has a side effect. `val` properties emit private backing fields plus public getters — byte-for-byte the Java field/getter split, including `getStarted()`/`getPosition()`/`getTotal()` and their KDoc.

**(b) Not a `data class`, and not open.** A `data class` would generate `equals`/`hashCode`/`toString` — silently replacing three hand-written methods, including the defective `equals` D10 exists to preserve — and add `copy()` to the public API. Forbidden, and grepped for in AC13. `EpisodeAction` stays **final**: nothing subclasses it (verified by grep), and its finality is what makes D5's wildcard question terminate.

**(c) `Action` and `Builder` stay nested.** `enum class Action` and `class Builder` keep the `EpisodeAction$Action` / `EpisodeAction$Builder` JVM names that `EpisodeActionFilterTest.java` (20 sites) and seven production `new EpisodeAction.Builder(...)` sites need. Kotlin nested classes are static-equivalent by default, so no `inner`, and neither may be promoted to a top-level type.

**(d) One authorised rename.** `readFromJsonObject`'s parameter is named `object` in Java, which is a Kotlin keyword; it becomes `jsonObject`. Parameter names are not part of the JVM contract for Java callers, and this is the **only** rename authorised anywhere in this plan. It must be recorded in Implementation Notes.

Finality inventory, verified by repo-wide grep and stated so the reviewer does not have to re-derive it: `SyncServiceException` → `open` (2 Java subclasses, D6). `SynchronizationQueue`, `UploadChangesResponse` → `abstract`, hence open (1 and 3 Java subclasses). `EpisodeAction`, `EpisodeAction.Builder`, `SynchronizationQueueStub`, `SubscriptionChanges`, `EpisodeActionChanges` → **final**, zero subclasses each. No other `open` is permitted; AC13 greps for it.

**D9 — `EpisodeAction`'s nullability map, the exhaustive three-`!!` inventory, and the one overload-resolution trap that changes the exception type.**

Every reference-typed member is nullable, and each is forced rather than chosen:

| Member | Type | Forced by |
|---|---|---|
| `podcast`, `episode` | `String?` | `optString("podcast", null)` (`:56-57`) returns null, and `writeToJsonObject`'s `putOpt` (`:189-190`) exists precisely to tolerate it. A non-null declaration would make `Builder(String, String, Action)` throw where it currently succeeds. |
| `guid` | `String?` | no initializer (`:239`); `GuidValidator.isValidGuid`'s first clause is `guid != null` (`GuidValidator.java:6`) |

| `timestamp` | `Date?` | no initializer (`:235`); `EpisodeActionFilter.java:60,62,72-74` null-checks it four times and `EpisodeActionFilterTest.java:191-196` proves the null state is live |

| `writeToJsonObject` return | `JSONObject?` | `return null` on `JSONException` (`:203`); `SynchronizationQueueStorage.java:164` passes it straight to `JSONArray.put` unguarded |

**Both public `Builder` constructors take `action: Action?`, and this is stated here rather than left to be inferred from the table above** — because Rule N is applied per declaration site, and so is J2K's nullability inference, which does not reason across sibling overloads. `Builder(podcast: String?, episode: String?, action: Action?)` (`:246-250`) only assigns its three parameters. `Builder(item: FeedItem, action: Action?)` (`:241-244`) only *forwards* `action` — to that sibling constructor, and thence to the private primary constructor — so neither body ever dereferences it, and Rule N yields nullable at both. Note the asymmetry inside the `FeedItem` overload's own signature: `item` **is** non-null (Rule N: `:242` evaluates `item.getFeed()` as its first bytecode, per D0), while `action` beside it is not.

That overload is the trap of the two. It is the one all seven production call sites use, and a developer taking raw J2K output could plausibly land on `action: Action` here while correctly getting `Action?` for the sibling — because only the sibling has a test forcing the correction. Both declarations compile cleanly, and every production caller passes a static `Action` constant, so nothing in the seven-module build would reach the difference: a non-null declaration would simply add an `Intrinsics.checkNotNullParameter` at a public constructor that Java callers can reach and javac will not warn about. Same class of silent narrowing as D1, D7(b) and D7(c), and pinned the same way — by `builderStringConstructorAcceptsNullAction` **and** `builderFeedItemConstructorAcceptsNullAction`, one per overload (Step 4, AC4). Either test missing leaves its overload unguarded.

Exactly **three** `!!` are permitted in the entire module, all in `EpisodeAction.kt`. The table is the authority; any `!!` not on it is a review finding, and a count of two is equally a finding.

| # | Expression | Why faithful | Pinned by (discriminating) |
|---|---|---|---|
| 1 | `item.feed!!.downloadUrl` in `Builder(FeedItem, Action)` | `FeedItem.feed` is `Feed?` (`FeedItem.kt:56`); `item.getFeed().getDownloadUrl()` NPEs today at all seven production call sites, none of which guards `getFeed()` | `builderFeedItemConstructorWithNullFeedThrowsNullPointerException` — **fully discriminating**: `?.` would yield `podcast = null` and construction would complete, because the fixture's `media` is non-null |
| 2 | `item.media!!.downloadUrl` in the same constructor | `FeedItem.media` is `FeedMedia?` (`FeedItem.kt:47`); unguarded at `MediaDownloadedHandler.java:112` (which guards only `item != null`) | `builderFeedItemConstructorWithNullMediaThrowsNullPointerException` — **fully discriminating**, and its fixture **must** have a non-null `feed` with a non-null `downloadUrl`, because Java evaluates `item.getFeed().getDownloadUrl()` first (`:242`) and an imprecise fixture would prove row 1 twice and row 2 never |
| 3 | `action!!.name.lowercase(Locale.US)` in `getActionString()` | `this.action.name()` (`:114`) is unguarded and NPEs for a null action; the surrounding `try` catches only `JSONException`, so it propagates out of `writeToJsonObject` | `writeToJsonObjectWithNullActionThrowsNullPointerException` — **fully discriminating**: any `?.`/`orEmpty` softening writes an `"action"` value and returns a `JSONObject` |

**The overload-resolution trap at `writeToJsonObject` (`:195`), which is a genuine behaviour fork and is fully test-detectable.** `formatter.format(this.timestamp)` with a null `timestamp`: javac binds `DateFormat.format(Date)`, which reaches `Calendar.setTime(null)` and throws `NullPointerException`. In Kotlin, `timestamp` is `Date?` and **two** overloads are applicable — `DateFormat.format(Date!)` and `Format.format(Any!)` — because platform-typed parameters accept nullable arguments. Kotlin should pick the more specific `format(Date)`, matching Java. If it instead binds `format(Any)`, `SimpleDateFormat.format(Object, StringBuffer, FieldPosition)` throws **`IllegalArgumentException("Cannot format given Object as a Date")`**, a different exception class escaping the same public method.

So the expression is transcribed verbatim as `formatter.format(this.timestamp)` and the resolution is checked two ways: behaviourally by `writeToJsonObjectWithNullTimestampThrowsNullPointerException` (Step 3), which asserts `NullPointerException` specifically and therefore fails on `IllegalArgumentException`; and mechanically by `javap -c` (AC12), which must show `invokevirtual java/text/DateFormat.format:(Ljava/util/Date;)Ljava/lang/String;`. **Fallback if it resolves to `format(Object)`:** write `formatter.format(this.timestamp!!)`, which is observably equivalent (`!!` throws `NullPointerException` from the same public call, and no characterization test inspects stack traces or messages) and raises the module's `!!` count to four — a change that must be recorded in Implementation Notes and reflected in AC13's count.

**Forbidden softenings, none of which any compiler will catch:** `?: ""`, `.orEmpty()`, `?.let`, `putOpt` in place of `put`, or any guard around `formatter.format`. **Forbidden idiom swaps:** dropping the explicit locale from `.lowercase(Locale.US)` / `.uppercase(Locale.US)` (Kotlin's no-arg forms use `Locale.ROOT`, Java's no-arg forms use the default locale — neither is what the source says, and both silently change what gets written to the wire and to disk); and unifying `PATTERN_ISO_DATEFORMAT` (`:22`, used at `:72`) with the identical literal re-typed inline at `:193`. They are equal today; both are pinned by golden-string tests in Step 3, and merging them is a diff-widening cleanup `AGENTS.md` forbids.

**Permitted, because provably behaviour-neutral:** `hashCode()`'s five `x != null ? x.hashCode() : 0` ternaries become `x?.hashCode() ?: 0`. This is a faithful transcription of an explicit Java ternary, **not** an instance of the banned `?: ""` fallback pattern, and the distinction is stated here so a reviewer greping for `?:` does not misfile it. `toString()` becomes a string template that must render byte-identically, including `null` for null fields — pinned by two golden-string tests. Platform types from `org.json` (`optString(String, String)` is unannotated, so Kotlin sees `String!`) need **no** `!!` at `:56-58,69,79`; that is an asymmetry worth naming, because it is a place where the conversion silently does *not* surface a real null risk.

**D10 — `EpisodeAction.equals`'s inverted `action != that.action` is pinned, not fixed. The fix is not in this PR at all, and the warning lives in docs and test names rather than in a code comment.** (Unknown 2.)

**D11 — `EpisodeAction`'s JSON contract gets full characterization: round-trip plus golden strings in both directions. It is not deferred and it is not partially covered.** (Unknown 4, first half.)

**D17 — `SubscriptionChanges` and `EpisodeActionChanges`: honour the `@NonNull`s, transcribe both misleading `toString()` formats verbatim.**

Per Rule A, `SubscriptionChanges(added: List<String>, removed: List<String>, timestamp: Long)` and `EpisodeActionChanges(episodeActions: List<EpisodeAction>, timestamp: Long)` take non-null lists, honouring `SubscriptionChanges.java:12-13` and `EpisodeActionChanges.java:13`. Rule N would say nullable (the bodies only assign), so the conflict is resolved explicitly in favour of the author's declared contract, matching Milestone 10's D4. It is a **disclosed narrowing**: today a null list constructs fine and NPEs later inside `toString()`; afterwards the constructor throws `NullPointerException` immediately. The only caller is `ResponseMapper.java:40,57`, which passes freshly built `LinkedList`s, so nothing exercises it either way. Element nullability is *not* runtime-enforced by Kotlin, so `List<EpisodeAction>` is documentation only — which matters because `SynchronizationQueueStorage.getQueuedEpisodeActions()` can produce a list containing nulls; that list never reaches `EpisodeActionChanges`, and no per-element check is generated regardless.

Both `toString()` implementations are transcribed **byte-identically, including their misleading names**: `SubscriptionChanges` renders `"SubscriptionChange [added=…, removed=…, timestamp=…]"` (singular "Change", spaced brackets) and `EpisodeActionChanges` renders `"EpisodeActionGetResponse{…}"` (a name that does not match the class). Both reach `Log.d` in production (`SyncService.java:154,252-253`). Correcting either is a diff-widening cleanup; both are pinned by golden-string tests in Step 5. `SubscriptionChanges.toString()` lacks the `@NonNull` its sibling has; both become `override fun toString(): String` with a non-null return regardless, which is faithful in both cases.
