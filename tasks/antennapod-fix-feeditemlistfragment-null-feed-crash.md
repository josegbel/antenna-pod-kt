# antennapod-fix-feeditemlistfragment-null-feed-crash

> **Description:** Fix a pre-existing, ~50%-flaky production crash in `app/src/main/java/de/danoeh/antennapod/ui/screen/feed/FeedItemlistFragment.java:659`, which dereferences the `@Nullable` return of `DBReader.getFeed(...)` on an RxJava computation thread without a null check. When the feed has been deleted/cleared out from under a still-alive fragment (e.g. by a sibling test's `@Before` clearing the DB in `androidTest`, or analogously by real navigation-away-then-DB-change races in production), the resulting `NullPointerException` becomes RxJava-undeliverable on a disposed subscriber and crashes the whole app process. Discovered via a controlled 7-attempt CI comparison while researching a sibling task (`antennapod-fix-httpdownloadertest-null-bundle-argument`).
> **Repo:** `services/android-migration/projects/portfolio/antennapod`
> **Created:** 2026-08-13

> - **Why this exists.** While researching `tasks/antennapod-fix-httpdownloadertest-null-bundle-argument.md` (a different bug in the same CI run), `legacy-android-researcher` found that CI run `31694690838` executed the same commit 7 times (3 emulator API levels × up to 3 retries in `.github/workflows/runEmulatorTests.sh:12`). `de.test.antennapod.ui.DownloadLogTest.testExistingNonSubscribedFeed` passed in 4 of 7 attempts and failed in 3, with an `NullPointerException: Attempt to invoke virtual method 'long ...Feed.getId()' on a null object reference` — API 36's two clean attempts (69/69 tests completed both times, no crash) definitively rule out this being caused by the *other* bug in that CI run (`HttpDownloaderTest`'s unrelated null-Bundle crash, tracked in the sibling task above); this is an independent, standalone defect.

The dereference at `:659` has no null guard. This is not "test-only debt."

## Research
_Last updated by: legacy-android-researcher | 2026-08-14_

### Summary

The target is one method, `loadItems()`, in `app/src/main/java/de/danoeh/antennapod/ui/screen/feed/FeedItemlistFragment.java` (775 lines, plain Java, `Fragment` + EventBus + RxJava3, no ViewModel). Line 659 dereferences the `@Nullable` return of `DBReader.getFeed(...)` twice (`feed.getId()`, `feed.getItemFilter()`) with no guard, inside an `Observable.fromCallable` body running on `Schedulers.computation()`. This is not a migration artifact of any kind: `git blame` puts lines 656-661 on `f3bca9d9e4` (ByteHamster, **2024-04-13**), long predating every AEPM migration milestone, and nothing in the NPE's path touches migrated Kotlin. It is upstream AntennaPod debt, and it is still present on upstream `develop`.

The pre-research diagnosis is **confirmed in its mechanism and refuted in one important detail, with a second correction to its severity claim.** Confirmed: `DBReader.getFeed` is genuinely `@Nullable` by design, the dereference is unguarded, the failure lands on a computation thread, and the crash requires the subscriber to have been disposed. **Refuted:** the diagnosis said "there is genuinely no `onError` handler that would catch this" — there is one, at `:676-683`, and it handles the null-feed case correctly and gracefully. The crash is therefore *not* "an unhandled error"; it is specifically the **disposed-subscriber** branch of `ObservableFromCallable`, which bypasses that handler. **Corrected severity:** the app installs a global RxJava error handler (`RxJavaErrorHandlerSetup.java:16-36`, wired in `PodcastApp.java:19`) that swallows this exact class of exception — *except* under `if (BuildConfig.DEBUG)` (`:31-34`), where it deliberately rethrows onto the current thread's uncaught handler. So **the hard process crash is debug-build-only**; a release build logs it, writes `crash-report.log`, and continues. The pre-research statement that this is "a genuine crash risk in the shipped app" needs softening — but the defect is still real in release, where it silently manufactures a spurious crash report that AntennaPod surfaces to users in its own Bug Report screen.

### Findings

#### Existing surface

`FeedItemlistFragment` renders one feed's episode list. Relevant surface for this defect:

- Fields: `feedID` (from `ARGUMENT_FEED_ID`, `:126`), `feed` (mutable, written from a background thread at `:658` and read on the main thread), `disposable` (single, shared by `loadItems()` and `loadMoreItems()`), `adapter`, `viewBinding`.
- `loadItems()` (`:652-684`) — the defect site. Disposes any prior subscription (`:653-655`), builds `Observable.fromCallable` (`:656-661`), `subscribeOn(Schedulers.computation())` (`:662`), `observeOn(AndroidSchedulers.mainThread())` (`:663`), subscribes with a success consumer (`:665-675`) and an error consumer (`:676-683`).
- `loadMoreData(int)` (`:230-233`) — **calls the same `DBReader.getFeed` and guards it**: `return feed != null ? feed.getItems() : Collections.emptyList();`. Same file, same class, ~430 lines above the bug.
- `loadMoreItems()` (`:686-716`) — separate RxJava chain; `:701` dereferences the `feed` *field* unguarded (see Unknowns).
- `showErrorDetails()` (`:598-614`) — uses `Maybe.fromCallable` returning `null` to mean "nothing to show", routed to an `onComplete` handler at `:613`. An in-file precedent for the idiom discussed under "Cleanest fix point".
- EventBus registration at `:191` (`onCreateView`), unregistration + `disposable.dispose()` at `:259-262` (`onDestroyView`).
- `RemoveFeedDialogClose` (`:341-357`) — overrides `onRemoveButtonPressed()` to navigate away *before* deleting, with the comment "Make sure fragment is hidden before actually starting to delete". Evidence the authors already knew about this hazard on the in-app delete path and mitigated it there by navigation, not by a guard.

#### Java/Kotlin interop boundary

Not a Java/Kotlin boundary issue at all — this is Java calling Java. `DBReader.java` is Java, `FeedItemlistFragment.java` is Java, and `androidx.annotation.Nullable` (`DBReader.java:7`) is a source-retention annotation javac does not enforce. `Feed.getId()` is migrated Kotlin (`Feed.kt`), but the NPE is on the *receiver*, not a Kotlin intrinsic — the log line is `Attempt to invoke virtual method ... on a null object reference`, an ART NPE, not `Intrinsics.checkNotNullParameter`. **No AEPM migration milestone caused or contributed to this.** It should not be framed as migration fallout in the case study.

The one place a callers-outside-the-module concern arises: `loadItems()` is `private`, so the blast radius of a change to it is confined to this file.

#### Verification 1 — is `DBReader.getFeed`'s `@Nullable` genuine, or should the declaration change?

**Genuine. Do not touch the declaration.** Weighed the same way the sibling SpotBugs tasks weighed "fix the caller vs. tighten/loosen the declaration":

- The Javadoc states the contract explicitly (`DBReader.java:321-328`): "@return The Feed or null if the Feed could not be found."
- The implementation makes "not found" a first-class, non-exceptional outcome: `feed` is initialised to `null` (`:334`), populated only inside `if (cursor.moveToNext())` (`:336-345`), and the `else` branch merely logs (`:346-348`). Returning null for a nonexistent row is correct, not a bug.
- Tightening it to `@NonNull` would require choosing an alternative for "feed deleted", and every option is worse: throwing would convert 9 currently-correct guarded call sites into new crash sites; returning an empty `Feed` would silently corrupt callers that persist what they read.
- **Nine of fifteen production call sites already guard it**, so the contract is load-bearing across the repo, not vestigial.

#### Verification 2 — the exact crash mechanism (prior diagnosis partially incorrect)

RxJava 3.1.5 (`gradle/libs.versions.toml:68`). `ObservableFromCallable.subscribeActual` wraps `callable.call()` in a try/catch and branches on disposal: if **not** disposed it calls `observer.onError(ex)`; if **disposed** it calls `RxJavaPlugins.onError(ex)` with the **raw, unwrapped** `NullPointerException`. The CI stack trace confirms this frame exactly (`ObservableFromCallable.subscribeActual(ObservableFromCallable.java:46)`), and confirms the crash surfaced on a `ScheduledThreadPoolExecutor` worker — i.e. a computation thread, not the main thread.

So there are four distinct outcomes, and only one of them crashes:

| Build | Subscriber state when the NPE is thrown | Outcome |
|---|---|---|
| debug | **disposed** | `RxJavaPlugins.onError(raw NPE)` → not an `UndeliverableException` → falls past the swallow at `RxJavaErrorHandlerSetup.java:18-22` → `BuildConfig.DEBUG` rethrow at `:31-34` → **process crash** ← what CI observes |
| debug | live | `observer.onError` → `observeOn` main → error consumer `:676-683` → empty state, logged. No crash. |
| release | **disposed** | Logged + `CrashReportWriter.write(exception)` (`:28-29`), swallowed. No crash — but a spurious `crash-report.log` is written. |
| release | live | Same graceful empty state as above. No crash. |

Two consequences the planner must not miss:

1. **The prior diagnosis's claim that there is no `onError` handler is wrong.** The handler at `:676-683` sets `feed = null`, calls `refreshHeaderView()` (which early-returns on null, `:497-500`), clears the adapter, and calls `updateToolbar()` (which early-returns on null, `:273-275`). The null-feed case is *already handled correctly* whenever the subscriber is alive. This is why the flake is intermittent rather than deterministic: the null return is common, the disposal race is not.
2. **`RxJavaErrorHandlerSetup`'s comment already anticipates this exact bug** (`:24-27`: "If an undeliverable exception is a NPE ... wrapping does not happen. AntennaPod threads might throw NPEs after disposing ... Just swallow all exceptions here."). The upstream design intent is to swallow; the `BuildConfig.DEBUG` rethrow is a deliberate developer-facing tripwire, and it is doing its job. **Do not "fix" this by weakening `RxJavaErrorHandlerSetup`** — that would suppress the symptom and blind every future instance of this class of bug.

#### Verification 3 — what disposes the subscriber

Two disposal sources, both inside this file:
- `onDestroyView()` → `disposable.dispose()` (`:260-262`) — fires during fragment/activity teardown.
- `loadItems()`/`loadMoreItems()` re-entry → `disposable.dispose()` (`:653-655`, `:687-689`) — each new load disposes the previous one.

Disposal *before* the worker starts is harmless: `subscribeActual` early-returns at its `d.isDisposed()` check and never invokes the callable. The NPE only escapes if disposal lands **during** `callable.call()`. That window is wider than it looks, because `DBReader.getFeed` and `DBReader.getFeedEpisodeCount` are both `static synchronized` on `DBReader` (`DBReader.java:330`, `:250`), so every DB read in the process serialises on one monitor and an in-flight callable can sit blocked there for a long time. (`PodDBAdapter.open()`/`close()` are no-ops — `PodDBAdapter.java:398-406` — so they contribute no additional locking.)

Note also `git blame` line `:662`: `97416e0458` (Hans-Peter Lehmann, 2026-03-30, "Move database calls from Schedulers.io to Schedulers.computation (#8374)") changed this chain from `Schedulers.io()` (unbounded elastic pool) to `Schedulers.computation()` (bounded to CPU count). That plausibly widens the queue-and-block window and so the race window. **Stated as a hypothesis, not a finding** — I have no before/after flake-rate data, and I am not proposing to revert it.

#### Verification 4 — what re-triggers `loadItems()`

`loadItems()` has exactly one non-EventBus caller and five EventBus-driven ones. After `onCreateView`, **every** re-trigger is an EventBus event:

| Trigger | Line | Relevance guard? |
|---|---|---|
| `onCreateView()` | `:197` | n/a |
| `onEvent(FeedEvent)` | `:396-398` | yes — `event.feedId == feedID` |
| `onEventMainThread(FeedItemEvent)` → `updateUi()` | `:404-406`, `:419-421` | partial |
| `onQueueChanged(QueueEvent)` → `updateUi()` | `:451-454` | **none** — unconditional |
| `onPlayerStatusChanged(PlayerStatusEvent)` → `updateUi()` | `:475-478` | **none** — unconditional |
| `onFeedListChanged(FeedListUpdateEvent)` → `updateUi()` | `:480-485` | yes — `feed != null && event.contains(feed)` |

`updateUi()` (`:471-473`) is a bare alias for `loadItems()`. Neither `onQueueChanged` nor `onPlayerStatusChanged` checks visibility, `isAdded()`, or whether the event concerns this feed. `PlayerStatusEvent` fires on every playback state change; `QueueEvent` on every queue mutation. Both are high-frequency.

**A guard placed inside `loadItems()` therefore covers all six entry points uniformly** — which answers the blast-radius question in the affirmative.

#### Verification 5 — is this test-only, or a real production trigger?

**Real, and the mechanism is not exotic.** Three findings combine:

1. **A hidden `FeedItemlistFragment` stays fully alive and EventBus-registered.** `MainActivity.loadChildFragment(...)` (`:516-539`) uses `.hide(...).add(...).addToBackStack(null)` — **not** `replace`. The hidden fragment's view is never destroyed, so `onDestroyView()` never runs, so it stays registered on EventBus and keeps servicing `PlayerStatusEvent`/`QueueEvent` by calling `loadItems()`. (`loadFragment(...)` at `:493-514` does use `replace` and does tear down — which is exactly why `RemoveFeedDialogClose` at `:350-356` routes through `loadFragment` before deleting.)
2. **Feeds get deleted by background machinery the user never touches.**
   - `SyncService.kt:164` → `DBWriter.removeFeedWithDownloadUrl(...)`, on a gpodder/Nextcloud sync that reports an unsubscribe **from another device**. This is precisely the scenario the task asked me to check, and it is real.
   - `FeedUpdateWorker.java:115` → `NonSubscribedFeedsCleaner.deleteOldNonSubscribedFeeds(...)`, which runs after *every* feed refresh (scheduled or forced) and deletes any `STATE_NOT_SUBSCRIBED` feed untouched for >1 day (`NonSubscribedFeedsCleaner.java:14,17-36`).
3. **`FeedItemlistFragment` is the screen that displays non-subscribed feeds** (`:281-284`, `:517-521`, `:535-542`), so target (2b) and the affected screen are the same screen. Sharper still: `refreshHeaderView():544-549` has the fragment itself kick off `FeedUpdateManager.runOnce(context, feed, true)` when a non-subscribed feed is >24h stale — i.e. the fragment can start the very worker whose tail-end cleaner deletes non-subscribed feeds.

Concrete production repro sketch (unverified on device — see Reproduction attempt): open a non-subscribed feed preview → tap an episode (`ItemPagerFragment` added on top; the item-list fragment is hidden but alive) → a feed refresh completes and the cleaner deletes the previewed feed → playback starts, `PlayerStatusEvent` fires → hidden fragment's `updateUi()` → `loadItems()` → `getFeed` returns null → NPE at `:659`.

**Severity, stated honestly:** in a release build this does not crash (see Verification 2). It writes `crash-report.log` via `CrashReportWriter.write` (`RxJavaErrorHandlerSetup.java:29`), and that file is read back and displayed in AntennaPod's own Bug Report screen (`BugReportViewModel.java:66-67`) — so the user-visible release symptom is a phantom crash report inviting them to file a bug for a crash that never happened. In debug builds it is a hard process kill, which is what every AntennaPod contributor and every CI instrumented run experiences. I'd characterise the pre-research claim as **substantiated as to the defect, overstated as to the release-build blast radius** — and the planner and José should decide how the PR describes it, because "fixes a production crash" would not be accurate.

The pre-research hypothesis (stale fragment + a later test's `clearDatabase()`) is **confirmed in class, and I can now name the specific predecessor test.**

2. Test ends. `IntentsTestRule<MainActivity>(MainActivity.class, false, false)` (`DownloadLogTest.java:43-44`) finishes the activity but does **not** await `onDestroy`, so teardown overlaps the next test.

#### Cleanest fix point — and why "a null guard at :659" alone is **wrong**

The critical structural fact the pre-research missed: **the success consumer does not read `result.first`.** It reads the *field* `feed` (`:666`, `:667`, `:671`) and uses only `result.second` (`:672`). The callable assigns that field at `:658` before anything can guard it.

Therefore, if the fix guards only the callable — e.g. `if (feed == null) return new Pair<>(null, 0);` — then on the **live-subscriber** path the success consumer runs with `feed == null` and NPEs at `:666` **on the main thread**, which is uncaught in *every* build type. That converts a debug-only background crash into an unconditional foreground crash. This is the single most important thing for the planner to carry forward: a one-line guard at the dereference site is not merely insufficient, it is a regression.

> **⚠️ PLANNER CORRECTION — legacy-android-planner, 2026-08-14 (post red-team Loop 1). The paragraph immediately above is factually wrong and must not be relied on.**
>
> `legacy-android-red-team` fetched the pinned RxJava `v3.1.5` source (`ReactiveX/RxJava` git tag, matching `gradle/libs.versions.toml:68`) and traced `Observable.subscribe(Consumer, Consumer)` → `LambdaObserver`. **`LambdaObserver.onNext(t)` wraps the user's success consumer in a `try/catch`.** If that consumer throws a non-fatal exception (a plain NPE is non-fatal — `Exceptions.throwIfFatal` treats only `VirtualMachineError`/`ThreadDeath`/`LinkageError` as fatal), the catch block disposes the **upstream** disposable and calls `LambdaObserver.onError(e)`. Disposing upstream does **not** flip `LambdaObserver`'s own `isDisposed()` flag — that is a separate `AtomicReference` — so `onError` takes its not-disposed branch and invokes **the user-supplied error consumer, i.e. the existing graceful handler already at `:676-683`**.
>
> **Consequence: the "guard only the callable" variant does not crash, on the main thread or anywhere else, in any build type.** It is a *functionally correct* fix — it stops the NPE being thrown inside the callable, which is the actual defect, and on the live-subscriber path its NPE is rerouted to the same empty-state handler that runs today. It was rejected on design grounds (see D1 as revised), not because it regresses anything.
>
> I verified the two supporting facts by direct read of `FeedItemlistFragment.java`: `:666` is the **first** statement of the success consumer, so under that variant nothing in the consumer executes before the throw (no `progressBar` change at `:669`, no adapter mutation at `:670-672`); and `adapter.setDummyViews(1)` is called only in `loadMoreItems()` (`:691`), never at fragment creation. The two paths are therefore not merely similar but **UI-indistinguishable**.
>
> This correction propagates to D1, D2, D3, Step 1 and the Acceptance Criteria, all revised below. Research's Verification 2 (the live-subscriber path is already graceful today) was correct all along — this paragraph simply failed to apply that same reasoning to the hypothetical naive fix.

Options, with the trade-offs — **not decided here:**

- **(A) Guard in the callable *and* in the success consumer.** Smallest conceptual change, keeps `Observable`. Cost: the empty-state block (`refreshHeaderView` / `setDummyViews(0)` / `updateItems(emptyList())` / `updateToolbar()`) is duplicated between the new success-path branch and the existing error consumer at `:678-681`.
- **(B) Switch `Observable.fromCallable` → `Maybe.fromCallable`, returning `null` when the feed is missing**, and put the empty-state handling in the `onComplete` argument. `Maybe.fromCallable` treats a null return as `onComplete`, so the success consumer is skipped entirely and no exception is ever thrown — nothing can become undeliverable. `Maybe` is **already imported** (`:67`) and this exact idiom is **already used in this file** at `showErrorDetails()` (`:599-613`), and in three sibling feed fragments. Cost: a slightly larger structural diff than (A), which sits in tension with `AGENTS.md`'s minimal-diff rule.

On **"should it visibly do something?"** — my reading is **no navigation, no new user-visible string.** Three reasons: the existing error consumer already defines this file's answer for "feed unavailable" (empty list + cleared header, silent); the in-app delete path already handles navigation explicitly and deliberately at `RemoveFeedDialogClose:350-356`; and the three sibling fragments do nothing at all on `onComplete`. Adding a toast or auto-dismiss would be new product behavior, and per `AGENTS.md` any new user-visible string would also have to land in `:ui:i18n`. Flagged as **OQ** rather than decided.

Revised again 2026-08-17 after red-team Loop 2-rerun — this time the fix itself changes: the `Maybe` switch and callable guard are retained unchanged, and a second guard is added at the other end of the chain, because the `Maybe` switch turns out to make the success consumer's pre-existing field-read hazard *worse* than it is today, not better.**

Both options fix the defect. The original justification for (B) rested on a false premise — that (A)'s naive single-end variant would crash the main thread — and that premise is now retracted (see the Planner Correction in Research §"Cleanest fix point"). **The real case for (B) is weaker than originally written, and it is still sufficient.** Stated honestly:

- **(B) removes the throw; it does not merely reroute it.** `MaybeFromCallable`, like `ObservableFromCallable`, still has a disposed-subscriber branch that hands a thrown exception to `RxJavaPlugins.onError`. Switching to `Maybe` alone would fix nothing — **the `if (feed == null) return null;` guard is what fixes it**, and `Maybe`'s null→`onComplete` contract is what makes that guard safe to write without a downstream null hazard. Stating this precisely matters, because "we switched to `Maybe`" is not the proof; "the callable can no longer throw an NPE for this cause" is. **This bullet is unaffected by the correction and remains the load-bearing one.**
- **(B) makes null-handling explicit at the type level; (A) delegates it to an implicit RxJava safety net.** Under (A), the success consumer still dereferences a null `feed` field at `:666` and still throws; the program is only well-behaved because `LambdaObserver.onNext` happens to catch consumer exceptions and reroute them to the error consumer. That behavior is real (red-team verified it against the pinned v3.1.5 source) but it is an internal implementation detail of the subscriber wrapper, not a contract the call site declares. Under (B), "no feed" is a first-class signal in the stream's type — `Maybe` emits `onComplete`, the success consumer is **never invoked**, and no exception is created, caught or rerouted anywhere. A reader of `loadItems()` can see the missing-feed path without knowing anything about `LambdaObserver`.
- **Corollary, stated because the original text claimed the opposite:** under (A) an NPE is still constructed and still reaches `Log.e(TAG, Log.getStackTraceString(error))` at `:682` on **every** missing-feed load, writing a full stack trace to logcat for a routine, expected outcome. That is log noise that reads like a crash in a user-submitted bug report — a genuine but **minor** drawback, not a crash.
- **(B) matches four in-repo precedents**, including one 50 lines above the defect in the same file (`showErrorDetails()`, `:598-614`, `Maybe.fromCallable` returning `null` → `onComplete` handler at `:613`), plus `FeedInfoFragment:128-135`, `FeedSettingsPreferenceFragment:127-134`, `FeedSettingsFragment:55-62`. Consistency with four sibling feed-loading sites is a real maintenance argument independent of any crash claim.

**What is explicitly no longer claimed:** that (A) is a regression, that (A) converts a background crash into a foreground crash, or that a developer who implements (A) by mistake ships a defect. (A) implemented naively is *functionally correct*; it is merely less explicit and noisier. The decision for (B) therefore rests on explicitness, in-repo consistency, and log hygiene — all design-quality arguments — **not** on safety. Anyone re-reading this Plan should weight it accordingly.
- **Diff cost is acceptable under `AGENTS.md`'s minimal-diff rule.** One identifier changed (`Observable` → `Maybe`), three lines added inside the callable, one handler argument added. `Maybe` is already imported (`:67`); `Observable` stays imported (still used by `loadMoreItems()` at `:693`); `Disposable` is unchanged (`Maybe.subscribe(Consumer, Consumer, Action)` returns `Disposable`, exactly as the `:609-613` precedent does). **Zero import churn, zero changes outside `loadItems()`.**

**Added rev. 3 (2026-08-17) — the load-bearing bullet the four above were missing, and the reason the fix is no longer a one-ended change.**

- **Switching to `Maybe` silently downgrades the success consumer's safety net, so the callable guard alone is not enough.** Today's code subscribes an `Observable` with a 2-arg `subscribe`, backed by `LambdaObserver`; Loop 1 verified that `LambdaObserver.onNext`'s catch calls `get().dispose()` then `this.onError(e)`, which lands in **the fragment's own graceful error consumer** at `:676-683`. The fix's 3-arg `Maybe.subscribe` is backed by a *different* class, `MaybeCallbackObserver`, whose `onSuccess` is `lazySet(DISPOSED); try { onSuccess.accept(value); } catch (Throwable ex) { Exceptions.throwIfFatal(ex); RxJavaPlugins.onError(ex); }` — it routes a thrown consumer exception **directly to `RxJavaPlugins.onError`**, bypassing the supplied error consumer entirely, disposed or not. Both classes were read from the pinned RxJava `v3.1.5` tag (matching `gradle/libs.versions.toml:68`) by the Loop 2-rerun review. **Consequence:** an NPE inside the success consumer is *graceful today* and *an undeliverable exception after the `Maybe` switch* — i.e. a debug-build process kill and a release-build phantom `crash-report.log`, the exact defect this task exists to close. Since the success consumer's first statement dereferences the shared `feed` **field** (`:666`), and Research's Verification 3 establishes that a disposed invocation's callable keeps running to completion on its `Schedulers.computation()` worker — including the plain field write at `:658` — a slower, disposed invocation can null the field *after* a live invocation's `Pair` is queued for main-thread delivery. The live consumer then dereferences null. **The `Maybe` switch is therefore only safe when paired with a guard at the consumer end; without it the fix would trade a common crash path for a rarer one.** This is the CRITICAL finding from red-team Loop 2-rerun, accepted in full.

**Which in-scope variant closes it — decided, with the reasoning recorded because it diverges from the stated leaning.** José authorized closing the gap inside File Scope and named two variants: (i) source the consumer's feed reads from the emitted `result.first` instead of the field, or (ii) guard the consumer's field read. He leaned (i) on the grounds that it does not depend on the field still holding the value the callable computed. **This plan adopts (ii), the guard.** Both variants make the crash unreachable — under (i) the three direct reads move to a race-immune local value, and `refreshHeaderView()`/`updateToolbar()` already early-return on a null field, so neither variant can throw. The tie is broken on four points, in order of weight:

1. **The consumer has five feed-dependent reads, not three.** `:666`, `:667` and `:671` read the field directly; `refreshHeaderView()` (`:668`, guards at `:497`) and `updateToolbar()` (`:673`, guards at `:273`) read it transitively. Variant (i) can only move the first three — moving the other two means changing those methods' signatures, which is code **outside `loadItems()`** and therefore outside both D1's "zero changes outside `loadItems()`" property and File Scope's "`loadItems()` (`:652-684`) only" restriction. So (i) cannot deliver the clean claim "the success consumer does not read the mutable `feed` field"; an Acceptance Criterion asserting it would be unsatisfiable as written.
2. **A partial move is worse than no move, because it can render a hybrid of two feeds.** Under (i), in the race where the clobbering invocation writes a *different, non-null* feed rather than null, the consumer would populate the item list and filter from `result.first` while the header and toolbar render the field's other feed. Under (ii) the consumer reads exactly one source, checked once at the top, so whatever it renders is internally consistent. Removing a crash by introducing a split-brain render is a bad trade on a task whose entire claim is behavioral equivalence.
3. **(ii) is a pure insertion; (i) modifies three lines on the success path every user hits.** The unchanged-by-inspection argument that D1 and D3's four-variant table both rest on survives (ii) intact — the ten statements of the existing consumer stay byte for byte — whereas (i) would edit the highest-blast-radius code in the diff for a race-window benefit, and would require re-deriving equivalence for the normal path.
4. **(ii) matches the file's own idiom.** `showFeedInfo()` (`:616-619`), `refreshHeaderView()` (`:497-500`) and `updateToolbar()` (`:273-275`) are all already `if (feed == null) { return; }` at the top. The same in-repo-consistency argument that selected `Maybe` over `Observable` selects the guard over the result-read.

**What (ii) does not buy, stated plainly so the case study stays honest:** it makes the field read *safe*, it does not *decouple* the consumer from the field. In the narrow race where the clobbering invocation writes a different non-null feed, the consumer still renders that feed's items alongside `result.second`'s count from the other invocation — a count/content mismatch with no crash. **That mismatch exists identically in today's unfixed code and is unchanged by this fix**, so it is a pre-existing condition being carried forward, not a regression introduced here; it is recorded in D2's bounds and belongs with the field-sharing design smell already captured for the future-work doc under OQ-2. If José prefers variant (i) after reading this, it is a three-line swap at implementation time and only the two guard-specific Acceptance Criteria below change.

**The guard's body is chosen for observable equivalence with today's behavior on this exact path, not for brevity.** Today, when the live consumer meets a clobbered null field, `LambdaObserver` reroutes into the error consumer at `:676-683`, whose net observable effect — given `feed` is already null, so `feed = null` is a no-op and both `refreshHeaderView()` and `updateToolbar()` early-return — is exactly `adapter.setDummyViews(0)` plus `adapter.updateItems(Collections.emptyList())`, with the spinner left visible. The guard reproduces those two statements and nothing else. It deliberately omits `feed = null` (already null), `refreshHeaderView()` and `updateToolbar()` (documented no-ops on a null feed), and `Log.e` (there is no throwable, and suppressing this stack trace is the log-hygiene win D1 already argues for). Clearing the list is also semantically right, not merely equivalent: the field is null only because the most recent `DBReader` read found no feed, so the items in `result.first` describe a feed that no longer exists.

The target shape, given exactly so no interpretation is required at implementation time:

```java
disposable = Maybe.fromCallable(
        () -> {
            feed = DBReader.getFeed(feedID, true, 0, page * EPISODES_PER_PAGE);
            if (feed == null) {
                return null;
            }
            int count = DBReader.getFeedEpisodeCount(feed.getId(), feed.getItemFilter());
            return new Pair<>(feed, count);
        })
        .subscribeOn(Schedulers.computation())
        .observeOn(AndroidSchedulers.mainThread())
        .subscribe(
            result -> {
                if (feed == null) {
                    adapter.setDummyViews(0);
                    adapter.updateItems(Collections.emptyList());
                    return;
                }
                /* :666-675 UNCHANGED, byte for byte, below this guard */
            },
            error   -> { /* :676-683 UNCHANGED, byte for byte */ },
            () -> {
                feed = null;
                refreshHeaderView();
                adapter.setDummyViews(0);
                adapter.updateItems(Collections.emptyList());
                updateToolbar();
            });
```

**The `onComplete` handler deliberately mirrors the existing error consumer (`:677-681`) statement for statement, minus `Log.e` (there is no throwable to log).** This is the equivalence argument in its strongest form: today, a live subscriber with a missing feed reaches `:677-681` via `onError`; after the fix it reaches an identical statement sequence via `onComplete`. The user-visible result is unchanged by inspection, not by assertion. In particular the handler does **not** add `viewBinding.progressBar.setVisibility(View.GONE)` — the error path does not hide the spinner today (it is only hidden at `:669`, in the success consumer), and adding it would be a behavior change on the exact path being characterized. See Out of Scope.

**The success-consumer guard is the only change to `:665-675`, and it is additive (rev. 3).** The ten existing statements move down by five lines and are otherwise byte for byte identical; nothing is reordered, renamed or deleted, per `AGENTS.md`'s minimal-diff rule. The guard does not touch `viewBinding.progressBar` either, for the same reason the `onComplete` handler does not: the spinner is a pre-existing, deliberately-preserved artifact of the feed-missing path (see Out of Scope), and hiding it here would be a behavior change smuggled in on a race path that no test observes.

**D2 — Verification bar. Decided, and deliberately split so no leg of it claims more than it can carry.** (Research Unknown 2 — the hardest decision here.)

The defect has two distinct paths, with two distinct risk profiles, and conflating them is how a plan ends up overclaiming:

| Path | What the fix changes | Regression risk | How it is verified |
|---|---|---|---|
| **Live subscriber, feed missing** | `onError` → `onComplete` (same statements) | Low, and fully deterministic — the statement sequence is identical | **Deterministic instrumented test** (D3) |
| **Disposed subscriber, feed missing** | NPE thrown → no NPE thrown | None (nothing to regress; it crashes today) | **Structural argument** + bounded CI corroboration |
| **Live subscriber, field clobbered by a slower disposed invocation** (added rev. 3) | Consumer NPE → guard returns early. Without the rev.-3 guard the `Maybe` switch would have made this path *worse* than today: graceful under `LambdaObserver`, undeliverable under `MaybeCallbackObserver` | Low — the guard's two statements reproduce today's net observable effect on this path (D1) | **Structural argument only.** No test seam: D3's test drives one invocation, not two overlapping ones, and D2's 9-leg CI bar is far too small a sample for a race rarer than the ~36% original. Enforced by diff inspection |

1. **Primary proof — structural, and it is a real proof, not a hand-wave. Extended rev. 3 to cover both ends of the chain, because rev. 2's version covered only the first and was therefore false as stated.** `RxJavaPlugins.onError` can be reached from `loadItems()` by exactly two routes, and the fix closes both:
   - **Route 1, the callable.** The crash requires an exception to escape `callable.call()`. After the fix the only statements in the callable that can produce the observed NPE (`feed.getId()`, `feed.getItemFilter()`) are unreachable when `feed == null`, because the `return null` precedes them. `Maybe.fromCallable`'s documented contract turns that null into `onComplete`, which cannot carry a throwable. So no NPE for this cause escapes the callable, disposed or not.
   - **Route 2, the success consumer — the route rev. 2 missed.** `MaybeCallbackObserver.onSuccess` catches a consumer throwable and hands it to `RxJavaPlugins.onError` directly, so an NPE in the success consumer is undeliverable by construction under `Maybe`, not rerouted to `:676-683` the way `LambdaObserver` reroutes it today (D1, rev. 3). After the fix the guard is the consumer's **first** statement, so every subsequent statement — the three direct field reads at `:666`, `:667`, `:671` and the two transitive ones inside `refreshHeaderView()` and `updateToolbar()` — executes only on a non-null `feed`. So no NPE for this cause escapes the consumer either, whatever a concurrent invocation does to the field.

   Together: `RxJavaPlugins.onError` is never reached *for a null `feed`*, from either end of `loadItems()`, in any build type and any disposal state — including the cross-invocation clobber that Research's Verification 3 makes possible. This is checkable line by line and does not depend on timing. **Bounded honestly, and the bounds are now three:** (a) it proves the elimination of the null-`feed` NPE specifically, **not** that the callable can never throw anything else — a `SQLiteException` from `DBReader` on a disposed subscriber would still be undeliverable; (b) it does not fix the general undeliverable-exception hazard elsewhere in the app, nor `loadMoreItems()`'s own unguarded field read (D7); (c) it makes the field read *safe*, not *race-free* — in the narrow case where a concurrent invocation replaces the field with a **different non-null** feed, the consumer renders that feed's items against `result.second`'s count from the other invocation. That mismatch is present identically in today's unfixed code, is not introduced or widened here, and produces no exception; it is a symptom of the shared-mutable-field design smell captured for the OQ-2 future-work doc, not something this minimal-diff bugfix undertakes to fix.

2. **Secondary proof — the deterministic instrumented test (D3)**, which pins the live-subscriber path: it confirms the fix produces the correct graceful empty state, and (via its second method) that the success path still works across the `Observable` → `Maybe` swap. **Revised 2026-08-14:** this test was previously credited with "failing hard if a developer implements the D1 landmine." That claim is retracted — the landmine produces a UI-indistinguishable outcome, so no assertion in this test can separate them (full reasoning in D3 as revised). The landmine is in any case not a defect, merely a less explicit shape, so nothing needing a gate is left ungated. **Conformance to D1's specified fix shape is enforced by diff inspection at code-review time, not by a test** — see the "Fix correctness (Step 2)" acceptance criteria, which are deliberately written as inspectable properties of the diff for exactly this reason.

3. **Corroboration — CI observation, with the confidence stated rather than implied.** Mechanics, per Research's CI findings:
   - **Grep raw logs, never job conclusions.** Run `31796405935` reported `Emulator Test API 30` as `success` while its own log contained a full signature-matched crash. Verification is `gh run view --job <id> --log | grep -c 'FeedItemlistFragment.lambda$loadItems'` for **every** leg of **every** run, expecting `0`.
   - **Confirm each leg actually ran the suite.** Because `checks.yml:112-120` has no `fail-fast: false`, a cancelled leg produces zero crash hits *and* zero evidence. Each leg's log must show the instrumentation actually started and completed (`Starting NN tests` and a completion line), or that leg does not count toward the sample.
   - **Sample size and what it buys.** Post-fix, a passing leg makes exactly one attempt (`runEmulatorTests.sh:12`'s `runTests || runTests || runTests` short-circuits on success), so one full run ≈ 3 attempt-legs. Research's observed rate is ~5 signature failures across ~13-14 attempts (p̂ ≈ 0.36; 95% CI roughly 0.14-0.65). Probability of observing zero crashes across N clean attempts if the bug were **not** fixed:

     | Clean attempt-legs | at p̂ = 0.36 | at pessimistic p = 0.14 |
     |---|---|---|
     | 3 (1 run) | 27% | 64% |
     | 6 (2 runs) | 7.1% | 41% |
     | **9 (3 runs)** | **1.9%** | **26%** |

     **The bar is 3 full `emulator-test` runs of the fix branch, ≥9 clean attempt-legs, zero grep hits across all of them.** Use `gh run rerun <run-id>` for runs 2 and 3 — it produces genuinely fresh emulator attempts without junk retrigger commits on the PR.
   - **What that does and does not establish, to be written into the PR in these terms:** even at 9 clean legs, CI evidence alone leaves up to ~26% residual under the pessimistic end of the rate estimate, and the three legs within one run are not fully independent samples (API 36 never reproduced the signature; API 23 and 30 did). **CI is corroboration; the structural argument is the proof.** Anyone reading this plan should understand the CI runs are there to catch a mistake in the structural argument, not to substitute for it.

**But that precedent does not settle the instrumented option, and Research did not evaluate it.** It should have been, because the answer is much better: a targeted instrumented test needs **zero new dependencies** and is **fully deterministic**. `FeedSettingsTest.setUp()` (`:37-49`) is a working template for exactly the manoeuvre required — `EspressoTestUtils.clearDatabase()`, then `launchActivity` on an `Intent` carrying `MainActivityStarter.EXTRA_FEED_ID`, which reaches `MainActivity.handleNavIntent()` (`:745-753`) → `loadFeedFragmentById` (`:484-491`) → `FeedItemlistFragment.newInstance(feedId)` → `loadItems()`. **D4 — PR/commit severity wording. Decided; the exact text is fixed here so it is not improvised at PR time.** (Research Unknown 4.)

"Fixes a production crash" is **inaccurate** and must not appear. `RxJavaErrorHandlerSetup.java:18-34` swallows this exception class in release builds and rethrows only under `if (BuildConfig.DEBUG)`. Required framing, to be used in the commit message and PR description:

> Guards an unguarded dereference of `DBReader.getFeed(...)`'s documented-`@Nullable` return in `FeedItemlistFragment.loadItems()`. When the feed has been deleted out from under a still-alive fragment, the resulting NPE is thrown on a computation thread inside `Observable.fromCallable`; if the subscriber has already been disposed, RxJava routes it to the global handler as an undeliverable exception. **In debug builds that is a hard process kill** (`RxJavaErrorHandlerSetup` deliberately rethrows under `BuildConfig.DEBUG`), which is what CI's `emulator-test` job has been hitting intermittently. **Release builds do not crash** — they swallow it and write a `crash-report.log` that AntennaPod then surfaces to the user in its own Bug Report screen, i.e. a phantom crash report for a crash that never happened.

Equally required, on the CI claim:

> This does **not** by itself make `emulator-test` reliably green. It eliminates one specific, signature-matched crash; the job's residual flakiness from other sources is unmeasured.

And the honest bound from D2, stated rather than omitted:

> Verified structurally (the callable can no longer throw for this cause) and by a new deterministic instrumented test covering the live-subscriber path; the disposed-subscriber path has no test seam and rests on the structural argument plus N clean CI runs, which is corroboration, not proof.

Per `CLAUDE.md`'s rule on commercially-relevant public claims, this wording is flagged for José before the PR is opened (OQ-1) — it is portfolio case-study material and the severity framing is the part a reader will quote.

### Concerns

- **Severity:** CRITICAL
- **Class:** Characterization tests prove equivalence, not just existence / unverified equivalence claim
- **Concern:** The Plan's central risk narrative — that guarding only the callable ("option A's naive variant," Research's "Cleanest fix point," carried into D1) produces "the success consumer... NPEs at `:666` on the main thread, which is uncaught in every build type" and "converts a debug-only background crash into an unconditional foreground crash" — is **factually wrong** about RxJava3's actual behavior. I fetched and read the real, tagged v3.1.5 source (`io.reactivex.rxjava3.internal.observers.LambdaObserver`, the class that backs `Observable.subscribe(Consumer, Consumer)` — confirmed by reading `Observable.java`'s two-arg `subscribe` overload, which constructs exactly this class). `LambdaObserver.onNext(t)` wraps the call to the user's `onNext` consumer in a `try/catch`; if it throws (as the landmine's NPE would, at `feed.getItems()`), the catch block calls `Exceptions.throwIfFatal(e)` (confirmed via `Exceptions.java`: only `VirtualMachineError`/`ThreadDeath`/`LinkageError` are fatal — a plain NPE is not), then `get().dispose()` (disposes the *upstream* disposable only — it does **not** flip `LambdaObserver`'s own `isDisposed()` flag, which is a separate `AtomicReference` check), then calls `this.onError(e)`. Inside `LambdaObserver.onError`, `isDisposed()` is still `false` at this point, so it takes the **not-disposed branch**: it self-disposes *then* invokes the real, user-supplied error consumer — i.e., the exact same handler already at `FeedItemlistFragment.java:676-683` today. The result: on the deterministic live-subscriber path, the "landmine" fix produces **the identical visible outcome** (empty recyclerView, empty header title, via the same `refreshHeaderView()`/`updateToolbar()` early-return calls) as both the correct D1 fix and, critically, **the current unfixed code** (Research's own Verification 2 already established the unfixed live-subscriber path is graceful — this finding is consistent with, not contradictory to, that earlier finding; the Plan simply failed to apply the same reasoning to the "naive fix" hypothetical).
