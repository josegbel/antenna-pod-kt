# tasks/artifacts/

Checked-in visual artifacts generated by this portfolio's Android-migration case studies. Each PNG here
is produced by a Robolectric test living in the module it captures, so it can be regenerated from the
commit noted below rather than existing as an orphan binary.

This is an **interim** location. If the AEPM marketing site
(`web-aepm-labs/public/images`) becomes the publishing home for a screenshot, the file is *copied* there
— this repo keeps the reproducible provenance record, since the marketing repo is a separate repository
and cannot be regenerated from this one.

## `sync-settings-before-milestone-15b.png`

**This screenshot postdates Milestone 15.** Milestone 15 (`kotlin` track, PR #21, merged as `f5d4c5551`)
converted the Sync Settings screen (`:ui:preferences`, `screen/synchronization/`) from Java to Kotlin
behavior- and visually-unchanged — its own acceptance criteria required no rendered-output change. This
screenshot was captured *after* that conversion, so it is visually identical to what the original Java UI
looked like. It is the correct "before" baseline for Milestone 20's future Compose comparison; it does not
predate Milestone 15, and nobody should assume it does.

**Provenance.**
- Production code rendered: unchanged since `f5d4c5551` ("kotlin/ui-preferences: convert
  screen/synchronization/ (4 files) to Kotlin, stand up module's first test suite (#21)") — this task adds
  no production-code change, so the rendered screen reflects that commit exactly.
- Generating test:
  `de.danoeh.antennapod.ui.preferences.screen.synchronization.SyncSettingsScreenshotCaptureTest.testWritesPngUnderModuleBuildDirectory`
- Regenerate with:
  `./gradlew --console=plain :ui:preferences:testPlayDebugUnitTest --tests "*SyncSettingsScreenshotCaptureTest*" --rerun`
  then copy `ui/preferences/build/reports/screenshots/sync_settings_before_milestone_15b.png` over this
  file. The test's own PNG output is never asserted byte-for-byte and is not itself checked in — only this
  copy is a frozen historical baseline.

**Why API 34, not the module's target SDK 36.** The capture is pinned to `@Config(sdk = [34])`. This is
**not** because production lacks system-inset handling — it does: `ToolbarActivity`'s `toolbar_activity.xml`
sets `android:fitsSystemWindows="true"` and consumes insets above a real `MaterialToolbar`. The pin instead
renders at an API level that **predates edge-to-edge enforcement**, so the capture does not depend on how
faithfully Robolectric simulates system-bar insets at API 35+ — a simulation this task has no budget to
verify. At API 34 the geometry is the one directly observed and confirmed correct (all rows visible, none
clipped behind the toolbar).

**Chrome fidelity.** This capture is hosted by `SyncSettingsCaptureHost`, which extends production's own
`ToolbarActivity` and inflates production's own `settings_activity.xml` — the same `MaterialToolbar` under
the same `Theme.AntennaPod.Light.NoTitle` that ships to users, not an approximation of it. Two departures
from production's real `PreferenceActivity` are deliberate and disclosed: the capture host does not
register on EventBus in `onStart` (production does, solely to show a `MessageEvent` Snackbar — nothing in
this logged-out capture path posts one), and it attaches the target fragment directly rather than routing
through `MainPreferencesFragment` + `openScreen()` navigation. Neither affects rendered chrome.

**Fidelity caveats, documented rather than investigated.**
1. The three disabled preference rows ("Synchronize now", "Force full synchronization", "Logout") do not
   render visibly dimmed in this capture — their titles draw at the same weight as the enabled header row.
   The plausible cause is that AndroidX preference's `setEnabled` state does not propagate to the child
   `TextView`s' drawable state under Robolectric's native renderer — this is an **unverified hypothesis**,
   not a confirmed diagnosis.
2. This is a Robolectric render, not a real-device render, and has not been compared against one. Font
   rasterisation, anti-aliasing, and disabled-state dimming may all differ from what a physical device or
   emulator would show.

**Do not pixel-diff this against Paparazzi output.** Milestone 20's planned "after" capture will use
Paparazzi (added in Milestone 16) rendering Compose UI — a different rendering engine entirely from this
PNG's Robolectric View-system capture. A pixel-diff between the two would be meaningless. This PNG is a
side-by-side visual reference for the case study, not a golden image for an automated regression check.
