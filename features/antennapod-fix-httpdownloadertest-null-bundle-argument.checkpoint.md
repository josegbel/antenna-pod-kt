### Added by Research, 2026-08-13

- **Primary root cause CONFIRMED, unchanged.** Exactly two `DownloadRequest` construction sites in `HttpDownloaderTest.java`, at current lines **87-88** and **123-124**, both 9-arg calls binding to the convenience constructor at `DownloadRequest.kt:30-43` whose `arguments: Bundle` (`:38`) is genuinely non-null. Pre-migration Java at `936c16aec^` had `destination`/`source`/`title` as `@NonNull` but `arguments` unannotated. All 9 tests fail, deterministically, on every API level and all 7 CI attempts.
- **New supporting detail:** passing `null` was never supported even in Java — the pre-migration `hashCode()` did `arguments.hashCode()` unguarded (`DownloadRequest.java:141` at `936c16aec^`). The test only got away with it by never calling `hashCode()`/`equals()`. Kills any "the test meant to probe null" reading.
- **Cascade hypothesis REFUTED.** `DownloadLogTest.testExistingNonSubscribedFeed` is an independent, pre-existing, ~50%-flaky defect, **not** caused by `HttpDownloaderTest`. Run `31694690838` contains 7 executions of the same commit (3 API levels × up to 3 retries in `runEmulatorTests.sh:12`). `HttpDownloaderTest` failed identically in 7/7; `DownloadLogTest` **passed in 4 of 7**. API 36 is the clean disproof: two attempts, same 9 failures, `DownloadLogTest` passed both times, 69/69 tests completed, no crash.
- **Direction was also inverted.** `HttpDownloaderTest`'s NPEs are caught by JUnit as ordinary failures and never crash the process. It is `DownloadLogTest` that kills the instrumentation process, which is why crashed attempts stop at 34-35 tests instead of 67-69.
- **Real mechanism of the secondary failure:** not `DownloadLogTest`'s own `feed` field, but production code — `FeedItemlistFragment.java:659` dereferences the `@Nullable` return of `DBReader.getFeed(...)` (`DBReader.java:329-330`) on a `Schedulers.computation()` thread; once the subscriber is disposed the error becomes RxJava-undeliverable and kills the app process. A `FeedItemlistFragment` left alive by a sibling test in the same class re-runs `loadItems()` after `EspressoTestUtils.clearDatabase()` wipes the DB in the next test's `@Before`. `FeedItemlistFragment` is not even in `testExistingNonSubscribedFeed`'s intended path (`DownloadLogDetailsDialog.java:157-168` routes non-subscribed feeds to `OnlineFeedviewActivity`).
- **Consequence for AC13:** fixing `HttpDownloaderTest` is necessary but **not sufficient** for a guaranteed green `emulator-test`. `DownloadLogTest` can still flake and fail the whole matrix (no `fail-fast: false` in `checks.yml:112-120`). Every API level had at least one clean attempt, so the 3× retry makes green likely — but API 30 flaked on 2 of 3.
- **Fix recommendation (planner's call):** `new Bundle()` at both sites, matching `DownloadRequestBuilder.kt:19`. Switching the test to `DownloadRequestBuilder` is **not** a like-for-like option — the builder has no general constructor, derives `title` from `getHumanReadableIdentifier()` (which would become the URL for these title-less feeds), rewrites `source` via `UrlChecker.prepareUrl`, injects `REQUEST_ARG_PAGE_NR`, and defaults `initiatedByUser = true`. It would change the requests under test.
- **Not reproduced locally** — `adb devices` is empty, no AVD running; `connectedPlayDebugAndroidTest` needs a live device. Conclusions rest on full source reading plus the 7-attempt CI matrix as a controlled comparison.
- **5 Unknowns logged** in the task file for the planner, incl. whether the `FeedItemlistFragment.java:659` null guard becomes a fifth sibling CI-blocker task (scope decision for José, deliberately not decided in Research).
