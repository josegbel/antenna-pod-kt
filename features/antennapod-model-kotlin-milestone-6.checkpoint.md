## Research outcome (legacy-android-researcher, 2026-07-24)
- **Milestone 5's Tier C inventory confirmed still current** against live source: `DownloadRequest` (227 LOC, Parcelable-only), `FeedMedia` (548 LOC, `implements Playable`), `RemoteMedia` (299 LOC, `implements Playable`), `Playable` (128 LOC interface, `extends Parcelable, Serializable`). LOC counts match M5 exactly; these are the only 4 Java files left in `:model`. Verified `FeedMedia` + `RemoteMedia` are the **only** two `Playable` implementers repo-wide (no external implementers) — the interface's Kotlin nullability contract only has to satisfy these two, both in scope.
- **All the prior-pass claims verified true:** `DownloadRequest`'s username/password null→`""`→null asymmetry (`nonNullString`/`nullIfEmpty`, L78-91); hand-written field-selective `equals`/`hashCode` on all three concrete classes (must stay, NOT `data class`), incl. the mutual `FeedMedia`↔`RemoteMedia` cross-type `equals`; `Playable` getters mostly unannotated (only `getDescription`/`getImageLocation` are `@Nullable`) while implementers return null in practice → platform-type ambiguity; only `FeedMedia` has any existing test (`FeedMediaTest`, 3 tests, `setDownloaded`/item-state only, no Parcel round-trip).
- **New, load-bearing findings beyond the prior pass:**
  1. **Parcel round-trips are lossy-by-design and asymmetric** — each type parcels a *subset* of fields with null/empty transforms that must be preserved verbatim: `DownloadRequest` doesn't parcel `progressPercent`/`soFar`/`size`/`statusMsg` (yet `equals` compares them); `FeedMedia` drops `item` (keeps `itemID`) and turns null `lastPlayedTimeHistory` into `Date(0)`; `RemoteMedia` turns null `pubDate` into `Date(0)` and drops `chapters`. Characterization tests must account for these, not assume full-fidelity round trips.
  2. **MediaBrowser coupling is `FeedMedia`-only** — `RemoteMedia` has none. This corrects the task-prompt assumption that both are coupled. `FeedMedia.getMediaItem()` also uses `Uri.parse` (bare-JVM stub → null); both resolve for free under the Robolectric this milestone adds, so they need not stay mocked — but they're not Parcel concerns.
  3. **An existing external Robolectric test already partially characterizes `DownloadRequest`** — `DownloadRequestBuilderTest` in `:net:download:service-interface` round-trips it through `Bundle.putParcelableArrayList` with null/mixed-auth cases. Robolectric is already used in 10+ repo test classes; the Robolectric-free precedent being excepted is `:model`-specific, not repo-wide.
  4. **Property-vs-getter ripple** — converting `Playable`/`FeedMedia` to Kotlin *properties* breaks 3 already-Kotlin in-module callers using `getX()` syntax (`EmbeddedChapterImage.kt:50`, `FeedFilter.kt:48`, `FeedItem.kt:50`); the ~102 Java consumers are unaffected. Planner must decide: expand File Scope to fix those 3, or keep members as functions.
  5. No `serialVersionUID` in any of the four (`FeedMedia`/`RemoteMedia` are transitively `Serializable` via `Playable`; `DownloadRequest` is not `Serializable`) — same M4/M5 `1L`-pin question recurs.
- **6 Unknowns flagged for the planner:** sub-batching (Playable+FeedMedia+RemoteMedia coupled vs DownloadRequest solo); per-getter `Playable` nullability + functions-vs-properties; `serialVersionUID` pinning; File Scope boundary for the 3 in-module Kotlin ripple files; whether `getMediaItem`/`checkEmbeddedPicture` get characterization or are conversion-only; and `DownloadRequest` test approach (direct `CREATOR` vs mirror the external Bundle-arraylist test).
