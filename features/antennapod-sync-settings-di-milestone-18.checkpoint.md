- **`kotlinx-coroutines-test` is probably NOT this milestone's bill.** Nothing forces a `suspend` repository read — every wrapped read is a synchronous SharedPreferences getter, and a suspension point between `onStart()` and the first `render()` is a behavior change two frozen lifecycle tests discriminate on. Recommend a synchronous seam and no new test dependency; the entry that would actually be earned is `hilt-android-testing`, which is absent from the catalog.
- **`PreferenceActivity.java:75` is a direct `new SynchronizationPreferencesFragment()`, not reflective instantiation.** Reflective re-creation still happens via `FragmentManager` on state restore, so the public/no-arg rule holds — but Hilt field-injects in `onAttach`, so reflective instantiation is a non-issue. The real constraint is the host-Activity requirement.
- **KSP is forced, not merely preferred.** `:app` is 100% Java (0 `.kt` files) and processes Hilt with plain javac `annotationProcessor`; `:ui:preferences` is Kotlin, so javac AP cannot see its declarations. kapt is used nowhere in the repo.

The `di` milestone stands up an actual Hilt container: KSP + Hilt plugin on `:ui:preferences`, `@AndroidEntryPoint` on the slice fragment(s), `@HiltViewModel` on `SynchronizationPreferencesViewModel`, a real `@Module @InstallIn(SingletonComponent)` binding the seam. Option A (plain interface seam, no container) was rejected as too weak for a `di` case study. ### The blocking question for the Plan (now resolved — see above)
- **`@HiltViewModel` is unreachable without `@AndroidEntryPoint`, and `@AndroidEntryPoint` breaks 21-43 of the 55 tests.** `:ui:preferences` has no `robolectric.properties`, no `@Config(application = …)`, a bare library manifest with no `<application>`, and **zero `com.google.dagger:*` on its unit-test runtime classpath** (verified by resolution). Hilt fragment injection needs a Hilt `Application`; `PodcastApp` lives in `:app` and is unreachable from here. Two options, both costed in Research finding 5: **(A)** plain interface seam, no Hilt graph, all 55 tests byte-identical; **(B)** real `@HiltViewModel` + `@AndroidEntryPoint`, requiring `hilt-android-testing` + `HiltTestApplication` + `HiltAndroidRule` + `@HiltAndroidTest` on 4 test classes (class-level annotations only — no bodies, no assertions). **This is a scoping decision with a commercial dimension (what the `di` track delivers) and should be surfaced to José, not settled inside the plan.**
- **Unverified and must be the plan's earliest gate:** does mixed-processor Hilt (javac in `:app`, KSP in `:ui:preferences`) actually build? And does `./gradlew lint` survive Hilt-generated code, given `checkGeneratedSources = true` + `warningsAsErrors true` + no lint baseline anywhere?
