## Planner's decisions (2026-08-18) — read before red-teaming

- **Matchers are scoped by ancestor, not by visibility.** `:56` → `allOf(isDescendantOfA(withId(R.id.appBar)), withId(R.id.txtvTitle))`; `:76` → `allOf(isDescendantOfA(withId(R.id.appBar)), withText(feed.getTitle()), isDisplayed())`, the `FeedSettingsTest.java:59-60` idiom verbatim.
- **Research Unknown 2 resolved without an extra verification step, on structural grounds.** `R.id.appBar` is declared in exactly 2 layouts repo-wide (`feed_item_list_fragment.xml:11`, `feedinfo.xml:11` — the latter a different screen, never concurrent), and there is exactly one `txtvTitle` under it. There are **no `layout-v*` qualifiers anywhere in the repo** (the only layout qualifier is `layout-sw720dp/main.xml`, a screen-size bucket declaring no `appBar`), so containment is identical on API 23/30/36. The API-level variation Research documented is entirely in visibility/presence state — the axis ancestor-scoping does not consult. Residual risk stated in the Plan: `:56` has never executed on API 23, so Step 3's run is its first-ever execution there.
- **`isDisplayed()` deliberately omitted at `:56`** (kept at `:76`). At `:56` the assertion is `withText("")`, and an empty `TextView`'s bounds are the most API-variable thing in play; containment is already unique, so the conjunct could only convert a correct assertion into a `NoMatchingViewException`.
- **`waitForViewGlobally` kept at `:76`, not swapped for `waitForView`.** `EspressoTestUtils.waitForView:74-80` returns on the first breadth-first match, so an over-broad matcher would silently pass against the wrong view; `waitForViewGlobally` routes through `onView` and throws `AmbiguousViewMatcherException` loudly. Loud failure beats a possible silent false green on a characterization test. Also the smaller diff.
- **The new `progressBar` assertion needed scoping too — `withId` alone would have reintroduced the same class of bug.** `id/progressBar` appears in **14** layouts, including `nav_list.xml:77` (always-present drawer) and `feeditemlist_item.xml:199` (every episode row). Anchor is `withParent(withId(R.id.coordinatorLayout))`, not `isDescendantOfA`: the fragment's spinner is a *direct child* of `coordinatorLayout` while episode-row spinners are descendants of it. `R.id.coordinatorLayout` is declared in exactly one layout repo-wide.
- **The "characterization tests first" rule is satisfied in inverted form, not waived.** The tests exist but cannot execute, so Step 1 (repair until they execute and pin behavior) is the characterization step and precedes all production code. Stated openly in the Plan: Step 2 has no honest "pin current behavior / prove equivalence" framing, because current behavior on that path *is* the defect — it is a deliberate user-visible behavior change, and the D6 assertion is a regression test for the new behavior. Step 1's CI evidence (API 23 still failing at launch with both matchers fixed) serves as the "red before".
