The same defensive treatment was correctly applied to the sibling class `DownloadResult` in this same diff (Implementation Notes Deviation #3) but never extended to `FeedItemFilter`, despite `FeedItemFilter` having a demonstrably more exposed serialization boundary (3 real Bundle call sites vs. zero found for `DownloadResult`'s own `ObjectOutputStream` usage). Neither Research's "zero Android-framework imports" batch-selection criterion nor either Code Review loop's `javap` check (which verified `DownloadResult`'s `serialVersionUID` but never checked `FeedItemFilter`'s) caught this.
- **Fix needed:** add `private const val serialVersionUID = 1L` to `FeedItemFilter.kt`'s companion object (same pattern `DownloadResult.kt` already uses, same value the class has always had). Re-verify via `javap -p` that the field is now present on the compiled class, confirm `FeedFilterTest`/`DownloadResultTest`/`FeedItemFilterTest`/`TranscriptTest` all stay green, and confirm no other file changed.
