# :net:download:service-interface

Interface of the download service. Enables other modules to call the download service without actually depending on the implementation.
`DownloadServiceInterface` is a singleton whose static implementation is registered in `:app` during `ClientConfigurator.initialize`.

This module is 100% Kotlin. Conventions below must survive future edits — the ~95 Java call sites across `:app`, `:net:download:service`, `:net:sync:service`, `:storage:database`, `:storage:importexport` (including three Java subclasses of the abstract classes here) depend on them.

- The five `WORK_*` constants on `DownloadServiceInterface` are `const val`. `DownloadServiceInterfaceImpl`'s unqualified inherited reads catch a regression to plain `val` — that shape forces `Companion.getWORK_TAG()` on every Java caller — but not a regression to `@JvmField val`, which emits the identical externally-visible `public static final` field on the outer class. What `const val` adds over `@JvmField val` is a `ConstantValue` attribute, so Java call sites inline the literal at their own compile time and need no class initialization; `javap -v` is the check that distinguishes the two.
- The three static singleton accessors (`DownloadServiceInterface.get()`/`setImpl()`, `FeedUpdateManager.getInstance()`/`setInstance()`, `AutoDownloadManager.getInstance()`/`setInstance()`) and both `DownloadRequestCreator.create(...)` overloads carry `@JvmStatic`. Without it, Java callers would need `.Companion.` qualification, breaking every call site.
- `DownloadServiceInterface.isDownloadingEpisode`/`isEpisodeQueued`/`getProgress` take `url: String?`, not `String`. Tightening this to non-null looks like an obvious cleanup but is not: several Java callers pass a possibly-null `getDownloadUrl()` with no guard, relying on `HashMap.containsKey(null)` returning `false`. A non-null parameter would turn that into a crash via `Intrinsics.checkNotNullParameter`. The same reasoning also covers the abstract-method `Context?`/`FeedItem?`/`FeedMedia?` parameters on `DownloadServiceInterface`, `FeedUpdateManager` and `AutoDownloadManager`: their still-Java implementations in `:net:download:service` are not compile-checked against Kotlin nullability, so tightening those declarations would convert today's latent null-dereference into a guaranteed crash at several Java call sites rather than fix anything (see `net/download/service/README.md`).
- `setCurrentDownloads` installs the caller's map by reference — never copy it (`.toMap()`, `HashMap(...)`, etc.). At least one caller hands the same map instance to another consumer afterward and relies on both references observing later mutations.
- Test tasks are flavored (`free`/`play`, from `playFlavor.gradle`): use `testFreeDebugUnitTest` / `testPlayDebugUnitTest`, not a bare `testDebugUnitTest` (it doesn't exist). Always pass `--rerun`, since Gradle otherwise reports `UP-TO-DATE` without re-executing — and run the two flavors as **two separate** `./gradlew` invocations: `--rerun` on a combined two-task command line forces only one of them, and the other silently reports `UP-TO-DATE` without executing.
- This module's tests are Kotlin. They prove the `WORK_*` constants' **values** but not their `const val`-shaped-static-field **shape**, and they prove nothing about `@JvmStatic`'s presence on the singleton accessors or on `FileNameGenerator.generateFileName` — Kotlin resolves all of these identically regardless of the annotation. The live compile-time guard is external: `DownloadServiceInterfaceImpl`'s unqualified inherited `WORK_*` reads and the ~87 Java call sites of the `@JvmStatic` accessors, both compiled by `:app:assembleDebug`. `FileNameGenerator.generateFileName`'s `@JvmStatic` has no remaining Java caller anywhere in the repo and is therefore unguarded. `javap -p` (`-v` for the `WORK_*` constants, to see the `ConstantValue` attribute) against the built classes is the check to run before changing any of this.
